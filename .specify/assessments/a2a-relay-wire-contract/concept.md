# Concept: A2A v1.0 as the relay's wire contract

- **Slug**: a2a-relay-wire-contract
- **Created**: 2026-09-03
- **Recommended option**: Option B — Replace the wire with A2A v1.0, an optional BrainBuddy extension, BrainBuddy-side deduplication and a background observer

Inputs: problem.md, research.md (intake.md skipped — the idea was supplied directly by the product owner).

## Options

### Option A — A2A adapter beside the bespoke wire, Hermes first (smallest thing that could work)
- **Sketch**: Keep the 007 generic HTTP connector and its envelope exactly as ratified and add a second connector kind that speaks the standard. When connecting an agent the owner picks the kind. The new kind is validated against the unmodified Hermes A2A plugin only; cloud-hosted agents are "should work, untested". Everything downstream of the connector — consent preview, run projection, retention, disconnect — is shared. Nothing is removed and the 007 baseline is not touched.
- **Appetite**: small (days) as scoped to Hermes alone. It becomes medium the moment the problem's goals are honoured: the honest-disclosure mode for agents without a single-start guarantee and the observer for a runtime that only reports at the end are both needed for Hermes itself, so the "small" scope still carries the hardest part.
- **Trade-offs**: Wins — smallest blast radius, no change to 007's ratified wire, the bespoke wire remains as a fully controlled fallback. Sacrifices — two wire contracts to secure and test (the SC-003 security suite and SC-008 barrier tests run twice), one of them with zero consumers; the cloud-hosted population stays unreached; guarantee semantics diverge per kind (required single-start on one, best-effort plus disclosure on the other) and the owner-facing copy has to explain both; contradicts owner decision 5 (bespoke wire removed, custom agents via SDK). Unknowns — the same Fly long-lived-activity question as Option B; whether anyone would ever choose the bespoke kind.
- **Rabbit holes**: keeping two connector kinds' capability and honesty semantics consistent as either evolves; the temptation to "fix" Hermes upstream so the adapter can stay thin; a migration of the bespoke kind that is always planned and never done.

### Option B — Replace the wire with A2A v1.0, optional BrainBuddy extension, BrainBuddy-side deduplication, background observer (matches owner decisions 1–8)
- **Sketch**: The relay speaks only the standard. Connecting an agent means giving BrainBuddy the agent's public HTTPS address and a bearer or API-key credential; BrainBuddy reads the agent's published card, learns which of reply and cancel it offers and whether it declares the optional BrainBuddy extension, and reports the resulting guarantee level honestly before any hand-off. A hand-off sends exactly the previewed content as one message inside a fresh conversation context owned by that run. Before any resend BrainBuddy asks the agent whether it already holds a task for that context; agents implementing the extension carry the strong single-start guarantee, all others are admitted with a visible "duplicate start possible on retry" disclosure. Run state is observed by BrainBuddy itself — a background observer follows the agent's stream or polls it, tolerating a reply that blocks for up to 300 seconds — and mapped onto the existing 007 projection; the agent's own notifications only accelerate what the observer would find and are never authoritative alone. The generic HTTP connector is removed; custom agents connect through any A2A SDK. Everything the owner sees — consent preview, **Sent** / **Delivery unconfirmed**, **Stopped reporting**, **Agent reported complete** — stays as 007 specifies.
- **Appetite**: medium (weeks) — the owner's budget (decision 8), no calendar date. research.md rates the effort beyond the ~719 counted wire lines (a JSON-RPC client, the observer, a rewritten inbound path, re-running SC-003 and SC-008, a new review campaign) as an assumption, so treat the budget as tight, not comfortable.
- **Trade-offs**: Wins — every goal in problem.md: both populations, zero agent-side code, an SDK ecosystem in six languages plus validation tooling (Inspector, TCK), and the two reference runtimes named in the definition of done; one wire to secure; the 007 Product Boundary ("Hermes is not a required runtime or permanent dependency") finally true. Sacrifices — (1) the hard 007 FR-006 precondition ("no single-start guarantee, no hand-off") becomes a two-tier guarantee, and for most agents single-start is best-effort plus disclosure; (2) FR-009's authoritative monotonic version and freshness must be synthesised by BrainBuddy from what it observes, because the standard carries no version counter and delivers notifications at-least-once — and Hermes signs its push without timestamp or nonce, so push can never be trusted on its own; (3) a long-lived observer per active run is new operational surface on Fly; (4) **Delivery unconfirmed** must be re-derived for a call that may legitimately block for five minutes; (5) dependence on a young standard (16 breaking changes to reach v1.0, v1.0.1 within eleven weeks) and on Hermes still answering pre-1.0 method aliases; (6) removing the only wire BrainBuddy fully controls leaves no fallback if a future protocol revision breaks a reference runtime. Unknowns — Fly capacity for observers; the cloud platforms' accepted credential schemes; residual duplicate risk for agents with in-memory task stores (Hermes forgets tasks on restart, so the pre-resend check can honestly find nothing).
- **Rabbit holes**: implementing all three transports (streaming, push, polling) when one plus push-as-accelerator would do; defining the extension broadly (it should promise single-start on replay and nothing else); agent-card signature verification growing into a mini-PKI; "while we're here" OAuth2 or mTLS; chasing protocol revisions mid-build; an optional upstream Hermes patch becoming a silent dependency; the observer growing into a general job system; private-network egress for home-hosted agents.

### Option C — Keep the bespoke wire; ship a Hermes plugin that speaks it (do nothing inside BrainBuddy)
- **Sketch**: BrainBuddy is untouched. The shim moves to the agent side as a Hermes platform plugin — upstream or in a separate repository — implementing the 007 capabilities/start/reply/cancel envelope and signed, versioned run events. Hermes operators get a working relay with the strong guarantees exactly as 007 specified; every other agent stays unreachable until its operator writes their own shim. The pure do-nothing variant (no plugin either) is the cost-of-inaction baseline in problem.md and is not treated as an option: it keeps zero agents reachable indefinitely.
- **Appetite**: small (days) for the plugin, zero inside BrainBuddy — but the plugin's maintenance is perpetual and lives outside the repository's review, CI and landing gates.
- **Trade-offs**: Wins — no change to a ratified baseline, no review campaign, no security re-run; strong single-start and ordering guarantees intact because BrainBuddy authors the shim; sidesteps the Fly observer question because the plugin pushes asynchronously. Sacrifices — Hermes-only, so the provider-agnostic promise stays unmet and the cloud-hosted population unreachable; contradicts owner decisions 1 and 5; the 007 boundary "Hermes is not a required runtime" becomes false in practice; BrainBuddy-specific code sits in a third party's tree subject to upstream review and drift, or in a repository BrainBuddy must maintain; every additional agent restarts the treadmill. Unknowns — whether Hermes maintainers would accept it; whether anyone would install it.
- **Rabbit holes**: upstream acceptance cycles; keeping the plugin in lock-step with envelope changes; "one plugin per agent" quietly becoming the product.

## Recommendation

**Option B.** It is the only option that reaches the first two success metrics — at least two unmodified runtimes (the Hermes A2A plugin and an official a2a-sdk sample agent) completing an end-to-end hand-off, with zero BrainBuddy-specific code on the agent side. Option A reaches one runtime and keeps a dead wire alive; Option C reaches one runtime and buries the promise. B is also the only option consistent with all eight owner decisions, and the only one under which 007's Product Boundary ("provider-agnostic; Hermes is a reference connector, not a permanent dependency") becomes true rather than aspirational. The remaining metrics — replay safety, SC-003 on the new wire, web/iOS parity, honest degradation — are constraints B must carry, not differentiators.

What the owner's decisions sacrifice, stated plainly so the decision stage can weigh it: the strong single-start guarantee 007 treated as a precondition becomes the exception (extension-capable agents) rather than the rule, and the majority of agents will run under best-effort deduplication with a disclosed residual risk; against Hermes specifically the projection will be sparse — **Sent**, then possibly nothing but a **Stopped reporting** overlay until the terminal report — honest, but less informative than the bespoke wire could have been; removing the generic HTTP connector removes the only wire BrainBuddy fully controls; and the medium appetite covers a rework that research.md rates as larger than its line count suggests.

Two conditions on the recommendation: (1) the Fly long-lived-activity question is answered during planning, before implementation begins — if per-run observers are not viable, the fallback inside B is periodic polling from the existing maintenance thread at the cost of projection latency, not a change of option; (2) the BrainBuddy extension is scoped to single-start on replay and nothing else, so it cannot grow into a second bespoke contract.

## Out of Scope (for the recommended option)

- OAuth2, mTLS and any other credential scheme beyond bearer or API key (owner decision 1).
- Compatibility with, or continued support for, the 007 bespoke envelope and the generic HTTP connector (decision 5); the ratified 007 baseline is history, not re-ratified (decision 3).
- Any dependency on an upstream Hermes change; an upstream patch may be proposed but nothing waits for it (decision 6).
- BrainBuddy acting as an agent server — being discovered or called by other agents. BrainBuddy is the calling side only.
- Agent discovery, registries, catalogues or a marketplace; the owner supplies the agent's address.
- Private-network or non-HTTPS agent destinations; 007 FR-004 egress rules stay.
- Rendering streamed partial output or structured progress beyond the plain-language progress text 007 already allows (007 backlog).
- Cancellation beyond what the agent itself supports; a cancel remains "requested" until the agent confirms it, and agents that only mark a task cancelled without aborting the work are reported exactly that way (007 AC-017).
- Multi-agent fan-out, routing, delegation chains, workflow builders, billing, quotas, managed hosting, connection templates, shared connections, organisation policy (007 backlog and Out of Scope).
- Task classification, planning, decomposition, provider selection, automatic retry, completion verification or automatic Task completion (007 FR-012).
- Any protocol version other than v1.0.x, including compatibility with pre-1.0 method names.
