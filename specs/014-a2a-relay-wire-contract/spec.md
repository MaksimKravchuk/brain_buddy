# Feature Specification: A2A Relay Wire Contract

**Feature Branch**: `014-a2a-relay-wire-contract`

**Created**: 2026-09-03

**Status**: Accepted (founder-accepted 2026-09-04)

**Input**: User description: "Hand off a BrainBuddy task to any user-operated agent that speaks the open Agent2Agent (A2A) v1.0 protocol, replacing the bespoke relay envelope no agent implements, while keeping every consent, security, honesty and retention guarantee of feature 007"

## Relationship to feature 007

Feature 007 (`specs/007-external-agent-relay/`) ratified a bring-your-own-agent relay whose connector envelope is BrainBuddy-specific. No agent implements that envelope, so the provider-agnostic promise of 007 is unfulfilled and zero agents are reachable. This feature replaces **only the wire contract** between BrainBuddy and the agent with the Linux Foundation Agent2Agent protocol, version 1.0.x, and removes the bespoke envelope entirely.

Everything in 007 that does not describe the bespoke wire remains binding and is referenced here rather than restated: the product boundary (BrainBuddy owns faithful dispatch and honest display, never execution), the hand-off consent review (007 FR-005), server-verified reauthentication for sensitive operations (007 FR-003), egress safety (007 FR-004), the run and compact Task surfaces with their expiry marker (007 FR-010), honest copy (007 FR-011), no mutation of the canonical Task (007 FR-012), the silence rule (007 FR-013), inert rendering of agent content (007 FR-014), retention (007 FR-015), disconnect (007 FR-016), correlation IDs (007 FR-017), interruption and offline behavior (007 FR-018) and rollout-OFF semantics (007 FR-019). Where this specification names a 007 requirement, that requirement applies unchanged unless a clause here narrows it.

The 007 requirements that described the bespoke wire — the connector adapter allowlist and capability probe (007 FR-001; 007 FR-002 in part, its connector-response and capability-disclosure clauses), the `start`/`reply`/`cancel` command envelope (007 FR-006 in part, its `start(...)` call shape and connector-side dedup clause; 007 FR-007), the state mapping and versioned event envelope (007 FR-008 in part, its connector-report mapping; 007 FR-009) and the reporting-instructions manifest fields (007 FR-005 in part) — are superseded by FR-001 through FR-012 below. The generic clauses of those partly superseded requirements stay binding exactly where this specification cites them: the last-contact, stale-threshold and stale rule of 007 FR-002 (FR-002 below), the three dispatch states and the retry rule of 007 FR-006 (FR-006 below), and the projection overlays, terminal locking and label derivation of 007 FR-008 (FR-009 below). The 007 ratified baseline stays as history and is not re-ratified.

This feature does not touch voice capture, capture review, native Task ownership, Weekly Review or the CRT canvas. It has no impact on the primary loop; an external run remains an optional evidence lane after a canonical Task exists.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Connect an A2A agent by its card (Priority: P1)

A signed-in user adds an agent they operate by entering its address and a credential. BrainBuddy discovers the agent through its published card, verifies the credential and shows what the agent supports, including which guarantee tier the hand-off will run under, before any task can be handed off.

**Why this priority**: No task can be handed off safely or truthfully until BrainBuddy has a valid, owner-scoped connection to an agent whose protocol, interface, authentication scheme and guarantees are known.

**Independent Test**: Add the official a2a-sdk sample agent and the Hermes A2A plugin as connections, complete recent reauthentication, test each connection and inspect the saved connection without dispatching a task.

**Acceptance Scenarios**:

1. **AC-001**: **Given** a signed-in user who completed server-verified reauthentication within the previous 15 minutes, **when** they save an agent address whose card advertises protocol version 1.0.x with a JSON-RPC interface over HTTPS and a supported authentication scheme, and the connection test succeeds, **then** BrainBuddy shows the agent name, version, description, skills, streaming and push-notification support, the guarantee tier, tested status and last contact.
2. **AC-002**: **Given** an address that is unreachable, does not serve an agent card, or serves a card without a usable protocol version or interface, **when** the user tests it, **then** BrainBuddy shows a distinct actionable category (unreachable, not an A2A agent, unsupported protocol version, no supported interface) and does not mark the connection ready.
3. **AC-003**: **Given** a reachable agent that rejects the supplied credential, **when** the user tests it, **then** BrainBuddy reports invalid credentials without displaying the submitted secret and does not mark the connection ready.
4. **AC-004**: **Given** a card that requires only authentication schemes this feature does not support (for example OAuth2 or mutual TLS), **when** the user tests it, **then** BrainBuddy names the unsupported scheme, explains that bearer tokens and API keys are supported, and does not mark the connection ready.
5. **AC-005**: **Given** a card that does not declare the BrainBuddy single-start extension, **when** the test succeeds, **then** the connection is ready under the best-effort tier and the disclosure explains that BrainBuddy checks for an existing task before any retry but a duplicate remains possible if the agent forgets its tasks.
6. **AC-006**: **Given** an agent address on a loopback, link-local, metadata or private network, **when** BrainBuddy validates it, **then** the destination is refused exactly as 007 FR-004 requires unless the deployment separately governs that network class.
7. **AC-031**: **Given** a discovered agent card whose name, version, description, skill names or descriptions, offered authentication-scheme names or interface address carry markup, a `javascript:` address or a private or metadata address, or a connection-test error detail carrying such a value, **when** any connection, hand-off review or run surface renders them on web or iOS, **then** every card-sourced value and every error-detail value is shown as plain inert text — never an anchor or a link the platform can open, never interpreted as HTML or markdown, never auto-linkified — bounded to the card-summary lengths, exactly as an agent-reported result link is treated (design states D-01-S10, D-01-S11, D-01-S15, D-01-S17, D-01-S20, M-01-S09, M-01-S13, M-01-S15, M-01-S18, and the agent name on D-02 and M-02).
8. **AC-037**: **Given** an agent that rate-limits the connection test (HTTP 429, or an agent-specific rate-limit code from the allowlist — Hermes `-32051`), **when** the user tests it, **then** BrainBuddy shows the actionable **rate limited** category ("The agent is rate limiting") with the agent's retry-after when it gave one, records `last_test_error_code = a2a_rate_limited`, leaves the connection untested — never ready — until a later successful test, and lets the user test again after `retry_after_seconds` — at once, with "Test again shortly.", when the agent gave no retry-after (design states D-01-S25 and M-01-S22, following the D-03-S03 pattern).

### User Story 2 - Review and hand one task to the agent (Priority: P1)

From an existing Task, a user chooses **Hand to agent**, selects one tested connection, reviews exactly what will leave BrainBuddy together with the guarantee tier, and confirms one dispatch.

**Why this priority**: This is the constitutional consent boundary before task content leaves BrainBuddy, and the point where the single-start promise is either kept or honestly qualified.

**Independent Test**: Open one Task, select a tested connection, remove one supporting item, confirm, and verify that exactly one task exists at the agent with the reviewed content and that replaying the confirmation creates no second task.

**Acceptance Scenarios**:

1. **AC-007**: **Given** a tested, non-stale connection and an existing Task, **when** the user opens the hand-off review, **then** BrainBuddy lists every value that will be sent: the Task title, the Task details when selected, each selected supporting item, the stable Task ID and the new run ID that travel with the message, the destination agent, the guarantee tier disclosure, the cancellation-support disclosure, the external-copy notice and, when the agent supports push notifications, the disclosure that BrainBuddy registers a private callback address carrying a per-run token with the agent, which the agent holds until the run ends.
2. **AC-008**: **Given** the hand-off review, **when** the user removes a supporting item or cancels, **then** the removed item is not sent and cancellation creates no task at the agent and no visible run.
3. **AC-009**: **Given** a confirmed hand-off, **when** dispatch succeeds, **then** exactly one task exists at the agent, exactly one Execution run is linked to the Task, and the timeline shows **Sent** followed by agent-reported state.
4. **AC-010**: **Given** the same confirmation or dispatch request is replayed, **when** BrainBuddy handles it again, **then** the same run and outcome are returned and no second task is created at the agent, under both guarantee tiers.
5. **AC-011**: **Given** a stale, failed-test, disconnected or wrong-owner connection, **when** a hand-off is attempted, **then** BrainBuddy refuses before sending task content and explains the corrective action.
6. **AC-012**: **Given** a tested connection whose agent card has since changed its interface address or authentication requirements, **when** a hand-off is attempted, **then** BrainBuddy refuses, reports that the agent changed, and requires a new successful test before dispatch.
7. **AC-026**: **Given** a best-effort connection with no prior hand-off, **when** the user opens the hand-off review, **then** confirmation stays disabled until the user explicitly acknowledges that a duplicate task is possible, the disclosure links to the published extension specification, and later hand-offs on that connection show the disclosure without a separate acknowledgement.
8. **AC-027**: **Given** a run shown as **Delivery unconfirmed**, **when** the user chooses **Check again** from the run view, **then** BrainBuddy looks the run up at the agent with the same correlation ID and message ID: a found task is adopted and the run shows **Sent**; only when the agent reports no task is the identical message resent once with the same message ID; nothing else is sent, a later **Check again** first finds the task that resend created and does not resend again, and no new run or message ID is ever minted.
9. **AC-030**: **Given** a run shown as **Delivery unconfirmed**, **when** the user chooses **Check again** or a confirmation is replayed while the connection is untested, stale, disconnected or **Agent changed**, or its verified scope was reset since the run was dispatched (agent address, authentication scheme, credential rotation or card drift), or the run's content tier has expired, **then** the lookup may still run (except on a disconnected connection, whose credential no longer exists) but the resend branch is refused with exactly one reason per condition — `connection_not_ready` for an untested, stale or scope-reset connection, `agent_card_changed` for **Agent changed** or a pinned card fingerprint that no longer matches, `run_content_expired` for expired content, `connection_disconnected` for a disconnected connection; the complete list, with `reauthentication_required`, `run_terminal`, `agent_task_missing` and `rollout_disabled`, is FR-006 — nothing leaves BrainBuddy, the run stays **Delivery unconfirmed** and the user is told the corrective action; **when** the resend branch does run, **then** it requires the same recent reauthentication a dispatch requires (a trigger the exchange start spends, FR-004), goes to the interface recorded at dispatch after the card fingerprint is re-checked, and concurrent checks converge on at most one resend.
10. **AC-032**: **Given** BrainBuddy restarts while a confirmed hand-off is still **Queued** (its exchange never started), **when** the process comes back, **then** the run shows **Not sent** with "BrainBuddy restarted before this hand-off was sent. Nothing left BrainBuddy.", offers the hand-off again with the same run ID and message ID — its first-dispatch trigger is unspent because nothing left (FR-004), and the same identifiers are reused only while the rebuilt manifest token still equals the frozen one (FR-005) — and is never shown as **Delivery unconfirmed**; **given** the restart interrupted an exchange that had already started, **then** the run shows **Delivery unconfirmed** and the next scheduled observation only looks the run up by its correlation ID — adopting a found task and otherwise leaving the run for the user's **Check again** — and no background thread ever resends.
11. **AC-034**: **Given** an agent that keeps a request open by dripping bytes (headers or body) beyond the exchange or observation window, **when** BrainBuddy's own deadline for that request passes, **then** BrainBuddy closes the request itself: a hand-off exchange becomes **Delivery unconfirmed** (lookup before any resend, as AC-027) and an observation counts as a failed contact, never a fabricated state; **and given** one connection already holds its configured share of exchange workers, **then** further hand-offs on that connection show **Queued** ("Waiting for a free connection slot; nothing has been sent yet") while other connections' hand-offs and every scheduled observation proceed.
12. **AC-036**: **Given** rollout is OFF and a run is **Delivery unconfirmed**, **when** the user chooses **Check again** or a confirmation is replayed, **then** the correlation-ID lookup runs and a found task is adopted, but the resend branch is refused with `rollout_disabled` — returned after the lookup ran, with the lookup's outcome already applied — and the run stays **Delivery unconfirmed** until rollout is ON again; reply and cancel for existing runs, observation, verified push handling, purge and retention continue meanwhile.

### User Story 3 - Monitor and respond without false claims (Priority: P1)

The user watches the run from the Task. They can see the agent-reported state, answer a question when the agent asks one, request cancellation, inspect the result, and distinguish agent-reported completion, failure, cancellation and silence.

**Why this priority**: The relay is useful only if the user understands what the agent reported without BrainBuddy inventing progress, success or failure, including against agents that answer slowly or forget their tasks.

**Independent Test**: Drive one run against a reference agent through working, input-required, completed, failed and canceled states, and against an agent that answers only after a long delay, and inspect both responsive Task surfaces.

**Acceptance Scenarios**:

1. **AC-013**: **Given** a dispatched run, **when** BrainBuddy's own authenticated observation of the agent's task shows a new state, **then** the Task shows the agent name, the reported state, the agent's latest status text when present, last contact and a chronological timeline, without fabricated percentages, stages or ETA.
2. **AC-014**: **Given** an agent that answers a hand-off only after a long delay (up to the deployment-configured reply window, at least 300 seconds), **when** the user watches the run, **then** BrainBuddy shows **Sent** and then agent-reported state without inventing a failure, and shows the true terminal state within one observation interval after the agent finishes.
3. **AC-015**: **Given** an observation in the agent's input-required state and an agent that accepts follow-up messages, **when** the user answers from the Task, **then** BrainBuddy sends the answer once, records it in the timeline, shows the reply as unconfirmed until the agent acknowledges it, and returns the run to a later agent-reported state only after a subsequent authenticated observation.
4. **AC-016**: **Given** an authenticated observation of completion with text or artifacts, **when** it is displayed, **then** the Task says **Agent reported complete**, renders text inertly, shows an agent-reported HTTPS link as inert text the user can copy — never as a clickable link, exactly as the shipped 007 relay renders it — and leaves Task completion under user control.
5. **AC-017**: **Given** an authenticated observation of failed, rejected or canceled, **when** it is displayed, **then** BrainBuddy shows **Failed** with the reason (including "Rejected by agent"), or **Cancelled**, preserves the timeline and does not retry the work.
6. **AC-018**: **Given** the user requests cancellation, **when** the agent accepts the request, **then** BrainBuddy shows **Cancellation requested** until an observation shows the task canceled; **when** the agent answers that cancellation is not supported or the task is no longer cancelable, **then** BrainBuddy says so and keeps the last observed state.
7. **AC-019**: **Given** a non-terminal run with no successful authenticated observation within the configured reporting window, **when** the window expires, **then** BrainBuddy shows **Stopped reporting** with last contact, without claiming the agent stopped or failed.
8. **AC-020**: **Given** an agent that no longer knows the run's task (it answers that the task does not exist), **when** BrainBuddy observes this, **then** the run shows **Agent no longer reports this run** with last contact, keeps the timeline, and offers no reply or cancel control.
9. **AC-021**: **Given** a push notification arrives from the agent, **when** it carries the per-run verification token BrainBuddy registered, **then** BrainBuddy performs an immediate observation and changes state only from that observation; **when** the token is missing or wrong, **then** nothing changes and the rejection is recorded with bounded cardinality.
10. **AC-028**: **Given** a blocked run whose answer the agent acknowledges with a different task in the same conversation (the run's correlation ID), **when** BrainBuddy handles the reply, **then** the reply is not refused, the new task becomes the run's current task, the timeline shows **The agent continued this run in a new task** with both task IDs, the projected state is unchanged until the next observation, and the run keeps its single correlation ID; **when** the agent ends the previous task on its own timeout while the reply is still unconfirmed, **then** the timeline records that the previous task ended and the run stays blocked with the reply pending rather than being marked failed; **when** the reply itself meets a failed task and no successor exists, **then** the run shows the agent's own reason and withdraws the reply control.
11. **AC-029**: **Given** the user requests cancellation and the request itself fails ambiguously (timeout, server error or transport loss), **when** the run is displayed, **then** BrainBuddy keeps the last observed state and the cancel control, shows the request as unconfirmed, does not claim that the agent does not support cancellation, and a later cancel attempt reuses the same command ID; only an explicit agent answer may report cancellation as unsupported or the task as not cancelable.
12. **AC-033**: **Given** a reply whose exchange ends ambiguously (timeout, server error or transport loss) and is never acknowledged, **when** the reply exchange closes or is interrupted, or its deadline passes, whichever comes first, **then** scheduled observation of the run's task resumes, the reply stays in the timeline as unconfirmed, the run is never left unobserved until its identifiers expire, and the reply control is offered again — for a new reply with a new command ID — only after a later observation shows the run blocked again; a reply exchange that a restart interrupted is confirmed only by evidence at the agent (a task in the run's conversation created after the reply command), never by resending it.
13. **AC-035**: **Given** every exchange worker is held by long-running hand-offs, one of them the user's own, **when** the user requests cancellation, **then** the cancel request reaches the agent within its own short timeout without waiting for an exchange worker, and **Cancellation requested** reflects the agent's answer rather than pool saturation.

### User Story 4 - Disconnect and retain only bounded evidence (Priority: P2)

The user can disconnect an agent without exposing its secret or erasing the honest history of runs already attached to Tasks.

**Why this priority**: Credentials and relayed content are sensitive, while past task evidence must remain understandable for a bounded period. This story is unchanged from 007 apart from the identifiers this feature adds.

**Independent Test**: Disconnect a connection after recent reauthentication, inspect existing run history, advance retention cleanup clocks, and run the account-purge flow.

**Acceptance Scenarios**:

1. **AC-022**: **Given** a connected agent and reauthentication no older than 15 minutes, **when** the user confirms disconnect, **then** BrainBuddy destroys the credential, stops observing and registering push notifications for that connection's runs, prevents new hand-offs and replies, and preserves bounded redacted history per 007 FR-016.
2. **AC-023**: **Given** saved credentials, **when** any connection, Task, audit, export, log or error view is rendered, **then** the secret is never returned or displayed after save (007 FR-003).
3. **AC-024**: **Given** relayed content reaches 30 days, **when** retention cleanup runs, **then** content is deleted and only coarse metadata may remain: agent task identifiers, message identifiers and identifier fingerprints for at most 90 days (007 FR-015), and the run ID — which is also the run's correlation ID — with the run row until account purge; the connection's own discovered card summary is connection configuration, not run content: it survives every sweep while the connection is live and is erased on disconnect together with the credential.
4. **AC-025**: **Given** the user invokes account deletion, **when** purge completes, **then** connections, credentials, card metadata, runs, observations and audit data are removed under the existing purge contract.

### Edge Cases

- A card fetch that redirects, serves multiple interfaces, or lists a JSON-RPC interface on a different host than the card: redirects are refused per 007 FR-004; the first JSON-RPC interface with protocol version 1.0.x is used; an interface whose destination fails 007 FR-004 validation makes the connection unsupported.
- An agent that returns a direct message instead of a task when the hand-off is sent: the run records **Agent reported complete** with that message text as the result, since the agent chose to answer without creating a task.
- An agent that reaches a terminal state within the dispatch itself (the reference sample agent does): the run shows **Sent** and the terminal state in the same timeline without a fabricated intermediate state.
- An agent that rate-limits the dispatch before creating a task: the run is **Not sent** with an actionable "agent is rate limiting" category; no task exists, so a later confirmation may retry with the same run ID and message ID (while the rebuilt manifest token still equals the frozen one, FR-005).
- A dispatch that times out or fails ambiguously: **Delivery unconfirmed**; before any resend BrainBuddy looks the run up at the agent by its correlation ID; if a task exists it is adopted, otherwise the identical message is resent. The user can trigger that same check from the run view (**Check again**, AC-027); it never mints a new run or message ID. The resend branch has preconditions the lookup does not: it is refused while the connection is untested, stale, disconnected or **Agent changed**, when the connection's verified scope was reset since the dispatch, or when the run's content has expired, and it needs the same recent reauthentication as a dispatch (AC-030); concurrent checks converge on one resend.
- An agent that keeps a request open by dripping bytes: BrainBuddy's own absolute deadline — the operation's window plus a margin — closes the request; an exchange becomes **Delivery unconfirmed**, an observation is a failed contact (AC-034). One connection may hold only a configured share of exchange workers at a time; its further hand-offs wait as **Queued** while other owners' hand-offs and every scheduled observation proceed.
- A cancel request while every exchange worker is held: cancel and push registration run on a dedicated control pool with a short timeout, so **Cancellation requested** never waits behind the hand-off exchanges it is meant to end (AC-035).
- BrainBuddy restarts while a hand-off is **Queued**: nothing had left BrainBuddy, so the run becomes **Not sent** with "BrainBuddy restarted before this hand-off was sent. Nothing left BrainBuddy." and the hand-off is offered again with the same run ID and message ID; an exchange that had started is recovered as **Delivery unconfirmed** by lookup only; no background thread ever resends (AC-032).
- A reply that is never acknowledged: observation of the run resumes once the reply exchange closes, is interrupted, or reaches its deadline; the reply stays in the timeline as unconfirmed and the reply control returns, for a new reply, only after the run is observed blocked again; a restart-interrupted reply is confirmed only by succession evidence at the agent, never by resending it (AC-033).
- A confirmed hand-off queued behind other hand-offs: the message waits for a free exchange worker; the run shows **Queued** with the explanation "Waiting for a free connection slot; nothing has been sent yet", never **Sent**, until the exchange actually starts; no lookup runs until the message has left, and the reply window counts from the moment the exchange starts, not from confirmation.
- An agent that does not keep BrainBuddy's correlation ID on the task it creates (the returned task carries a different one): BrainBuddy records that on the connection and never resends for it at all — not on its own (no background thread ever resends) and not on **Check again**, because an empty lookup on such a connection proves nothing — so an empty lookup keeps **Delivery unconfirmed**, and the best-effort disclosure says so.
- An agent that refuses push-notification registration: the run continues by observation only; nothing is shown as an error to the user.
- A valid push notification that arrives after the run has closed (the agent's terminal push racing BrainBuddy's own terminal observation is the common case): it triggers no observation and is recorded as a late push, never as a forged or wrong token, because the token's fingerprint is kept until the run's identifiers expire.
- A run whose content is due to expire but not yet swept: every read already projects it as expired — no manifest, question, result, reason, blocked reason, artifact placeholders, availability marker or agent status text — before the sweep runs (007 FR-015, SC-007).
- An agent that fails a waiting task on its own timeout (Hermes fails any task that has waited 300 seconds, including one waiting for the user's answer): while a reply is unconfirmed or its exchange is open, a terminal report about the previous task is recorded in the timeline and does not lock the run; the successor task the reply returns supersedes it; when the reply itself meets a failed task and no successor exists, the run shows the agent's own reason and withdraws the reply control (AC-028).
- A cancel request that fails ambiguously (timeout, server error, transport loss): the request is shown as unconfirmed, the last observed state and the cancel control are kept, and a later attempt reuses the same command ID; only an explicit agent answer may report cancellation as unsupported or the task as not cancelable (AC-029).
- An agent whose task record exceeds BrainBuddy's task response cap: the task state is still observed through the agent's task list, the run reaches its true terminal state, and the result is marked unavailable (too large to store) with a visible marker instead of the run being shown as **Stopped reporting**.
- Artifacts that are not text (files, structured data): shown as non-interactive placeholders naming the content type; an HTTPS link inside them is shown as inert text the user can copy, never as a clickable link; nothing is fetched server-side to render a run.
- Text that exceeds the configured result, question or status limits: truncated with a visible marker; the observation is still accepted.
- Barrier-concurrent duplicate `start`, `reply` and `cancel` submissions converge on one durable winner and at most one agent-side action, exactly as 007 requires.
- Editing or completing the Task after dispatch does not rewrite the frozen sent content; a later hand-off creates a distinct run.
- Mobile interruption, app closure and offline windows behave as 007 FR-018: reopening loads the server projection, offline clients label cached state as potentially stale and disable reply and cancel rather than queue them.
- Rollout OFF blocks new connections, tests, credential changes, hand-off previews and fresh dispatches; observation of already-dispatched runs, verified push handling, safe reply and cancel for existing runs, purge and retention continue (007 FR-019). A delivery check (**Check again** or a replayed confirmation) is allowed only as far as its lookup — an authenticated observation that adopts a found task — while its resend branch is refused, so the run stays **Delivery unconfirmed** until rollout is ON (AC-036).
- An agent card that changes while a run is active: observation of that run continues at the interface recorded at dispatch; new hand-offs on that connection require a new successful test (AC-012). Observation of an active run is never redirected to an interface that was not tested.
- Many concurrent runs for one owner: there is no per-owner cap; every non-terminal run is observed on the same schedule, and the deployment's general rate limiting is the only bound. Hand-off exchanges, observations and control calls (cancel, push registration) run in three separate bounded pools, queued exchanges are served owner by owner and one connection may hold only a configured share of exchange workers, so one owner's slow agents never delay another owner's observations, hand-offs or cancellations; every outbound request carries an absolute deadline; observations of runs on an unreachable host are coalesced to one probe per connection per interval; a run past its reporting window is observed at a bounded backed-off interval until its identifiers expire (FR-008).

## Clarifications

### Session 2026-09-03

- Q: Which agent runtimes and authentication schemes are in scope? → A: Any A2A v1.0.x agent reachable over public HTTPS with bearer-token or API-key authentication, whether self-hosted or cloud-hosted; OAuth2 and mutual TLS are deferred (product owner).
- Q: Are agents without the BrainBuddy extension admitted? → A: Yes, under a best-effort tier with BrainBuddy-side deduplication and an honest disclosure; extension-capable agents get the strong guarantee (product owner).
- Q: Does the bespoke wire survive alongside A2A? → A: No; it is removed entirely (product owner).
- Q: Must the relay work with the unmodified Hermes A2A plugin? → A: Yes; an upstream patch may be proposed but nothing depends on it (product owner).
- Q: What is the definition of done? → A: End-to-end hand-off to the unmodified Hermes A2A plugin and to an official a2a-sdk sample agent, three replays produce one task, the 007 security suite passes on the new wire, web and iOS show one projection (product owner).
- Q: Appetite and deadline? → A: Medium, weeks, no calendar deadline; release through exact-SHA review, CI and ASK authority as for 007 (product owner).
- Q: Where is the best-effort single-start disclosure shown? → A: On the connection after every successful test and again in every hand-off review before confirmation (product owner).
- Q: Is the BrainBuddy single-start extension published? → A: Yes, under a public, stable identifier with a short public specification in the repository documentation (product owner).
- Q: How is the unmodified Hermes plugin verified? → A: In CI against the unmodified plugin code with a stub agent handler and no model, plus one attended live run against a real Hermes as release evidence before rollout (product owner).
- Q: How many non-terminal runs may one owner have at once? → A: No per-owner limit; background observation scales with active runs and is bounded only by the deployment's general rate limiting (product owner).
- Q: Should best-effort agents only be warned about, or acknowledged? → A: The first hand-off on a best-effort connection requires a one-time explicit acknowledgement that a duplicate is possible; later hand-offs only show the disclosure (product owner, design sign-off 2026-09-03).
- Q: ADR-0006 forbids the word Context in the product; which terms replace it? → A: "supporting items" for the optional payload items and "correlation ID" for the identifier the protocol calls contextId; protocol field names appear only in technical artifacts and never in client-facing responses (product owner, design sign-off 2026-09-03).
- Q: Does the best-effort disclosure link to the published extension specification? → A: Yes, so the owner knows what to ask their agent operator to declare (product owner, design sign-off 2026-09-03).
- Q: What happens when the agent answers a reply with a different task in the same conversation? → A: BrainBuddy adopts it as the run's current task, never refuses the reply, keeps the run's single correlation ID and records **The agent continued this run in a new task** in the timeline; while a reply is unconfirmed or its exchange is open, a terminal report about the previous task is recorded but does not lock the run, and the successor supersedes it (review campaign 1, 2026-09-03).
- Q: Can the user recover a **Delivery unconfirmed** run from the run view? → A: Yes; **Check again** replays the same lookup-before-resend with the same correlation ID and message ID and never starts a new send (review campaign 1, 2026-09-03).
- Q: What does BrainBuddy claim when a cancel request itself fails? → A: Nothing about the agent's capability: only an explicit agent answer may report cancellation as unsupported or the task as not cancelable; a timeout, server error or transport loss leaves the request unconfirmed with the cancel control still available (review campaign 1, 2026-09-03).
- Q: How long is a live connection's discovered card summary kept? → A: For the connection's lifetime, as connection configuration; it is erased on disconnect together with the credential. The 90-day audit bound applies only to audit entries that name the card, not to the live connection's card summary (product owner, 2026-09-04).
- Q: Are agent-reported result links clickable? → A: No; they stay inert text the user can copy, exactly as the shipped 007 relay renders them, because only syntax is available server-side and a publicly named host can resolve to a private or metadata address at click time (product owner, 2026-09-04).
- Q: What does the run show while a confirmed hand-off waits for a free exchange worker? → A: **Queued** with "Waiting for a free connection slot; nothing has been sent yet"; it becomes **Sent** only once the exchange starts, never before (review campaign 1 honesty fix, 2026-09-04).
- Q: What happens to a hand-off that was still **Queued** when BrainBuddy restarted? → A: It is provably unsent, so it is settled as **Not sent** ("BrainBuddy restarted before this hand-off was sent. Nothing left BrainBuddy.") and offered again with the same run ID and message ID; only an exchange that had already started is recovered as **Delivery unconfirmed**, and only by lookup — no background thread ever resends task content (review campaign 2, 2026-09-04).
- Q: May **Check again** or a replayed confirmation resend on a connection that is stale, changed, re-scoped since the dispatch, or whose run content has expired? → A: No; the lookup may run, but the resend branch is refused with the existing reasons and the run stays **Delivery unconfirmed**. When the resend does run it needs the same recent reauthentication as a dispatch, goes to the interface recorded at dispatch, and concurrent checks converge on one resend (review campaign 2, 2026-09-04).
- Q: How long is observation of the previous task suspended while a reply is pending? → A: Only while the reply exchange is open, and at most until the exchange deadline; then scheduled observation resumes, an unacknowledged reply stays in the timeline as unconfirmed, and the reply control returns — for a new reply — only once the run is observed blocked again (review campaign 2, 2026-09-04).
- Q: What does **Check again** do while rollout is OFF? → A: The lookup runs (it is an authenticated observation) and a found task is adopted; the resend is refused and the run stays **Delivery unconfirmed** until rollout is ON (review campaign 2, 2026-09-04).
- Q: How is text taken from the agent's card rendered? → A: As inert plain text on every surface — never a link, never interpreted as markup, never auto-linkified — exactly like an agent-reported result link (review campaign 2, 2026-09-04).
- Q: What does a rate-limited connection test show? → A: The **rate limited** category with the agent's retry-after; the connection stays untested until a later successful test (review campaign 2, 2026-09-04).
- Q: Is the run's correlation ID erased at 90 days? → A: No, and BrainBuddy does not pretend it is: the correlation ID is the run ID, retained with the run row as coarse metadata until account purge; the 90-day bound applies to agent task IDs, message IDs and fingerprints (review campaign 2, 2026-09-04).
- Q: Can a cancel request wait behind hand-off exchanges? → A: No; cancel and push registration run on a dedicated control pool with a short timeout, never on the exchange pool (review campaign 2, 2026-09-04).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: BrainBuddy MUST let a signed-in owner create, test, inspect, update, rotate credentials for and disconnect an owner-scoped connection to an A2A agent given the agent's address and a credential. BrainBuddy MUST discover the agent through its published agent card at the standard well-known location, MUST require protocol version 1.0.x on a JSON-RPC interface, MUST record the agent's name, version, description, skills, streaming and push-notification support, authentication requirements and interface address, and MUST support exactly two credential schemes: a bearer token and an API key sent in a header named by the card. A card that offers only other schemes MUST leave the connection unsupported with the scheme named. No other connector kind exists after this feature.
- **FR-002**: A connection test MUST return **ready** only after an authenticated response from the agent's task interface, **invalid credentials** after an explicit authentication rejection, **unreachable** after transport failure or expiry of the configured test timeout, **unsupported** when the card, protocol version, interface or authentication scheme cannot be used, and **private destination** when the address or the card's interface fails 007 FR-004 validation (refused before any credential leaves). A test the agent rate-limits (HTTP 429, or an agent-specific rate-limit code from the allowlist — Hermes `-32051`) MUST return the **rate limited** category with `last_test_error_code = a2a_rate_limited` and the agent's retry-after when it gave one; the connection's status stays untested — never ready — until a later successful test, and a retry is allowed after `retry_after_seconds` — at once, with the copy "Test again shortly.", when the agent gave no retry-after (design states D-01-S25 and M-01-S22). Last authenticated contact, the stale threshold and the stale rule apply exactly as 007 FR-002. A previously tested connection whose card has changed its interface address or authentication requirements MUST show the condition **Agent changed** and behave as untested until a new successful test. A stale, untested or changed connection MUST NOT accept a new hand-off.
- **FR-003**: Every connection MUST carry a guarantee tier. **Guaranteed** applies when the agent's card declares the BrainBuddy single-start extension (FR-011); **best-effort** applies otherwise. The tier MUST be disclosed to the owner in plain language on the connection after every successful test and again in every hand-off review before confirmation. The best-effort disclosure MUST state that BrainBuddy checks the agent for an existing task before any retry and that a duplicate remains possible if the agent forgets its tasks or does not keep BrainBuddy's correlation ID on them (in which case BrainBuddy never resends on its own), and MUST link to the published extension specification (FR-011) so the owner knows what to ask their agent operator to declare; the link opens only on explicit user action. The first hand-off on a best-effort connection MUST require an explicit one-time acknowledgement that a duplicate task is possible before confirmation is enabled; later hand-offs on that connection show the disclosure without a separate acknowledgement. The acknowledgement MUST be asked again after any event that resets the connection's verified scope — a change of agent address or authentication scheme, a credential rotation, or detected card drift (**Agent changed**) — because it was given about a different destination. Nothing MUST present best-effort as guaranteed.
- **FR-004**: Secret material, reauthentication triggers and egress rules apply exactly as 007 FR-003 and FR-004 to every card fetch, every task operation and every push-notification registration. A change of the agent's interface address counts as a destination change for the purposes of 007 FR-003 and MUST require a new successful test and recent reauthentication before the next content-bearing dispatch. The resend branch of a delivery check (FR-006) is a content-bearing dispatch and MUST pass the same reauthentication check as a dispatch (`requires_dispatch_reauthentication`); the lookup that precedes it carries no content and needs none. The first-content trigger of 007 FR-003 is spent by `first_dispatch_at`, which BrainBuddy MUST stamp when the exchange starts — the moment the message actually leaves BrainBuddy — and never at reservation; a **Queued** hand-off that never started leaves it unset, so a hand-off that a restart settled as **Not sent** is a first dispatch again when retried and needs recent reauthentication, while the resend of an exchange that had started lies inside the spent trigger.
- **FR-005**: The hand-off review MUST expose an immutable, versioned manifest containing the exact text that will leave BrainBuddy (Task title, optional Task details, each selected supporting item), the stable Task ID and the new run ID that travel with the message, the destination agent, the guarantee tier disclosure, the cancellation-support disclosure and the external-copy notice of 007 FR-005. When the agent advertises push-notification support, the manifest MUST also disclose that BrainBuddy registers a push-notification callback address carrying a per-run token with the agent, and that the agent holds that address until the run ends; the token itself is never shown. Confirmation MUST identify the manifest token; any change to a value, the destination, the callback origin or the run ID invalidates confirmation and requires review again. A **Not sent** run is offered again by reopening the review on its frozen manifest: confirming it reuses the reserved run ID, message ID and idempotency key only when the rebuilt manifest token equals the frozen one; when it differs, confirmation is invalidated as above, a fresh review reserves a new run with a new run ID and message ID, and the earlier run stays **Not sent**.
- **FR-006**: Before dispatch BrainBuddy MUST durably reserve the run ID, a message ID derived from the reserved run ID (which the idempotency key pins), and the protocol's conversation identifier set to the run's stable correlation ID. A confirmed start MUST send exactly one message carrying those identifiers and the Task and run IDs as metadata, and MUST record the agent's task ID when one is returned. Dispatch MUST distinguish **Not sent**, **Sent** and **Delivery unconfirmed** as 007 FR-006, and additionally **Queued** while a confirmed hand-off is still waiting for a free exchange worker: nothing has been sent yet, the run says so, and it becomes **Sent** only once the exchange starts. Before any resend BrainBuddy MUST look the run up at the agent by its correlation ID: a found task MUST be adopted and never resent; only when no task exists MAY the identical message be resent with the same message ID. The user MAY trigger that check from the run view while the run is **Delivery unconfirmed** (**Check again**); the check reuses the run's correlation ID and message ID and never starts a new send. The only content-bearing sends that exist are a confirmed hand-off, its user-triggered replay (a replayed confirmation or **Check again**) and a user reply: no background thread — the observer scheduler, the observation pool, the exchange pool, restart recovery or the retention sweep — MUST ever emit a content-bearing message, and restart recovery only looks a run up. The resend branch (never the lookup) MUST be refused, leaving the run **Delivery unconfirmed**, with exactly one reason per condition: `connection_not_ready` when the connection is not ready, is stale, or its verified scope was reset since the run was dispatched (agent address, authentication scheme, credential rotation or card drift); `agent_card_changed` when the connection is **Agent changed** or the run's pinned card fingerprint no longer matches the connection's; `run_content_expired` when the run's content tier has expired; `reauthentication_required` when the dispatch reauthentication rule (FR-004) applies and no valid recent reauthentication was supplied; and `rollout_disabled` while rollout is OFF (FR-016) — the lookup still runs first and a found task is adopted, so this reason is returned after the lookup ran, with the lookup's outcome already applied. Three conditions refuse the whole check before any lookup: `connection_disconnected` when the connection is disconnected (its credential no longer exists), `run_terminal` when the run is already terminal, and `agent_task_missing` when the agent has answered that the run's task no longer exists. When the resend runs, it MUST satisfy the dispatch reauthentication rule (FR-004; the trigger is spent by the exchange start, so the resend of an exchange that had started lies inside it), MUST go to the interface recorded at dispatch after re-checking the card fingerprint, and MUST be serialised per run so that concurrent checks converge on at most one resend (SC-008). After a restart, a hand-off whose exchange never started (**Queued**) is provably unsent: it MUST be settled as **Not sent** with the reason `restarted_before_send` and offered again with the same run ID and message ID (under the FR-005 token rule; its `first_dispatch_at` stays unset because nothing left, FR-004), never labelled **Delivery unconfirmed**; an exchange that had started is recovered as **Delivery unconfirmed** by lookup only. Every task BrainBuddy adopts — from the dispatch answer, a lookup or a reply — MUST carry the run's correlation ID; when the agent's first answer shows that it did not keep BrainBuddy's correlation ID on its task, BrainBuddy MUST record that on the connection and MUST NOT resend for it at all — not on its own and not on **Check again**, because an empty lookup on such a connection proves nothing — so an empty lookup keeps the run **Delivery unconfirmed**. A guaranteed-tier agent MUST additionally deduplicate by message ID; a best-effort agent's residual duplicate risk is disclosed, not hidden.
- **FR-007**: Dispatch MUST NOT depend on the agent answering within the user's request. BrainBuddy MUST keep the exchange alive in the background for at least the deployment-configured reply window (default 300 seconds; a deployment MUST NOT configure it below 300 seconds) so that an agent which answers only at the end of its work is handled without a fabricated failure, and MUST treat the task returned at the end of that exchange as an authenticated observation. The exchange MUST also carry an absolute deadline — the reply window plus a fixed margin — that BrainBuddy itself enforces on the open request whether the agent is silent or dripping bytes; when it passes, the exchange closes as **Delivery unconfirmed** and the lookup rule of FR-006 applies.
- **FR-008**: Run state MUST come only from BrainBuddy's own authenticated observations of the agent's task. Each observation MUST receive a BrainBuddy-assigned strictly increasing version; an observation older than the current version MUST change nothing. BrainBuddy MUST observe every non-terminal run at a deployment-configured interval, on every reply or cancel acknowledgement, and immediately when a verified push notification arrives. After the reporting window elapses without contact, the observation interval MUST back off — bounded, never more than ten times the configured interval — until the run's identifiers expire; a verified push notification, a reply or cancel acknowledgement, or the user opening the run resets it to the configured interval. Observations and hand-off exchanges MUST run in separate bounded pools so that a slow or unresponsive agent never delays another run's scheduled observation; every outbound request MUST carry an absolute deadline sized to its window plus a margin, after which BrainBuddy closes it — a breached observation is a failed contact, never a fabricated state; one connection MAY hold at most a configured number of exchange workers at once (its further hand-offs stay **Queued**), so one hostile or broken agent cannot exhaust the exchange pool for every owner; a confirmed hand-off still waiting for a free exchange worker MUST be shown as **Queued** with the explanation "Waiting for a free connection slot; nothing has been sent yet" and MUST NOT be shown as **Sent** until its exchange has actually started. A push notification MAY accelerate observation and MUST NOT change state by itself. Push notifications MUST be verified against a per-run token that BrainBuddy registered with the agent; unverified, unknown-run, wrong-owner, malformed or oversized notifications MUST change nothing and MUST NOT create unbounded durable records, as the 007 post-ratification clarification requires. Every rejection class of the push route (unknown run, wrong token, closed run) MUST answer byte-identically — same status, same body, no distinguishing header; the one deliberate exception is the per-run rate-limit answer (429), reachable only for a known, dispatched, non-terminal run, which is accepted as a run-id-gated existence signal because run IDs are unguessable and the token authorises only an observation BrainBuddy would perform anyway.
- **FR-009**: BrainBuddy MUST map agent task states to the 007 projection as follows: submitted → **accepted**; working → **running** with the agent's latest status text as optional progress; input-required → **blocked** with the agent's message as the question; auth-required → **blocked** with the reason "Agent needs additional authentication" and no reply control; completed → **completed** with the result assembled from text artifacts and the final status message; failed → **failed** with the reason; rejected → **failed** with the reason "Rejected by agent"; canceled → **cancelled**; a direct message answer → **completed** with that text. Completed, failed and cancelled are terminal; later non-identical state changes MUST be rejected. Compact and detail surfaces MUST derive labels from this one projection. **Sent**, **Stopped reporting**, reply-pending and cancel-requested overlays apply exactly as 007 FR-008.
- **FR-010**: When the run is blocked and the agent's task is still open, the user MUST be able to send one reply as a follow-up message in the same conversation and task, carrying a stable command ID as its message ID. Duplicate submissions MUST return the same command and cause at most one message. The reply MUST be shown as unconfirmed until the agent acknowledges that message, and the run MUST return to an agent-reported state only after a subsequent observation. The agent MAY acknowledge a reply with a different task ID inside the same conversation (the run's correlation ID); BrainBuddy MUST adopt that task as the run's current task, MUST NOT refuse the reply, MUST append the timeline event **The agent continued this run in a new task** carrying both task IDs, and MUST keep the run's single correlation ID (design states D-03-S27 and M-03-S26). While a reply's exchange is open, scheduled observation of the previous task is suspended, and a terminal report about the previous task that arrives while the reply is unconfirmed or its exchange is open MUST NOT lock the run: it is recorded as a timeline event and the run stays blocked with the reply pending; a successor task returned by the reply supersedes that report; when the reply itself meets a failed or otherwise terminal task with no successor, the run MUST show the agent's own reason and withdraw the reply control. The suspension is bounded: scheduled observation MUST resume once the reply exchange is closed or interrupted, or at the exchange deadline, whichever comes first; a reply that is never acknowledged stays in the timeline as unconfirmed, the run is never left unobserved until its identifiers expire, and the reply control is restored — for a new reply with a new command ID — only after a later observation shows the run blocked again. A reply exchange interrupted by a restart MUST be recovered by lookup only and never resent; when the agent serves no message history, the reply is confirmed by succession evidence — a task in the run's conversation created after the reply command — and otherwise stays unconfirmed. Cancellation MUST send one cancel request with a stable command ID, show **Cancellation requested** until an observation shows the task canceled, and when the agent answers that cancellation is unsupported or the task is not cancelable, say so and keep the last observed state. When the cancel request fails ambiguously (timeout, server error or transport loss), BrainBuddy MUST show it as unconfirmed, keep the cancel control available for a later attempt with the same command ID, and MUST NOT claim that the agent does not support cancellation; only an explicit agent answer may establish that. Cancel requests and push-notification registrations MUST run on a dedicated control pool with a short timeout, never on the exchange pool, so a cancel never waits behind the hand-off exchanges it is meant to end. Because agent cards do not advertise cancellation support, the hand-off review MUST disclose that cancellation depends on the agent and can only be confirmed when requested.
- **FR-011**: BrainBuddy MUST define a single-start extension whose entire contract is: an agent that declares it deduplicates messages by message ID within one conversation and returns the original task on replay. Agents declaring the extension in their card are guaranteed tier; the extension MUST NOT carry any other capability. BrainBuddy MUST publish the extension under a public, stable identifier with a short public specification in the repository documentation, so that any third-party agent can declare it in its card.
- **FR-012**: The bespoke connector envelope, its capability probe and its signed inbound event route MUST be removed. Any pre-existing connection record that cannot be expressed as an A2A connection MUST be marked disconnected with the reason "superseded wire contract" rather than migrated; its runs keep their bounded history.
- **FR-013**: Task detail and compact surfaces MUST show, in addition to everything 007 FR-010 requires, the guarantee tier, the **Agent no longer reports this run** condition when the agent answers that the task does not exist, and the cancellation-unsupported outcome. Web and iOS MUST derive their labels from the same server projection.
- **FR-014**: User-visible copy MUST distinguish BrainBuddy facts from agent reports exactly as 007 FR-011, and MUST additionally use **Best-effort single start**, **Guaranteed single start**, **Cancellation depends on the agent**, **Agent changed**, **Agent no longer reports this run** and **Queued** ("Waiting for a free connection slot; nothing has been sent yet") for the conditions this feature introduces.
- **FR-015**: For a non-terminal run, last authenticated contact is the latest server receipt time of an accepted dispatch, a successful authenticated observation (including one that shows no change) or an acknowledged reply or cancel. **Stopped reporting** applies exactly as 007 FR-013. An observation answering that the task does not exist MUST set the **Agent no longer reports this run** condition, preserve last contact, and stop further reply and cancel controls without claiming failure.
- **FR-016**: Agent content rendering, retention, disconnect, correlation IDs, logs, interruption and offline behavior, and rollout-OFF semantics apply exactly as 007 FR-014 through FR-019; agent-reported result links are shown as inert text the user can copy, never as clickable links, exactly as the shipped 007 relay renders them. Every card-sourced value — the agent's name, version, description, skill names and descriptions, offered authentication-scheme names and interface address — and every connection-test error detail is untrusted agent-supplied text and MUST render inertly on web and iOS: never an anchor or a link target the platform can open, never interpreted as HTML or markdown, never auto-linkified, bounded to the card-summary lengths, exactly as a result link is treated. Agent task IDs, message IDs, the run's identifier fingerprints and the run's observation event rows are coarse metadata under 007 FR-015 and MUST follow its 90-day bound, as MUST audit entries that name an agent card; relayed content and reply drafts follow the 30-day content tier of 007 FR-015; the run's correlation ID is the run ID itself — it is the wire conversation identifier and part of the push callback path — and stays with the run row as coarse metadata until account purge, which BrainBuddy states rather than pretends to erase; the live connection's discovered card summary and its fingerprint are connection configuration, retained for the connection's lifetime and erased on disconnect together with the credential, and are not subject to that 90-day bound; logs MAY additionally carry the agent's protocol version and allowlisted A2A error codes and MUST NOT carry card secrets, the per-run push token, task text or artifacts. Disconnect MUST also stop observation and push registration for the connection's runs. While rollout is OFF, observation of already-dispatched runs, verified push handling, reply and cancel for existing runs, the lookup of a delivery check (never its resend, FR-006), purge and retention MUST continue.
- **FR-017**: BrainBuddy MUST ship deterministic reference conformance checks against two unmodified third-party runtimes: an official a2a-sdk sample agent and the Hermes A2A plugin's inbound server. The Hermes check MUST run in continuous integration against the unmodified plugin code driven by a stub agent handler without a model, and a separate attended live run against a real Hermes installation MUST be recorded as release evidence before rollout; that live run spends provider money and requires explicit human approval, exactly like the existing live verification skill. Neither runtime may require any BrainBuddy-specific code.

### Key Entities

- **Agent Connection**: Owner-scoped saved agent identity: address, discovered card metadata (name, version, description, skills, streaming and push support, authentication requirements, interface address, protocol version), a card fingerprint used to detect drift, the credential scheme and non-readable credential reference, guarantee tier, tested state, last authenticated contact and stale or disconnected status.
- **Execution Run**: Owner-scoped external attempt linked to one Task: stable run ID, message ID, correlation ID (also used as the protocol conversation identifier; it is the run ID), the agent's task ID once known, frozen sent-content manifest, dispatch state, the exchange in flight (start or reply) with its deadline, latest observed state and observation version, last contact, push-registration state, a marker when the agent's result was too large to store, and the conditions this feature adds. It is separate from the Task lifecycle.
- **Observation**: One authenticated retrieval of the agent's task by BrainBuddy: version, observed state, status text, artifacts summary, server receipt time, and whether it was triggered by schedule, by a command acknowledgement or by a verified push notification.
- **Run Command**: Idempotent owner request to start, reply or cancel, with its stable message or command ID and an explicitly unconfirmed or confirmed outcome.
- **Audit Entry**: Minimal owner-visible timeline fact with IDs, coarse state or action, timestamps and safe error metadata, never credentials or relayed content beyond its retention window.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An automated end-to-end hand-off from a Task completes through **Agent reported complete** against two unmodified third-party runtimes, an official a2a-sdk sample agent and the Hermes A2A plugin, with zero BrainBuddy-specific code on the agent side.
- **SC-002**: Three identical confirmation and dispatch replays produce exactly one task at the agent and one Task-linked run for each reference runtime, and the same holds against a reference agent that declares the single-start extension.
- **SC-003**: Every 007 security rejection case (unauthenticated, cross-owner, malformed, oversized, unknown-run, unsafe-destination, stale) plus forged, replayed and wrong-token push notifications and agent-card drift are rejected with zero accepted state changes and zero secret disclosure; a valid push arriving after the run closed is classified as a late push, never as a forged token; and the push route's unknown-run, wrong-token and closed-run rejections are indistinguishable to the caller (same status, same body, no distinguishing header); the per-run rate-limit answer (429) is reachable only for a known, dispatched, non-terminal run and is the one deliberate, run-id-gated existence signal (FR-008).
- **SC-004**: Every required user-visible state — queued, sent, accepted or running, needs-user, agent-reported-complete, failed, cancelled, cancellation-unsupported, stopped-reporting, agent-no-longer-reports-this-run, and the best-effort disclosure — is distinguishable on both the responsive Task detail and compact Task surfaces on web and iOS from one projection, without fabricated progress or Task completion.
- **SC-005**: A user can identify exactly what will be sent, the guarantee tier and the cancellation disclosure, and remove optional supporting items before confirming, on desktop-width and iPhone-width review surfaces.
- **SC-006**: Against an agent that answers only after a delay of up to 300 seconds, the run shows **Sent** and no fabricated failure while waiting, and the true terminal state within one observation interval (at most 60 seconds) after the agent finishes.
- **SC-007**: Retention tests prove relayed content and drafts do not exceed 30 days and are inaccessible on every read as soon as they are due — before the sweep runs; agent task IDs, message IDs, identifier fingerprints and event rows do not exceed 90 days; the run ID, which is the run's correlation ID, is retained with the run row as coarse metadata until account purge and the test asserts exactly that rather than a vacuous erasure; a live connection's card summary and fingerprint survive every sweep and are erased on disconnect together with the credential; a run row the sweep cannot parse is skipped and logged without stalling expiry for any other owner; and account purge removes all owner feature data.
- **SC-008**: Deterministic barrier tests for concurrent duplicate start, reply and cancel submissions — and for concurrent delivery checks: check against check, check against a replayed confirmation, check against restart recovery — prove one durable winner and at most one agent-side action for each command family.
- **SC-009**: A connection test or dispatch failure always shows an actionable category (unreachable, not an A2A agent, unsupported protocol version or interface, unsupported authentication scheme, invalid credentials, private destination, rate limited) and a correlation ID, while automated log checks — including a capture of application and access logging during verified, rejected and failing push notifications — find no secret, stored or transient (the per-run push token included), task text or artifact content.
- **SC-010**: No code path, test or fixture for the bespoke envelope remains, and a pre-existing bespoke connection record is shown as disconnected with the superseded-wire reason rather than as ready.

## Assumptions

- The existing session authentication, owner scoping, correlation-ID envelope, account purge, Admin Portal rollout flag, responsive Task surfaces and the Expo iOS application remain the host product contracts.
- A deployment chooses its observation interval, reply window, test timeout, reporting window and any governed private-network allowance; the UI reports their effects rather than promising a universal interval.
- Only protocol version 1.0.x of A2A is in scope; agents serving other versions are unsupported and later protocol revisions are handled as follow-up features.
- Cloud-hosted agents are in scope only insofar as they accept a bearer token or an API key; an agent that requires OAuth2, mutual TLS or platform-specific signed requests is unsupported until the deferred schemes are delivered.
- No production connection records exist on the bespoke wire (rollout has been OFF since ratification); pre-existing records in non-production data are invalidated, not migrated.
- The official a2a-sdk sample agent serves plain HTTP on a loopback address, so automated end-to-end runs use the existing governed private-destination allowance in the test environment only; production keeps HTTPS and public destinations.
- The Hermes A2A plugin is MIT-licensed and its inbound server can be driven by a stub agent handler without a model, which is how its own test suite exercises it.
- The user owns the agent's hosting, model provider, tools, cost and output quality; BrainBuddy neither hosts nor verifies agents.
- The default observation interval is 60 seconds and the default reply window is 300 seconds; both are deployment-configurable (the reply window never below 300 seconds, FR-007), and SC-006 is measured against those defaults.
- There is no per-owner limit on concurrent non-terminal runs (product-owner decision, 2026-09-03).
- Product vocabulary follows ADR-0006: "supporting items" and "correlation ID" are the user-facing terms; the A2A field names messageId and contextId appear only in technical artifacts and are never returned in client-facing responses.
