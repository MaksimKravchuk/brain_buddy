## Summary

Feature 007 ships a bring-your-own-agent relay whose connector envelope no agent implements. This feature replaces that wire with the Linux Foundation A2A protocol v1.0.x and removes the bespoke envelope, while every wire-independent 007 guarantee (consent manifest, reauthentication, sealed secrets, pinned HTTPS egress, honest projection, retention, purge, rollout-OFF semantics) is kept in place. Technical approach, decided in `research.md` (Decisions A–K):

- A minimal in-house JSON-RPC 2.0 client (`backend/app/modules/agents/a2a/`) built on the existing DNS-pinned egress; `a2a-sdk` is a dev-only dependency for the reference runtime, never a runtime dependency (Decision A).
- A background `AgentObserver` (three separately bounded thread pools — one for the blocking start/reply exchanges, one for observations, one small control pool for cancel and push registration — plus one scheduler thread) that holds the blocking `SendMessage` exchange for up to the reply window under an absolute deadline, observes every non-terminal run on a schedule, is woken by verified push notifications and command acknowledgements through a narrow wake port, recovers interrupted exchanges after a restart from durable run state by lookup only (a never-started exchange settles as **Not sent**; nothing is ever resent from a background thread), and applies every observation through `AgentRelayService.apply_observation`, which owns the run-state rules (Decision B).
- Correlation identifiers: the A2A `contextId` is the run id (shown as *Correlation ID*), the start `messageId` derives from the run's idempotency key, and BrainBuddy looks the run up with `ListTasks(contextId)` before any resend; agents declaring the published single-start extension are the guaranteed tier, all others best-effort with a one-time acknowledgement (Decisions C and the sign-off decisions in spec Clarifications).
- A per-run push token route replaces the bespoke inbound event route; a verified push only triggers an observation (Decision D).
- A pure state-mapping function with BrainBuddy-assigned observation versions and terminal locking (Decision E).
- Deletion of the bespoke wire in backend, web and mobile, with a ledgered migration that marks pre-existing records disconnected (Decision F).
- Two vendored, unmodified reference runtimes (a2a-sdk helloworld sample, Hermes A2A plugin driven by a stub handler) in backend integration tests and the compose Playwright stack, plus an attended live Hermes run as release evidence (Decision G).

## Technical Context

**Language/Version**: Python 3.11 (backend); TypeScript strict on React 18 / Vite (web); TypeScript strict on Expo / React Native (iOS)

**Primary Dependencies**: FastAPI 0.119, Pydantic 2.12, httpx (re-locked from 0.27.2 to 0.28.x inside the existing `>=0.25,<0.29` range because the dev-only `a2a-sdk[http-server]==1.1.2` requires `>=0.28.1`), React Query, Zustand; no protobuf or Google client libraries at runtime

**Storage**: SQLite JSON documents under `backend/data/agents.sqlite3` through `backend/app/modules/agents/repository.py`; new columns and one ledgered migration row, no new table (`data-model.md`)

**Testing**: pytest + FastAPI TestClient with `httpx.MockTransport` and loopback fake agents; Vitest + Testing Library; Jest plus the real-backend mobile integration suite; Playwright against the compose stack with two agent fixture services

**Target Platform**: Fly.io, one always-on `1 cpu / 1 GB` machine for the backend; web via the Fly frontend proxy; iOS via Expo

**Project Type**: web service + web client + mobile client (BrainBuddy modular monolith, ADR-0001)

**Performance Goals**: observation interval 60 s (SC-006: true terminal state within one interval), dispatch request returns within `dispatch_wait_seconds` (5 s) while the exchange continues in the background, exchange held up to `reply_window_seconds + 15 s` (315 s) under `httpx.Timeout(connect=5 s, read=window)` **and** an absolute wall-clock deadline of the same size that `egress.pinned_request` enforces itself while waiting for headers and inside its `iter_raw` loop (`EgressDeadlineExceeded`, stream closed on breach: an exchange breach is **Delivery unconfirmed**, an observation breach a failed contact), so a drip-feeding agent cannot hold a worker past the window; exchanges run in their own bounded pool (`agent_relay.exchange_workers`, default 8, queued exchanges served owner-round-robin, at most `agent_relay.max_exchanges_per_connection` — default 2 — held by one connection at a time, excess exchanges stay `queued`), scheduled observations in a separate bounded pool (`agent_relay.observer_workers`, default 4), and `CancelTask` / `CreateTaskPushNotificationConfig` on a dedicated short-timeout control pool (`agent_relay.control_workers`, default 2), so a long-held exchange can never delay a scheduled observation or a cancel, and SC-006 holds under saturation

**Constraints**: HTTPS-only public destinations with DNS pinning on every card fetch, task call and push registration (007 FR-004); no per-owner cap on concurrent runs (bounded by the two worker pools and API rate limits); 30-day content and 90-day identifier/audit retention, the live connection's card summary for the connection's lifetime (erased on disconnect with the credential); agent-reported result links stay inert text (`egress.interactive_result_link` unchanged); no secrets, card bodies, task text or artifacts in logs — the per-run push token is kept out of BrainBuddy's own logs by two in-process layers, `CorrelationIdMiddleware` logging any push path as `{api_prefix}/a2a/push/{run_id}/[redacted]` and a `uvicorn.access` filter in `backend/app/core/logging.py` that drops lines for that prefix; the callback URL is built from `BRAIN_BUDDY_PUBLIC_BASE_URL`, the backend Fly app's own origin (`fly.backend.toml`, `config.py` `agent_relay.public_base_url`), so agents call the backend app directly and the frontend image's `deploy/nginx/default.conf` never sees the token — the only edge outside BrainBuddy's control is the Fly proxy in front of the backend app (`contracts/push-callback.md`, Redaction and Residual)

**Scale/Scope**: single-user accounts on a multi-tenant service; tens of concurrent non-terminal runs per deployment; two reference runtimes; six designed screens with 129 states (125 at sign-off, the two task-succession states D-03-S27 and M-03-S26 added after review campaign 1, and the two rate-limited connection-test states D-01-S25 and M-01-S22 added after review campaign 2)

**Structure Decision**: the relay stays one module under `backend/app/modules/agents/` (ADR-0001 ownership unchanged); the A2A protocol surface is isolated in the new `a2a/` sub-package so the service keeps orchestrating through a port (`A2AClientPort`) the same way it used `ConnectorPort`; the observer is a sibling module because it owns threads and scheduling, not business rules. The ownership seam is explicit: `observer.py` owns scheduling, wake draining and network I/O only and calls `AgentRelayService.apply_observation(run_id, owner_id, observation, based_on)`, which owns the `run_version` compare-and-set, terminal locking, timeline append and `agent_task_missing_at`; the service receives the exchange executor as a constructor port (a `Callable`/executor protocol), so `container.py` wires `A2AClient` → `AgentRelayService(client, exchange_executor)` → `AgentObserver(service, client)` with no construction cycle; the one edge that points the other way — a verified push or a command acknowledgement waking the observer at once (FR-008, AC-021) — is a narrow wake port (`Callable[[str], None]`, taking the run id) that the observer hands to the service after construction and that `api/dependencies.py` exposes to the push route, so the ownership seam is described in both directions and "no construction cycle" stays true. Background threads never insert a *run* row; event, succession and audit rows are appended only for a run that still exists and is not purged. Vendored third-party runtimes live under `backend/vendor/` so ruff, black, mypy and coverage never touch them — `make lint-backend` and CI scope those tools to `app`/`tests`, and the pre-commit hooks are kept out too by a global `exclude: ^backend/vendor/` in `.pre-commit-config.yaml` plus ruff `extend-exclude = ["vendor"]` in `backend/pyproject.toml` (today neither file excludes anything) — and their provenance is asserted by a test. Web and iOS keep the existing feature folders; only the signing-secret surfaces disappear. The design mockups use `<span class="btn">` only for static rendering; the implementation renders real `<button>` (web) and `Pressable` (mobile) controls for every action so the tab order and Enter/Space activation `design.md` describes hold.

1. **Discovery, test and tier** (FR-001, FR-002, FR-003, FR-004, FR-011, FR-016; D-01-S08..S25, M-01-S08..S22). `a2a/card.py` fetches `{origin}/.well-known/agent-card.json` through `pinned_request`, parses both the v1.0 card and the legacy Hermes shape, selects the first JSON-RPC interface with protocol version 1.0.x, validates its host separately under 007 FR-004, maps offered security schemes to `bearer`/`api_key`/unsupported (a card whose API-key header name collides with the reserved set in `headers.py` yields `a2a_auth_scheme_unsupported`), detects the FR-011 extension URI for the tier, and computes the drift fingerprint. `service.test_connection` returns the six categories — ready, invalid credentials, unreachable, unsupported (four sentences: not an A2A agent, protocol version, no supported interface, authentication scheme), private destination, rate limited (HTTP 429 / `-32051` ⇒ `last_test_error_code=a2a_rate_limited`, `status` stays `untested` until a later successful test, retry allowed after `retry_after_seconds`; D-01-S25 / M-01-S22, AC-037) — by an authenticated `ListTasks(pageSize=1)`, with `last_test_error_detail` carrying the closed per-code shapes of `data-model.md` §1; every card-sourced value (`name`, `version`, `description`, `skills[].name/description`, `auth_schemes_offered[].name`, `interface_url`) and every `last_test_error_detail` value is rendered as inert plain text on both clients — never an anchor or `Linking` target, never HTML/markdown-interpreted, never auto-linkified (FR-016, AC-031); the disclosure copy and the `tier_disclosure_url` come from the projection; `agent_card_changed` puts the connection back to untested (D-01-S20 / M-01-S18), resets `scope_verified_at` and clears `best_effort_acknowledged_at`, as do an address change, an auth-scheme change and a credential rotation (FR-003).
2. **Hand-off review and dispatch** (FR-005, FR-006, FR-007; D-02-S01..S15 including the acknowledgement states D-02-S13..S15 and the extension link on D-02-S02, M-02-S01..S14 including M-02-S12..S14; D-03-S04 / M-03-S03 for the pending exchange including their **Queued** variant, D-03-S05 / M-03-S04 for **Delivery unconfirmed** with its **Check again** affordance, D-03-S03 / M-03-S02 for **Not sent** including the restarted-before-send variant). The manifest keeps the 007 token discipline and adds `message_id`, `correlation_id`, the tier and cancellation disclosures, `acknowledgement_required` and the `push_callback` disclosure (registered flag, token-masked URL preview, server-owned sentence; the callback origin is part of the token); a best-effort connection's first confirmation must carry `acknowledge_duplicate_risk: true` (AC-026). `dispatch_run` reserves ids, marks the exchange `queued` with `exchange_kind=start`, submits `SendMessage` to the exchange pool — at most `max_exchanges_per_connection` workers per connection, each request under the absolute deadline — (the wire conversation identifier = run id, message id = `{run_id}:start`, metadata with Task and run ids, inline push config when the card supports push, and for a guaranteed-tier agent the `A2A-Extensions` header plus `message.extensions` on this first send and on every replay), waits `dispatch_wait_seconds`, probes `ListTasks` by correlation ID only when the exchange has actually started and is still open (a still-queued exchange skips the probe, since nothing has gone out, and returns the **Queued** projection — `primary_state_label: "Queued"`, explained as "Waiting for a free connection slot; nothing has been sent yet" — which becomes **Sent** only once the worker starts the exchange), and returns the honest dispatch state. Replays and **Check again** (`POST /agent-runs/{id}/check-delivery`) never resend without the correlation-ID lookup. The resend branch — never the lookup — is refused with `connection_not_ready` / `agent_card_changed` / `run_content_expired` unless the connection is `ready`, not stale, not **Agent changed**, its `scope_verified_at` is not younger than the run's `dispatched_at` (no address, auth-scheme, credential or card-drift reset since dispatch) and the frozen manifest is still present; it passes `requires_dispatch_reauthentication` exactly like a dispatch (the lookup never does), goes to the run's pinned `interface_url` after re-checking `card_fingerprint`, and is serialised by a durable compare-and-set of `interrupted|delivery_unconfirmed → open` on `run_version` under the process-wide command lock before any I/O, so a second contender re-reads, sees the exchange open and returns the winner without touching the network (SC-008). While rollout is OFF the lookup runs and the resend is refused (AC-036). Every adopted task must carry the run's correlation ID; a connection recorded as `context_id_honoured=false` is never resent — not by any thread and not by **Check again** (FR-006, AC-030). Restart recovery settles a `queued` exchange (`exchange_started_at is None`) as `not_sent` with `dispatch_error_code=restarted_before_send` and re-offers the hand-off (the D-03-S03 / M-03-S02 variant text "BrainBuddy restarted before this hand-off was sent. Nothing left BrainBuddy."), flips an `open` one to `interrupted` for lookup-only resolution, and never resends (AC-032).
3. **Observation and run surfaces** (FR-008, FR-009, FR-010, FR-013, FR-014, FR-015; D-03-S03..S27 including the new D-03-S27 **Task succession** row, M-03-S02..S26 including the new M-03-S26). `observer.py` owns scheduling, wake draining and network I/O only: it selects due runs, coalesces in-flight runs and — when a host is unreachable — one probe per connection per interval fanned out to that connection's runs, issues `GetTask {id, historyLength: 0}` from the observation pool under the absolute deadline (a breach is a failed contact; history is fetched only when the observed state needs text; an over-cap task read falls back to `ListTasks` by correlation ID with `includeArtifacts: false` so the state is still observed and the result is marked too large), backs the interval off after the reporting window (bounded, at most 10× `observation_interval_seconds`) and resets it on a push, reply, cancel or the user opening the run, recovers interrupted exchanges at startup per `exchange_kind` (a start by lookup, a reply by lookup plus succession evidence — never a resend), and then calls `AgentRelayService.apply_observation(run_id, owner_id, observation, based_on)`. That service method owns the rules: it re-reads the run under the repository's process-wide command lock after I/O and aborts when the run is missing, disconnected, terminal or identifiers-expired; applies `mapping.project_observation` with compare-and-set on `run_version` through a conditional `UPDATE … WHERE owner_id=? AND id=? AND run_version=?` (no *run* insert path from background threads; event, succession and audit rows are appended only for a run that still exists and is not purged); appends timeline events only on change; writes no `blocked_reason`, `artifacts_summary`, status text or other agent text into a run whose content tier has expired — and `domain.project_run_for_access`, the read-time projection every read path applies (`service.py` reads, `repository.py` export), is extended to null `blocked_reason`, `artifacts_summary`, `result_availability` and the agent status text beside the 007 fields, so due content is inaccessible before the sweep (SC-007); locks terminal states; sets `agent_task_missing_at` on `TaskNotFound`. Network I/O never happens inside that lock — the 007 dispatch path in `service.py` (I/O at 1527, re-read under `command_lock` at 1529–1530) is the pattern. Reply sends a follow-up message with the command id as message id, carrying the same `taskPushNotificationConfig` when the card supports push, and adopts a succeeding task when Hermes returns a new one in the same conversation (timeline row **The agent continued this run in a new task**, D-03-S27 / M-03-S26); while the reply exchange is open, scheduled observation of the predecessor task is suspended — bounded: it resumes when the exchange is `closed` or `interrupted` or at `exchange_deadline_at`, whichever comes first — a terminal predecessor report that arrives while the reply is unconfirmed or its exchange is open is recorded as a timeline row without locking the run, the succession row supersedes it, a reply that meets a failed task with no successor shows the agent's own reason and withdraws the reply control, and a reply that is never acknowledged stays unconfirmed in the timeline with the reply control restored — for a new command id — only after a later observation shows the run blocked again (FR-010 precedence, AC-033). Cancel and `CreateTaskPushNotificationConfig` run on the dedicated control pool (`agent_relay.control_workers`, short timeout), never behind start/reply exchanges (AC-035). Cancel maps `-32002` to `not_cancelable`, `-32004` and `-32601` to `unsupported`, and `-32603`, HTTP 5xx, timeouts and transport loss to `unconfirmed` — the cancel control stays available and a later attempt reuses the same command id — without inventing a state. Agent-reported result links stay inert text the user can copy: the 007 helper `egress.interactive_result_link` is kept unchanged (it returns `False` for every link, with its documented click-time reason), so `result_link_interactive` is never `true` and D-03-S11 / M-03-S10 render the link as copyable text (product owner, 2026-09-04). The single projection feeds web and iOS labels verbatim.
4. **Push receipt** (FR-008, FR-016; push adds no distinct user-visible state — it is the ordinary observation row of D-03-S05/S06 and M-03-S04/S05 arriving sooner, with `events[].trigger: "push"` visible in the row's detail). `POST /api/a2a/push/{run_id}/{token}` in the order fixed by `contracts/push-callback.md`: body size limit → a bounded process-wide limiter before any database read → resolve the run (unknown → opaque `403`, no durable row, no limiter key) → constant-time token fingerprint comparison (the fingerprint is kept until identifier expiry rather than cleared at terminal, so a valid push arriving after the run closed — the agent's terminal push racing BrainBuddy's own terminal observation — passes this step and is classified `push_after_close` at the next one, never `push_token_rejected`) → the bounded per-run limiter (keys only for known, dispatched, non-terminal runs, a maximum key count, eviction when the run goes terminal or is disconnected — a bounded variant of `InMemoryRateLimiter`, which never evicts keys) → schedule an immediate observation, `204`; a wrong token on a known run → `403` with one bounded `push_token_rejected` audit row per owner/connection/UTC day; rejections of unknown ids are counted only in a process-wide fixed-size counter; the unknown-run, wrong-token and closed-run rejections are byte-identical to the caller (same status, same body, no distinguishing header or `Retry-After`), so the only run-existence signal is the per-run `429`, a deliberate, run-id-gated deviation from the repository's 404-for-wrong-owner convention recorded in one line in `docs/auth.md`; the body is never parsed for state. Redaction: `CorrelationIdMiddleware` logs any path under `{api_prefix}/a2a/push/` as `{api_prefix}/a2a/push/{run_id}/[redacted]` on both its success line and its `api_request_failed` exception line through a pure sanitiser applied before every log call that never raises; `backend/app/core/logging.py` adds a filter that rewrites or drops `uvicorn.access` lines whose path starts with that prefix. Those are the two in-process edges: the callback URL is built from `BRAIN_BUDDY_PUBLIC_BASE_URL`, the backend app's own origin, so agents call the backend Fly app directly, the frontend image's nginx never sees the request and needs no change, and the Fly proxy in front of the backend app is the disclosed residual (`contracts/push-callback.md`). The SC-009 log-scan test `test_push_token_never_appears_in_logs` (`test_agent_relay_api.py`) captures application and `uvicorn.access` logging — the two edges it covers — during a verified push, a rejected push and a failing push (exception path) and asserts the issued token string appears in none of them; `test_push_rejections_are_indistinguishable_to_the_caller` and `test_valid_push_after_terminal_is_classified_push_after_close` are the SC-003 companions.

## Risks and rollback

- **Duplicate tasks on best-effort agents** are disclosed and acknowledged, never hidden; the resend path is exercised against a fake agent that answers `ListTasks` empty (SC-002).
- **Restart during an exchange**: the run row records `exchange_state=queued|open` and `exchange_kind=start|reply`. A `queued` exchange (`exchange_started_at is None`) has provably not been sent: recovery settles it as `not_sent` with `restarted_before_send` and re-offers the hand-off. An `open` exchange is flipped to `interrupted` and the next observation resolves it by correlation-ID lookup only — adopt if found, otherwise the run stays **Delivery unconfirmed** for the user's **Check again**; an interrupted reply is confirmed only by succession evidence. Recovery never resends; nothing is lost because reservation and dispatch state are durable before I/O (Decision B).
- **Third-party churn**: the client accepts protocol versions `1.0.x` only and tolerates unknown card fields; Hermes' legacy card shape is covered by a fixture pinned to a commit.
- **Rollback boundary**: redeploy the previous image with the flag OFF. The stored connection payload stays parseable by the 007 image: storage keeps the `endpoint_url` key (the API exposes it as `agent_address`), `auth_header_name` is stored only for API-key connections and never holds a reserved name (a bearer connection omits the key, so the 007 model's default applies; the `Authorization` header is derived from `auth_scheme` at request time), and `StorageBaseModel` ignores unknown fields (`extra="ignore"`, `backend/app/schemas/common.py`), so with the flag OFF the previous image keeps connection reads, export and purge working on 014 rows — asserted by a test in which a frozen copy of the 007 `AgentConnectionDocument` validates a 014 payload. Purge is SQL-only (`delete_all_for_owner`) and unaffected for every row. Run rows were the limit of the boundary and are handled explicitly. The 007 `AgentRunManifest` requires the bespoke `reporting` and `reporting_instructions` keys, `AgentRepository._model` raises `RepositoryError` on any row that fails validation, and the 007 image's `expire_due_content` validates every due run row through `_model` inside one `BEGIN IMMEDIATE` transaction *before* nulling anything (`repository.py` 990–1104): without mitigation the first 014 run to reach its 30-day boundary would make the 007 image's sweep raise and roll back on every pass — no content expiring for any owner, `purge_expired_audit`, `purge_expired_event_ids` and `purge_all_expired_idempotency` skipped after the raise (`service.py` `run_retention_sweep`), the exception swallowed silently every interval by `main.py` — and `export_owner_data`, which also runs `_model` over every run row, would fail the always-on GDPR export for any owner holding a 014 run. Mitigation, verified: (a) every 014 manifest also writes `reporting` and `reporting_instructions` with inert placeholder values in the frozen 007 shape, so a 014 run row validates under the 007 image — asserted by `test_frozen_007_run_event_and_command_documents_validate_014_payloads` beside the connection-document test; (b) the 014 `expire_due_content` skips and logs (correlation id, no content) an unparseable row instead of aborting the transaction, so the same failure class cannot recur in the other direction; (c) `docs/external-agent-relay-release.md` states these consequences and this mitigation. With the flag OFF the 007 image therefore keeps reads, projection, export, expiry and purge working on 014 rows; what it cannot do is observe a 014 run — the observer does not exist there and the bespoke event route has no secret — so runs dispatched under 014 freeze at their last observed state until the 014 image returns, and rollback after the first 014 dispatch remains a runbook step, not a silent redeploy. The migration is one-way — migrated bespoke credentials are destroyed irreversibly — which is acceptable because the bespoke wire has no consumers; the assumption that no production records exist is verified rather than trusted by the runbook's pre-deploy count of bespoke rows, and every rewritten row is counted and audited (`wire_superseded`); encryption keys for stored credentials must be kept as in 007.
- **Landing**: ASK class, risk `high`; the review campaign records the human sign-off; dual review on the exact SHA; `make verify-all` green; rollout stays OFF until the live Hermes evidence is attached and, for every user, until the refreshed iOS build is the only distributed build (release-runbook gate).
