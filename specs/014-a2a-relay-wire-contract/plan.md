## Summary

Feature 007 ships a bring-your-own-agent relay whose connector envelope no agent implements. This feature replaces that wire with the Linux Foundation A2A protocol v1.0.x and removes the bespoke envelope, while every wire-independent 007 guarantee (consent manifest, reauthentication, sealed secrets, pinned HTTPS egress, honest projection, retention, purge, rollout-OFF semantics) is kept in place. Technical approach, decided in `research.md` (Decisions A–K):

- A minimal in-house JSON-RPC 2.0 client (`backend/app/modules/agents/a2a/`) built on the existing DNS-pinned egress; `a2a-sdk` is a dev-only dependency for the reference runtime, never a runtime dependency (Decision A).
- A background `AgentObserver` (two separately bounded thread pools — one for blocking exchanges, one for observations — plus one scheduler thread) that holds the blocking `SendMessage` exchange for up to the reply window, observes every non-terminal run on a schedule, is woken by verified push notifications and command acknowledgements, recovers interrupted exchanges after a restart from durable run state, and applies every observation through `AgentRelayService.apply_observation`, which owns the run-state rules (Decision B).
- Correlation identifiers: the A2A `contextId` is the run id (shown as *Correlation ID*), the start `messageId` derives from the run's idempotency key, and BrainBuddy looks the run up with `ListTasks(contextId)` before any resend; agents declaring the published single-start extension are the guaranteed tier, all others best-effort with a one-time acknowledgement (Decisions C and the sign-off decisions in spec Clarifications).
- A per-run push token route replaces the bespoke inbound event route; a verified push only triggers an observation (Decision D).
- A pure state-mapping function with BrainBuddy-assigned observation versions and terminal locking (Decision E).
- Deletion of the bespoke wire in backend, web and mobile, with a ledgered migration that marks pre-existing records disconnected (Decision F).
- Two vendored, unmodified reference runtimes (a2a-sdk helloworld sample, Hermes A2A plugin driven by a stub handler) in backend integration tests and the compose Playwright stack, plus an attended live Hermes run as release evidence (Decision G).

## Technical Context

**Language/Version**: Python 3.11 (backend); TypeScript strict on React 18 / Vite (web); TypeScript strict on Expo / React Native (iOS)

**Primary Dependencies**: FastAPI 0.119, Pydantic 2.12, httpx (re-locked from 0.27.2 to 0.28.x inside the existing `>=0.25,<0.29` range because the dev-only `a2a-sdk[http-server]==1.1.2` requires `>=0.28.1`), React Query, Zustand; no protobuf or Google client libraries at runtime

**Storage**: SQLite JSON documents under `backend/data/agents.sqlite3` through `backend/app/modules/agents/repository.py`; new columns and one ledgered migration row, no new table (`data-model.md`)

**Testing**: pytest + FastAPI TestClient with `httpx.MockTransport` and loopback fake agents; Vitest + Testing Library; Jest plus the real-backend mobile integration suite; Playwright against the compose stack with two agent fixture services

**Target Platform**: Fly.io, one always-on `1 cpu / 1 GB` machine for the backend; web via the Fly frontend proxy; iOS via Expo

**Project Type**: web service + web client + mobile client (BrainBuddy modular monolith, ADR-0001)

**Performance Goals**: observation interval 60 s (SC-006: true terminal state within one interval), dispatch request returns within `dispatch_wait_seconds` (5 s) while the exchange continues in the background, exchange held up to `reply_window_seconds + 15 s` (315 s) under `httpx.Timeout(connect=5 s, read=window)`; exchanges run in their own bounded pool (`agent_relay.exchange_workers`, default 8, queued exchanges served owner-round-robin) and scheduled observations in a separate bounded pool (`agent_relay.observer_workers`, default 4), so a long-held exchange can never delay a scheduled observation and SC-006 holds under saturation

**Constraints**: HTTPS-only public destinations with DNS pinning on every card fetch, task call and push registration (007 FR-004); no per-owner cap on concurrent runs (bounded by the two worker pools and API rate limits); 30-day content and 90-day identifier/audit retention, the live connection's card summary for the connection's lifetime (erased on disconnect with the credential); agent-reported result links stay inert text (`egress.interactive_result_link` unchanged); no secrets, card bodies, task text or artifacts in logs — the per-run push token is kept out of them by `CorrelationIdMiddleware` logging any push path as `{api_prefix}/a2a/push/{run_id}/[redacted]`, a `uvicorn.access` filter in `backend/app/core/logging.py` that drops lines for that prefix, and `access_log off` for `location /api/a2a/push/` in `deploy/nginx/default.conf` (`contracts/push-callback.md`, Redaction)

**Scale/Scope**: single-user accounts on a multi-tenant service; tens of concurrent non-terminal runs per deployment; two reference runtimes; six designed screens with 127 states (125 at sign-off plus the two task-succession states D-03-S27 and M-03-S26 added after review campaign 1)

**Structure Decision**: the relay stays one module under `backend/app/modules/agents/` (ADR-0001 ownership unchanged); the A2A protocol surface is isolated in the new `a2a/` sub-package so the service keeps orchestrating through a port (`A2AClientPort`) the same way it used `ConnectorPort`; the observer is a sibling module because it owns threads and scheduling, not business rules. The ownership seam is explicit: `observer.py` owns scheduling, wake draining and network I/O only and calls `AgentRelayService.apply_observation(run_id, owner_id, observation, based_on)`, which owns the `run_version` compare-and-set, terminal locking, timeline append and `agent_task_missing_at`; the service receives the exchange executor as a constructor port (a `Callable`/executor protocol), so `container.py` wires `A2AClient` → `AgentRelayService(client, exchange_executor)` → `AgentObserver(service, client)` with no cycle. Vendored third-party runtimes live under `backend/vendor/` so ruff, black, mypy and coverage never touch them — `make lint-backend` and CI scope those tools to `app`/`tests`, and the pre-commit hooks are kept out too by a global `exclude: ^backend/vendor/` in `.pre-commit-config.yaml` plus ruff `extend-exclude = ["vendor"]` in `backend/pyproject.toml` (today neither file excludes anything) — and their provenance is asserted by a test. Web and iOS keep the existing feature folders; only the signing-secret surfaces disappear. The design mockups use `<span class="btn">` only for static rendering; the implementation renders real `<button>` (web) and `Pressable` (mobile) controls for every action so the tab order and Enter/Space activation `design.md` describes hold.

## Implementation sections (design citations)

Each section names the spec requirements it realizes and the `design.md` state ids the acceptance auditor traces.

1. **Discovery, test and tier** (FR-001, FR-002, FR-003, FR-004, FR-011; D-01-S08..S24, M-01-S08..S21). `a2a/card.py` fetches `{origin}/.well-known/agent-card.json` through `pinned_request`, parses both the v1.0 card and the legacy Hermes shape, selects the first JSON-RPC interface with protocol version 1.0.x, validates its host separately under 007 FR-004, maps offered security schemes to `bearer`/`api_key`/unsupported (a card whose API-key header name collides with the reserved set in `headers.py` yields `a2a_auth_scheme_unsupported`), detects the FR-011 extension URI for the tier, and computes the drift fingerprint. `service.test_connection` returns the six categories — ready, invalid credentials, unreachable, unsupported (four sentences: not an A2A agent, protocol version, no supported interface, authentication scheme), private destination, rate limited — by an authenticated `ListTasks(pageSize=1)`, with `last_test_error_detail` carrying the closed per-code shapes of `data-model.md` §1; the disclosure copy and the `tier_disclosure_url` come from the projection; `agent_card_changed` puts the connection back to untested (D-01-S20 / M-01-S18), resets `scope_verified_at` and clears `best_effort_acknowledged_at`, as do an address change, an auth-scheme change and a credential rotation (FR-003).
2. **Hand-off review and dispatch** (FR-005, FR-006, FR-007; D-02-S01..S15 including the acknowledgement states D-02-S13..S15 and the extension link on D-02-S02, M-02-S01..S14 including M-02-S12..S14; D-03-S04 / M-03-S03 for the pending exchange including their **Queued** variant, D-03-S05 / M-03-S04 for **Delivery unconfirmed** with its **Check again** affordance). The manifest keeps the 007 token discipline and adds `message_id`, `correlation_id`, the tier and cancellation disclosures, `acknowledgement_required` and the `push_callback` disclosure (registered flag, token-masked URL preview, server-owned sentence; the callback origin is part of the token); a best-effort connection's first confirmation must carry `acknowledge_duplicate_risk: true` (AC-026). `dispatch_run` reserves ids, marks the exchange `queued`, submits `SendMessage` to the exchange pool (the wire conversation identifier = run id, message id = `{run_id}:start`, metadata with Task and run ids, inline push config when the card supports push, and for a guaranteed-tier agent the `A2A-Extensions` header plus `message.extensions` on this first send and on every replay), waits `dispatch_wait_seconds`, probes `ListTasks` by correlation ID only when the exchange has actually started and is still open (a still-queued exchange skips the probe, since nothing has gone out, and returns the **Queued** projection — `primary_state_label: "Queued"`, explained as "Waiting for a free connection slot; nothing has been sent yet" — which becomes **Sent** only once the worker starts the exchange), and returns the honest dispatch state. Replays and **Check again** (`POST /agent-runs/{id}/check-delivery`) never resend without the correlation-ID lookup, every adopted task must carry the run's correlation ID, and a connection recorded as `context_id_honoured=false` is never auto-resent (FR-006).
3. **Observation and run surfaces** (FR-008, FR-009, FR-010, FR-013, FR-014, FR-015; D-03-S03..S27 including the new D-03-S27 **Task succession** row, M-03-S02..S26 including the new M-03-S26). `observer.py` owns scheduling, wake draining and network I/O only: it selects due runs, coalesces in-flight runs and — when a host is unreachable — one probe per connection per interval fanned out to that connection's runs, issues `GetTask {id, historyLength: 0}` from the observation pool (history is fetched only when the observed state needs text; an over-cap task read falls back to `ListTasks` by correlation ID with `includeArtifacts: false` so the state is still observed and the result is marked too large), backs the interval off after the reporting window (bounded, at most 10× `observation_interval_seconds`) and resets it on a push, reply, cancel or the user opening the run, recovers interrupted exchanges at startup, and then calls `AgentRelayService.apply_observation(run_id, owner_id, observation, based_on)`. That service method owns the rules: it re-reads the run under the repository's process-wide command lock after I/O and aborts when the run is missing, disconnected, terminal or identifiers-expired; applies `mapping.project_observation` with compare-and-set on `run_version` through a conditional `UPDATE … WHERE owner_id=? AND id=? AND run_version=?` (no insert path from background threads; no event, command or audit row for a missing run); appends timeline events only on change; writes no `blocked_reason`, `artifacts_summary`, status text or other agent text into a run whose content tier has expired; locks terminal states; sets `agent_task_missing_at` on `TaskNotFound`. Network I/O never happens inside that lock — the 007 dispatch path in `service.py` (I/O at 1527, re-read under `command_lock` at 1529–1530) is the pattern. Reply sends a follow-up message with the command id as message id, carrying the same `taskPushNotificationConfig` when the card supports push, and adopts a succeeding task when Hermes returns a new one in the same conversation (timeline row **The agent continued this run in a new task**, D-03-S27 / M-03-S26); while a reply is unconfirmed or its exchange is open, scheduled observation of the predecessor task is suspended and a terminal predecessor report is recorded as a timeline row without locking the run, the succession row supersedes it, and a reply that meets a failed task with no successor shows the agent's own reason and withdraws the reply control (FR-010 precedence). Cancel maps `-32002` to `not_cancelable`, `-32004` and `-32601` to `unsupported`, and `-32603`, HTTP 5xx, timeouts and transport loss to `unconfirmed` — the cancel control stays available and a later attempt reuses the same command id — without inventing a state. ## Risks and rollback

- **Duplicate tasks on best-effort agents** are disclosed and acknowledged, never hidden; the resend path is exercised against a fake agent that answers `ListTasks` empty (SC-002).
- **Restart during an exchange**: the run row records `exchange_state=queued|open`; recovery marks it interrupted and the next observation adopts or resends by correlation-ID lookup; nothing is lost because reservation and dispatch state are durable before I/O.
- **Third-party churn**: the client accepts protocol versions `1.0.x` only and tolerates unknown card fields; Hermes' legacy card shape is covered by a fixture pinned to a commit.
- **Rollback boundary**: redeploy the previous image with the flag OFF. The stored connection payload stays parseable by the 007 image: storage keeps the `endpoint_url` key (the API exposes it as `agent_address`), `auth_header_name` is stored only for API-key connections and never holds a reserved name (a bearer connection omits the key, so the 007 model's default applies; the `Authorization` header is derived from `auth_scheme` at request time), and `StorageBaseModel` ignores unknown fields (`extra="ignore"`, `backend/app/schemas/common.py`), so with the flag OFF the previous image keeps connection reads, export and purge working on 014 rows — asserted by a test in which a frozen copy of the 007 `AgentConnectionDocument` validates a 014 payload. Purge is SQL-only (`delete_all_for_owner`) and unaffected for every row. The limit of the boundary is run rows: the 007 `AgentRunManifest` requires the bespoke `reporting` and `reporting_instructions` keys that 014 removes, and `AgentRepository._model` raises on any row that fails validation, so a run dispatched under 014 is unreadable and unexportable by the 007 image until `expire_due_content` nulls its manifest; rollback after the first 014 dispatch is therefore a runbook step in `docs/external-agent-relay-release.md`, not a silent redeploy. The migration is one-way — migrated bespoke credentials are destroyed irreversibly — which is acceptable because no production records exist and the bespoke wire has no consumers; encryption keys for stored credentials must be kept as in 007.
- **Landing**: ASK class, risk `high`; the review campaign records the human sign-off; dual review on the exact SHA; `make verify-all` green; rollout stays OFF until the live Hermes evidence is attached.
