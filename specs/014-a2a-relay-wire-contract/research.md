## Decisions

### A. A2A client strategy

- **Decision**: In-house minimal JSON-RPC 2.0 client in a new package `backend/app/modules/agents/a2a/` (`card.py`, `client.py`, `types.py`, `mapping.py`) built on the existing `validate_destination` + `pinned_request` (`egress.py`). **a2a-sdk is not a runtime dependency.** `a2a-sdk[http-server]==1.1.2` is added only to the `dev` extra in `backend/pyproject.toml` because the helloworld reference runtime (Decision G) needs it in the test interpreter.
- **Rationale**: (1) FR-004 pinning: the SDK transport builds `POST <interface url>` on an `httpx.AsyncClient` and the card resolver does `httpx_client.get(url)` (F8); pinning would need a custom `httpx.AsyncBaseTransport` that rewrites the URL host, injects `sni_hostname`, refuses redirects and caps bodies — replicating `pinned_request` inside an async stack the synchronous services and observer threads would have to drive through private event loops. (2) Error fidelity: the SDK collapses 401/403/429/5xx into `A2AClientError` text (F8), while FR-002/SC-009 need distinct categories. (3) Leniency: Hermes serves a legacy-shaped card (F5) that the SDK's `parse_agent_card` tolerates only through compat shims; our parser ignores unknown fields and accepts both shapes explicitly. (4) Weight: protobuf + google-api-core + json-rpc enter `pip-audit` (`ci.yml` "Audit Python dependencies") for six methods we can express in ~300 lines of strict, bounded Pydantic models (`StrictBaseModel`, `app/schemas/common.py`). (5) mypy `strict` (`pyproject.toml` 97–100): generated `a2a_pb2` types are opaque `Message` objects; our models are typed.
- **Pin consequences**: `httpx>=0.25,<0.29` admits the SDK's `httpx>=0.28.1`; adding the dev extra re-resolves `uv.lock` from 0.27.2 to 0.28.x for **all** environments (one lock). The re-lock is repo-wide, so the compatibility check is scoped deliberately over every production httpx call site — six once `connector.py` is deleted: `app/modules/agents/egress.py` (`httpx.Client(timeout, follow_redirects)`, `client.stream(..., extensions=)`, `response.iter_raw()`), `app/ai/title_completion.py`, `app/ai/providers/openai_provider.py`, and the three voice adapters `app/workflows/voice_brain_dump/adapters/deepgram_stt.py`, `openai_stt.py` (multipart `data=` + `files=`; its `_form_fields` returns `dict[str, str]`, still valid beside `files=` in 0.28) and `reconciler.py` — every call they make is present unchanged in 0.28; `httpx.MockTransport` (tests) and FastAPI `TestClient` are unaffected. The re-lock validation is the full backend suite, which exercises each of those six modules through `MockTransport`. Task: re-lock and run the full backend suite once before any feature work.
- **Alternatives**: full SDK client with custom transport (rejected: async/pinning/error-fidelity above); `a2a.types` only for validation (rejected: protobuf `ParseDict` is strict, so Hermes' extra `stateTransitionHistory`/`url` fields fail without the SDK's compat layer, and it still costs the protobuf stack for no runtime benefit).

### B. Background observer

- **Decision**: New `backend/app/modules/agents/observer.py` — `AgentObserver` owning **three separately bounded executors**: an exchange pool (`ThreadPoolExecutor(max_workers=agent_relay.exchange_workers, default 8)`) for the blocking `SendMessage` exchanges (start and reply) only, an observation pool (`ThreadPoolExecutor(max_workers=agent_relay.observer_workers, default 4)`) for `GetTask`/`ListTasks` observations, and a dedicated control pool (`ThreadPoolExecutor(max_workers=agent_relay.control_workers, default 2)`, short timeout) for `CancelTask` and `CreateTaskPushNotificationConfig` — never shared with start/reply exchanges, because with Hermes `CancelTask` is what resolves a blocked `SendMessage` (F5), and a cancel queued behind the very exchanges it is meant to end would wait up to 315 s while the UI could not tell pool saturation from agent behaviour (AC-029, D-03-S14) — plus one scheduler thread (`agent-observer`). Because the pools are separate, a long-held exchange can never delay a scheduled observation or a cancel, so SC-006 holds under saturation even with eight 315 s exchanges in flight. One connection may hold at most `agent_relay.max_exchanges_per_connection` (default 2) exchange workers at a time; its further exchanges stay `queued`, so one hostile or broken agent cannot exhaust the shared pool for every owner. The scheduler every `observation_interval_seconds` (default 60) selects every dispatched, non-terminal, non-disconnected, task-known-or-exchange-open run across all owners (repository query with `next_observation_at <= now`), submits one observation per run to the observation pool (coalesced by an in-process `set` of in-flight run ids; when a host is unreachable, coalesced further to one probe per connection per interval whose result is fanned out to that connection's runs), and drains a wake queue fed through a narrow wake port (`Callable[[str], None]`, taking the run id) that the observer hands to the service after construction and that `api/dependencies.py` exposes to the push route — the only edge pointing from the API/service side into the observer, so the construction order below stays acyclic while AC-021's "immediately" is met without waiting for the next scheduler pass (`observation_trigger_pending` remains the durable fallback). Queued exchanges are scheduled owner-round-robin, so one owner's slow agents cannot starve another owner's hand-offs. Correctness never depends on memory: the run row carries `exchange_state (none|queued|open|closed|interrupted)`, `exchange_kind (start|reply)`, `exchange_started_at`, `exchange_deadline_at`, `next_observation_at`; at startup `recover_interrupted_exchanges()` (no thread survives a restart) treats the two live states differently because the row can already tell them apart: a `queued` exchange (`exchange_started_at is None`) has provably never been sent, so it is settled as `dispatch_state=not_sent`, `dispatch_error_code=restarted_before_send`, and the hand-off is re-offered (D-03-S03 / M-03-S02 variant text "BrainBuddy restarted before this hand-off was sent. Nothing left BrainBuddy."; the next confirmation reuses the same run id and message id) — it is never labelled **Delivery unconfirmed**; an `open` exchange is flipped to `interrupted` and the first scheduled observation resolves it by `ListTasks` filtered on the run's correlation ID — for a start, adopt if found, else stay `delivery_unconfirmed` for the user's **Check again** (Decision C); for a reply, confirm by succession evidence (a task in the run's conversation created after the command's `created_at`, since Hermes serves no history, F5), otherwise leave the reply unconfirmed with the reply control restored once the run is observed blocked again (Decision E). Recovery never resends: no background thread — scheduler, observation pool, exchange pool, control pool, restart recovery or retention sweep — ever emits a content-bearing `SendMessage`; the only sends are a confirmed hand-off, its user-triggered replay and a user reply (FR-006, AC-032).
- **Ownership seam**: `observer.py` owns scheduling, wake draining and network I/O only. Every result — observation, exchange outcome, `TaskNotFound` — is handed to `AgentRelayService.apply_observation(run_id, owner_id, observation, based_on)`, which owns the `run_version` compare-and-set, terminal locking, the timeline append and `agent_task_missing_at` (Decision E). The service receives the exchange executor as a constructor port (a `Callable`/executor protocol), so `container.py` wires `A2AClient` → `AgentRelayService(client, exchange_executor)` → `AgentObserver(service, client)` with no construction cycle. No network I/O ever happens inside the repository's process-wide `command_lock` (F11): a worker performs the call, then re-reads the run under the lock and applies the result, exactly as the 007 dispatch path does in `service.py`; the lock is held only for that short conditional write, never across a wait.
- **Dispatch shape**: the API thread (`dispatch_run`) keeps the 007 durable reservation, marks `delivery_unconfirmed` + `exchange_state=queued` (F11), submits the `SendMessage` exchange to the exchange pool, and waits up to `dispatch_wait_seconds` (default 5) for the future. `exchange_state` becomes `open` and `exchange_started_at` / `exchange_deadline_at` are stamped when a worker **starts** the exchange, not at submit (deadline = start + `reply_window_seconds` + 15 s). If the exchange has started and is still open when the wait ends, the API thread performs **one inline probe** (`ListTasks` by correlation ID, `pageSize=5`, short timeout) and returns; if the exchange is still `queued`, the probe is skipped — nothing has gone out — and the response is the **Queued** projection (`primary_state_label: "Queued"`, explained as "Waiting for a free connection slot; nothing has been sent yet": the queued variant of D-03-S04 / M-03-S03), which becomes **Sent** only when a worker starts the exchange — never before, because nothing has left BrainBuddy. Probe or exchange evidence upgrades `dispatch_state` to `sent`; a `ConnectError`/4xx before any task → `not_sent` (429 → `a2a_rate_limited`); anything ambiguous stays `delivery_unconfirmed` with the exchange open. Exchanges use `httpx.Timeout(connect=5 s, read=reply_window_seconds + 15 s)` (default 300+15 for the read) so a black-holed host releases its worker after the connect timeout while an agent answering at exactly the window is still received (SC-006). An httpx read timeout is per chunk, though, so a server that emits one byte every few hundred seconds never trips it and `_bounded_response_body`'s byte budget (`egress.py` 404–491) bounds bytes, not time; `egress.pinned_request` (341–391) therefore also takes an absolute wall-clock deadline — sized to the operation's window plus a margin: reply window + 15 s for an exchange, the short-call timeout plus a margin for observations and control calls — that it enforces itself while waiting for headers and inside the `iter_raw` loop, closing the stream and raising a distinct `EgressDeadlineExceeded` on breach; an exchange breach maps to `delivery_unconfirmed` (lookup before any resend, Decision C), an observation breach to a failed contact. `exchange_deadline_at` is that deadline made durable, so it is enforced on the open socket rather than merely recorded. Reply exchanges reuse the same path with `command_id` as `messageId` and `exchange_kind=reply`.
- **Backoff** (FR-008): after `reporting_window_seconds` elapse without contact the run's observation interval backs off geometrically (×2 per missed interval), capped at 10 × `observation_interval_seconds`, until `identifiers_expire_at`; a verified push, a reply or cancel acknowledgement, or the user opening the run (a `GET` of the run) resets `next_observation_at` to the base interval. The configured interval is therefore a minimum, never a promise, which is how the spec Assumptions already describe it.
- **Shutdown/Fly**: scheduler stop event + `shutdown(wait=False, cancel_futures=True)` on all three executors (which only cancels futures that have not started — the absolute deadline is what releases a started one), joined with a 5 s timeout in the existing `_stop_maintenance_sweeps` handler (`main.py` 230–238); in-flight exchanges are recovered on restart as above. F10: one always-on machine, 8 + 4 + 2 threads and ≤ 14 open sockets are negligible at 1 GB; no per-run thread exists, so "no per-owner cap" (spec Assumptions) is bounded only by the three pools, the per-connection exchange bound and `sensitive_action_rate_limiter`-style limits on the API side.
- **Determinism in tests**: `AgentObserver(exchange_executor=SynchronousExecutor(), observation_executor=SynchronousExecutor(), control_executor=SynchronousExecutor(), clock=Clock, probe_delay=0)` runs exchanges, observations and control calls inline; `observer.run_once(now)` performs one scheduler pass; no test sleeps. The thread is started only by `main.py` under `background_maintenance_enabled` (F9), which the compose E2E already enables.
- **Alternatives**: one pool shared by exchanges and observations (rejected: eight 315 s exchanges would stall every owner's observations for five minutes and break SC-006 under the "no per-owner cap" decision); cancel and push registration on the exchange pool (rejected: a cancel would wait behind the exchanges it ends, and one owner's slow agents would delay every other owner's cancel); resubmitting a `queued` exchange to the pool after a restart (rejected: a background send without a fresh user action, and indistinguishable from the resend Constitution Principle I forbids); per-run threads (rejected: unbounded, Fly 1 CPU); asyncio task inside uvicorn (rejected: services are sync, ADR-0002 forbids correctness on untracked `asyncio` tasks); polling only from the maintenance thread with no held exchange (rejected: Hermes never creates a task without the blocked request, F1/F2); streaming `SendStreamingMessage` (rejected: doubles the transport surface, adds nothing over probe+poll, and `stateTransitionHistory` is absent on Hermes).

### C. Dedup and identifiers

- **Decision**: `context_id = run.id`; start `message_id = f"{run.id}:start"` (derived from the run's idempotency key, which 007 already equals to the run id — `service.py` 1506); reply `message_id = command_id`; cancel carries `CancelTaskRequest.metadata["brainbuddy.command_id"]`. Every message carries `metadata = {"brainbuddy.task_id": <task id>, "brainbuddy.run_id": <run id>}` (FR-006). Before **any** resend (a replayed confirmation or the user's **Check again** on a `delivery_unconfirmed`/`interrupted` run) BrainBuddy calls `ListTasks(contextId=run.id, pageSize=5)`; a found task is adopted (newest by `status.timestamp`) and never resent; only an empty answer allows resending the byte-identical message. **Resend preconditions and serialisation** (FR-004, FR-006, AC-030, SC-008): the lookup is an authenticated observation and is always allowed, also while rollout is OFF; the resend branch is refused — `connection_not_ready` when the connection is not `ready`, is stale, or its `scope_verified_at` is `None` or younger than the run's `dispatched_at` (an address, auth-scheme, credential or card-drift reset since dispatch: `service.py` 805–806 and 932–933 re-stamp `scope_verified_at` and clear `first_dispatch_at` on such a reset), `agent_card_changed` when the connection is **Agent changed** or the run's pinned `card_fingerprint` no longer matches the connection's, `run_content_expired` when the frozen manifest is null (`expire_due_content` nulls it at 30 d, so there is nothing reviewed left to send) — leaving the run `delivery_unconfirmed`; when it runs it passes `requires_dispatch_reauthentication` (`service.py` 1242–1256, today consulted only at preview and dispatch) exactly like a dispatch, taking `current_password` on the `check-delivery` request for that case, and goes to the run's pinned `interface_url`. The `interrupted|delivery_unconfirmed → open` transition is a durable compare-and-set on `run_version` under the process-wide `command_lock` (F11) before any resend I/O, so a second contender — a double-tapped **Check again**, a replayed confirmation whose key is the original dispatch key, or the observer's restart-recovery lookup — re-reads, sees the exchange `open` and returns the winner without network I/O; the SC-008 barrier suite gains those three interleavings (Decision J). While rollout is OFF the resend branch is refused and the run stays `delivery_unconfirmed` until the flag is ON (AC-036). With a guaranteed-tier agent the **first** `SendMessage`, every replay of it and every reply carry `A2A-Extensions: <uri>` **and** `message.extensions=[<uri>]` — activation on the first send is what obliges the agent to record the dedup key (extension spec §3–4; `contracts/a2a-wire.md` is authoritative, and the guaranteed-tier fake in `tests/a2a_fakes.py` asserts the header on the first request and refuses dedup when it is absent); the agent dedups by `(contextId, messageId)`. The `contextId` BrainBuddy sends is always the server-assigned run id and is never derived from any inbound request header, so a caller-supplied correlation header can never become a dedup, lookup or authorization input at the agent (constitution Principle IV). **Adoption safety**: every adopted task — from the dispatch answer, the probe/lookup or a reply — must satisfy `task.contextId == run.id`; when the first `SendMessage` response shows the agent ignored the client `contextId`, the connection records `context_id_honoured=false`, BrainBuddy never resends for it at all — not from any thread and not on **Check again**, because an empty lookup on such a connection proves nothing (an empty lookup keeps **Delivery unconfirmed**) — and the best-effort disclosure copy and the extension spec's client section (§5) say so.
- **Extension identifier**: `https://github.com/MaksimKravchuk/brain_buddy/blob/main/docs/a2a-extensions/single-start/v1.md` (repo remote per `git remote -v`; A2A `docs/topics/extensions.md` asks for a versioned URI whose specification is hosted at the URI). Contract in `contracts/brainbuddy-single-start-extension.md`; tier = `guaranteed` iff the URI appears in `card.capabilities.extensions[].uri`, else `best_effort`. Accepted for v1 (Resolved 5): the path is frozen by repository policy; a redirect-based identifier may be added in a later version without changing v1.
- **Rationale**: spec §3.4.1 lets an agent accept a client `contextId` (Hermes and the SDK do, F2/F6); `ListTasks` is a core operation with a `contextId` filter in both runtimes; replays of the same `Idempotency-Key` never reach the network at all (F11), so SC-002's three replays create one task on every runtime, extension or not. Residual duplicate risk (Hermes forgets tasks on restart, F3) is disclosed, not hidden (FR-003).
- **Alternatives**: `message_id = run.id` (rejected: replies need distinct ids and the extension dedups per message); a2a `referenceTaskIds` for replies (kept as an additional hint only); client-generated task ids (not allowed by §3.4.2).

### D. Push notification receipt

- **Decision**: New inbound route `POST {api_prefix}/a2a/push/{run_id}/{token}` replaces `/agent-events`. BrainBuddy registers, **inline in `SendMessage.configuration.taskPushNotificationConfig`** whenever the card declares `pushNotifications: true`, `{url: "<public_base>/api/a2a/push/<run_id>/<token>", token: <token>}` (Hermes stores only the URL, F4; the SDK echoes the token in `X-A2A-Notification-Token`, F6 — the path token works for both). `CreateTaskPushNotificationConfig` is used only for a task adopted after an interrupted exchange. The token is 32 random bytes per run, stored only as `SecretBox.fingerprint` (`push_token_fingerprint`); verification = path token fingerprint match against a dispatched, non-terminal, non-disconnected run whose connection still exists. The fingerprint is kept until identifier expiry (90 d), not cleared at terminal: Hermes pushes exactly once, on the terminal or input-required transition (F4), so a valid push racing BrainBuddy's own terminal observation is the common case, and with the fingerprint still present it passes the comparison step and is classified `push_after_close` at the run-state step — never `push_token_rejected` (SC-003, `test_valid_push_after_terminal_is_classified_push_after_close`). The unknown-run, wrong-token and closed-run rejections answer byte-identically (`test_push_rejections_are_indistinguishable_to_the_caller`), so the only run-existence signal is the per-run `429` — a deliberate, run-id-gated deviation from the repository's 404-for-wrong-owner convention, recorded in one line in `docs/auth.md`. A verified push enqueues an immediate observation and answers `204`; **the body is never parsed for state** (read up to 64 KB for the cap, then discarded). Unverified/unknown-run/oversize/malformed → opaque `403`/`413` with **no durable row** (007 post-ratification clarification, `specs/007-external-agent-relay/spec.md` 111–128); a known run with a wrong token records one bounded row per (owner, connection, `push_token_rejected`, UTC day) exactly like `_audit_authenticated_event_rejection`. **Check order** (`contracts/push-callback.md`): (1) body size limit → (2) a bounded process-wide limiter for the whole route, consulted before any database read → (3) resolve the run id; unknown → `403`, no durable row, no limiter key → (4) constant-time comparison of the token fingerprint → (5) the per-run limiter, whose keys exist only for known, dispatched, non-terminal runs, which has a maximum key count and evicts a run's bucket when the run goes terminal or is disconnected → (6) schedule the observation. `InMemoryRateLimiter` (`app/core/rate_limit.py`) never evicts keys — `_hits` and `_reservations` are `defaultdict`s and `_prune` only trims timestamps inside a key — so the push route uses a bounded variant (a `max_keys` extension of it), never the class as-is. Rejections of unknown ids are counted only in a process-wide fixed-size counter for alerting, never per unknown id. Reply messages carry the same `taskPushNotificationConfig` when the card supports push, so a successor task (Decision E) stays push-accelerated; the observation schedule remains the fallback. Keeping the path token out of BrainBuddy's own logs is Decision K.
- **Rationale**: FR-008 says push only accelerates observation, so the token is a capability to trigger one authenticated `GetTask`, nothing more — acceptable in a URL that Hermes may log, provided BrainBuddy's own logs never repeat it (Decision K). Hermes' `X-A2A-Signature` is keyed by `A2A_PUSH_SECRET` (unknowable) or the bearer token (F4); it is not per-run and is therefore **not** accepted as verification; a Hermes push without a path token is simply not accelerated and SC-006 still holds through the 60 s schedule.
- **Alternatives**: verifying Hermes' HMAC with the stored credential (rejected: not per-run, couples to one agent's convention); registering `authentication: {scheme: Bearer}` (kept optional; neither runtime honours it); parsing the payload to short-circuit `GetTask` (rejected: FR-008 forbids state from push).

### E. State mapping and observation versioning

- **Decision**: `mapping.py` is a pure function `project_observation(task_or_message, *, now, limits) -> Observation`: `TASK_STATE_SUBMITTED → accepted`; `WORKING → running` with `progress_text` = text parts of `status.message` (≤ `MAX_PROGRESS_CHARS` 2000); `INPUT_REQUIRED → blocked` with `question_text` (≤ 4000); `AUTH_REQUIRED → blocked` with `failure_reason=None`, `question_text=None`, fixed `blocked_reason="Agent needs additional authentication"` and `needs_user=False`; `COMPLETED → completed` with `result_text` = text-part artifacts joined by blank lines then the final status text (≤ `MAX_RESULT_CHARS` 20000), `result_link` = first `Part.url`, shown as inert text the user can copy — the 007 helper `egress.interactive_result_link` is kept unchanged: it returns `False` for every link with its documented reason (only syntax is available server-side, and a publicly named host can resolve to a private or metadata address at click time), so `result_link_interactive` is never `true` (product owner, 2026-09-04; AC-016, D-03-S11 / M-03-S10) —, non-text parts → `artifacts_summary[{name, media_type, kind}]` (≤ 20 entries) rendered as placeholders; `FAILED → failed` with `failure_reason` = status text; `REJECTED → failed` with `"Rejected by agent" + (": " + status text)`; `CANCELED → cancelled`; a direct `Message` answer → `completed` with its text. Truncation appends `" … [truncated]"` and still accepts the observation. `TaskNotFoundError (-32001)` on `GetTask` → `agent_task_missing_at=now`, last contact preserved, observation stops, reply/cancel withdrawn, `reported_state` unchanged (AC-020). **Task succession** (Resolved 6, FR-010, AC-028, design D-03-S27 / M-03-S26): when a reply exchange returns a Task whose id differs from `agent_task_id` but whose `contextId` equals the run's correlation id (Hermes mints a new task per message, F2, and its watchdog fails the original after 300 s, F3), BrainBuddy adopts the returned task as the run's current agent task, appends the timeline event **The agent continued this run in a new task** carrying the old and new task ids, keeps the run's single correlation id, and never refuses the reply. **Precedence against the terminal lock** (Hermes fails any non-terminal task, `INPUT_REQUIRED` included, 300 s after creation while the reply exchange itself may block up to 300 s): (a) while the reply exchange is open, scheduled observation of the predecessor task is suspended, and a terminal observation of the predecessor that arrives while the reply is unconfirmed or its exchange is open does not lock the run — it is recorded as a timeline row ("The previous task ended: <state>") and the run stays blocked/reply-pending; (b) when the reply exchange returns a successor task, the succession row supersedes the predecessor's terminal outcome; (c) when the reply itself meets a failed/terminal task with no successor, the run shows the agent's own reason honestly and the reply control is withdrawn; (d) the suspension has an exit: scheduled observation of the run resumes once the reply exchange is `closed` or `interrupted`, or at `exchange_deadline_at`, whichever comes first, so an ambiguous reply exchange (timeout, 5xx, transport loss) never leaves the run unobserved until identifier expiry; a reply that is never acknowledged stays in the timeline as unconfirmed and the reply control is restored — for a new command id — only after a later observation shows the run blocked again (AC-033; `test_ambiguous_reply_exchange_resumes_observation_at_the_deadline`, Decision J).
- **Observation reads and over-cap responses**: routine observation is `GetTask {id, historyLength: 0}`; history is fetched only when the observed state needs text (an `INPUT_REQUIRED` question, a terminal summary) with a small bounded `historyLength`. Task reads use a larger byte cap than card reads — new setting `agent_relay.a2a_task_max_response_bytes`, default 256 KB, hard maximum 1 MiB — because `GetTask` has no `includeArtifacts` switch and a completed task with artifacts can exceed the 64 KB card cap. On an over-cap `GetTask` the client falls back to `ListTasks {contextId, includeArtifacts: false, historyLength: 0}` so the state is still observed; the run then carries `result_availability="too_large"` and shows the result as "unavailable (too large to store)" with a visible marker instead of ever drifting into **Stopped reporting**.
- **Cancel outcomes** (FR-010, AC-029): `unsupported` only for `-32004` and `-32601`; `not_cancelable` only for `-32002`; `-32603`, HTTP 5xx, timeouts and transport loss map to `cancel_outcome="unconfirmed"`, which keeps the cancel control available for a later attempt with the same command id — never a durable "not supported by this agent" claim from a transient error.
- **Content expiry**: an observation (scheduled or push-triggered) on a run whose content tier has already expired (`content_expired` or `now >= content_expires_at`) advances only `reported_state`, `run_version`, `last_contact_at`/`last_observed_at`, `agent_task_state`, timeline markers (rows with `summary=None`) and terminal locking; it MUST NOT write `blocked_reason`, `artifacts_summary`, status text or any other agent text back into the row — the discipline the deleted `_event_updates`/`_event_summary` enforced for 007 FR-015. 007 also enforces expiry at read time: `domain.project_run_for_access` ("due content is inaccessible before sweep", `domain.py` 362–378) nulls the 007 content fields on every read path (`service.py` reads and `repository.py` `export_owner_data`); it is extended to null `blocked_reason`, `artifacts_summary`, `result_availability` and the agent status text as well, so between `content_expires_at` and the next sweep pass — and in a process where the maintenance thread is off, as under `BRAIN_BUDDY_ENV=test` — no read returns expired agent text (`test_expired_but_unswept_run_reads_with_no_agent_text`, SC-007).
- **Versioning and writes**: the worker reads `run.run_version` as `based_on` before I/O; after I/O `AgentRelayService.apply_observation` re-reads the run under the repository's process-wide `command_lock` and aborts when the run is missing, disconnected, terminal or identifiers-expired; it applies only if `run.run_version == based_on` (compare-and-set) and writes `run_version = based_on + 1` through a conditional `UPDATE … WHERE owner_id=? AND id=? AND run_version=?` — there is no insert path from observer or exchange threads, so a purged run can never be resurrected and a disconnected or terminal run never overwritten, and no event, command or audit row is written for a missing run. Network I/O never happens inside that lock (the 007 dispatch path in `service.py` 1527–1547 is the pattern). An identical observation (same state and texts) bumps `last_contact_at`/`last_observed_at` only and appends no timeline event and no audit row; a differing observation appends an `AgentRunEventDocument` with `trigger ∈ {dispatch, schedule, push, command}` and one `observation_accepted` audit row, bounded per (run, state class, UTC day). Terminal states lock the run: it leaves the schedule and any later differing observation is rejected (`observation_rejected: run_terminal`, bounded audit), subject to the succession precedence above.
- **Alternatives**: trusting `status.timestamp` ordering (rejected: absent/unreliable, spec has no version); treating `INPUT_REQUIRED` as terminal for Hermes because the watchdog fails it at 300 s (rejected: the observation of `FAILED` will arrive honestly, and the precedence rule keeps it from masking a successor); parsing `GetTask` bodies partially past the cap (rejected: a truncated JSON body is not an authenticated observation; `ListTasks` without artifacts is).

### K. Observability and honesty

- **Decision**: every outbound A2A call runs under a **server-generated** correlation id — `uuid4().hex` minted per outbound call, `obs_<id>` per observation in the observer — sent as `X-Correlation-ID` and recorded on audit rows, and the same value is logged on BrainBuddy's side; the inbound `X-Correlation-ID`/`X-Request-ID` header that `CorrelationIdMiddleware` accepts verbatim stays an observability label for the API request (`app/core/logging.py` `set_correlation_id`) and is never forwarded to an agent. Structured log fields are limited to `method`, `http_status_class`, `a2a_error_code` (allowlist: `-32700, -32600..-32603, -32001..-32009`; anything else logged as `other`), `response_over_cap` (a boolean for the Decision E fallback), `protocol_version`, `duration_ms`, `run_id`, `connection_id`, `owner_id`; never the card body, message parts, artifacts, credentials or the push token. **Push-token redaction** (`contracts/push-callback.md`, Redaction): `CorrelationIdMiddleware` (`backend/app/api/middleware.py`) today logs `request.url.path` on both its success line and its `api_request_failed` exception line, so it applies a pure sanitiser before any log call that rewrites any path under `{api_prefix}/a2a/push/` to `{api_prefix}/a2a/push/{run_id}/[redacted]` and never raises; `backend/app/core/logging.py`, which routes `uvicorn.access` to the console handler, gains a logging filter that rewrites or drops access lines whose path starts with that prefix. Those two are the only layers, and the only ones that exist on the path the token travels: the callback URL is built from `agent_relay.public_base_url` = `BRAIN_BUDDY_PUBLIC_BASE_URL` (`config.py` 1002–1003), which `fly.backend.toml` (line 16) sets to `https://brain-buddy-backend.fly.dev` — the backend Fly app's own origin — so agents call the backend app directly; `deploy/nginx/default.conf` is baked into the *frontend* image (`frontend/Dockerfile` 29) and proxies outward to that same backend (`fly.frontend.toml` `BACKEND_ORIGIN`), so it never sees a push request and gains no `location /api/a2a/push/` block; and `backend/Dockerfile` runs uvicorn with no reverse proxy of its own. The real production edge is therefore the Fly proxy in front of the backend app, which may log request paths outside BrainBuddy's control; that residual is disclosed rather than argued away, and it is bounded by the token's nature — wake-up-only (a verified push only schedules an observation BrainBuddy would perform anyway within `observation_interval_seconds`), unique per run, and not honoured once the run is terminal or disconnected (Decision D). SC-009's log-scan evidence (`test_push_token_never_appears_in_logs`) covers exactly the two in-process edges — application logging and `uvicorn.access` — and says so. User-visible failures map to the SC-009 categories with the correlation id (existing error envelope).

## Resolved (product-owner decisions at design sign-off, 2026-09-03; spec commit `9afdcaf`)

1. **Vocabulary** — client-facing fields are `supporting_items` (was `context_items`) and `correlation_id` (the A2A `contextId`); the protocol words never appear in client-facing responses (spec Clarifications, FR-014). Both clients are rewritten anyway; internal Python/JSON-RPC names keep the protocol terms.
2. **Link** — the best-effort disclosure links to the published extension specification (FR-003, AC-026): `tier_disclosure_url` on the connection response and on the hand-off preview response; opens only on explicit user action.
3. **Agent changed** — a fifth connection condition (FR-002, FR-014): `status="untested"` + `last_test_error_code="agent_card_changed"` + `agent_changed: true`, rendered as D-01-S20 / M-01-S18; behaves as untested until a new successful test and requires reauthentication before the next content-bearing dispatch (FR-004).
4. **One-time acknowledgement** — not warn-only (FR-003, AC-026): per-connection `best_effort_acknowledged_at`, set by the first confirm carrying `acknowledge_duplicate_risk: true`; a confirm without it while the timestamp is null on a best-effort connection is refused; the preview exposes `acknowledgement_required`.
5. **Extension identifier** — the GitHub URI is accepted for v1; the path is frozen by policy and a redirect-based identifier may be added in a later version without changing v1 (`contracts/brainbuddy-single-start-extension.md` §8).
6. **Task succession on Hermes** — accepted: a reply that returns a new task under the same correlation ID is adopted as the run's current agent task, the timeline records **The agent continued this run in a new task** with the old and new ids, and the reply is never refused (Decision E, `contracts/a2a-wire.md`). Written back into the spec after review campaign 1 as FR-010, AC-028 and a Clarifications entry, with the precedence rule against the terminal lock; designed as D-03-S27 / M-03-S26.
7. **Card metadata retention** (product owner, 2026-09-04, after review campaign 1) — connection lifetime: the live connection's card summary and `card_fingerprint` are erased on disconnect together with the credential; the 90-day bound applies only to audit rows that name the card (FR-016, AC-024, SC-007; Decision H; `data-model.md` §1/§8).
8. **Result links** (product owner, 2026-09-04, after review campaign 1) — inert text the user can copy, as 007 ships them: `egress.interactive_result_link` stays unchanged and `result_link_interactive` is never `true` (AC-016, FR-016; Decision E; `contracts/api-deltas.md`; D-03-S11 / M-03-S10 amended by the design stage).

**Review campaign 2 (2026-09-04) — technical resolutions, no product decision needed**, recorded in the spec's Clarifications and as AC-030..AC-037: the push callback lands on the backend origin and its redaction has two in-process layers plus a disclosed Fly-edge residual (Decision K); the read-time projection covers the 014 content fields (Decision E); the reply-pending observation suspension is bounded by the exchange deadline (Decision E); a `queued` exchange found at restart settles as **Not sent** `restarted_before_send` and nothing is ever resent from a background thread (Decision B); the resend branch of a delivery check has preconditions, needs dispatch reauthentication, is serialised per run and is refused while rollout is OFF (Decision C); card-sourced text renders inertly (Decision I); the rate-limited connection test is a named outcome with D-01-S25 / M-01-S22 (Decision I); the run id is retained honestly and the sweep is hardened (Decision H); every outbound request carries an absolute deadline, one connection holds at most two exchange workers, and cancel runs on its own pool (Decision B); 014 run rows stay parseable by the 007 image (Decision F); the migration is counted, audited and idempotent per startup (Decision F); the iOS compatibility mechanism is the release-runbook rollout gate (Decision F, `contracts/api-deltas.md` §Compatibility).
