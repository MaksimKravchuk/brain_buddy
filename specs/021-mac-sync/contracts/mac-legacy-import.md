# Contract: importing the pre-021 Mac store (FR-020 – FR-023, FR-033, US4-1, US4-2, US4-4, SC-003)

**Files**:

- `macos/Sources/BrainBuddyMac/LegacySnapshot.swift`: decoder of data-model E10;

- `ios/BrainBuddyKit/Sources/BrainBuddyCore/ImportCanonicalizer.swift`: the field transform of §2a, pure and Linux-tested, because it must agree with the kit's own `NameNormalizer` and `FieldRules` (review c2, blocking G02).

**Slices**: `ImportCanonicalizer` in PR-04 (kit, pure-helper lane); everything else in PR-08.

**Tests**: `ios/BrainBuddyKit/Tests/BrainBuddyCoreTests/ImportCanonicalizerTests.swift` (Linux) and `macos/Tests/BrainBuddyMacTests/LegacyStoreImporterTests.swift` (macOS lane), with synthetic fixtures under `macos/Tests/BrainBuddyMacTests/Resources/`:

No real data is used (constitution I).

## 1. When it runs

At launch, after `SingleInstanceGuard` (contracts/mac-app-host.md §1) and **before** `Workspace.load()`, holding the single-instance lock and the legacy `lockf` (on `.local-gtd.json.lock`, the protocol a pre-021 build uses) for the whole decision and import.

**State machine** (review c1, blocking F02; revised in review c2, G06, G10, G33): the import state is explicit and durable in `mac-local.json` (`legacyImport`, data-model E7.1), with the states `none`, `inProgress`, `completed`, `unreadable` and `laterFileKept`, and the launch decision table there is normative. In short:

- the import runs only when the workspace is **not in use** (data-model E7.1 invariant 2: no `store.json`, never written, no backup or quarantined file, record not `completed` or `laterFileKept`), which includes a fresh install never written to;
- `inProgress` is recorded durably before anything is written;
- the import is built in a staging file `store.import-<attemptID>.json`, verified (§3), recorded `completed`, and only then moved to `store.json` with an exclusive rename that fails if `store.json` exists. So the workspace never opens on an unverified import, and no `store.json` is ever replaced;
- only then is the imported legacy file (identified by its keyed digest) renamed to the backup, also exclusively, and `legacyRenamedAt` is recorded;
- orphaned staging files are deleted at every launch and at sign-out (invariant 5).

**A previous-version file that appears later** (FR-033): an older copy launched after the update, a Time Machine restore, a moved file, a deleted `mac-local.json`, or any of these after a sign-out emptied the workspace, can put a `local-gtd.json` beside a workspace in use. It is never imported, merged or written over, and never renamed or deleted. The person is told once (design X-05 "later file"), and X-02 keeps a quiet line with "Show in Finder" while the file exists (data-model E7.1).

While the import runs for longer than 300 ms, the window shows static list placeholders (X-05 "loading"). No progress text is shown.

## 2a. Canonical transform (review c2, blocking G02)

The kit stores names and texts the way the server does, and its rules differ from the old store's. The old store trimmed with Foundation whitespace, counted length in grapheme clusters (`String.count`), never limited notes, and compared names with `localizedCaseInsensitiveCompare` (`LocalGTDStore.swift:268-274, 526-550, 628-631`). The kit stores project names in `NameNormalizer.display` form (NFKC, Python whitespace strip and collapse) and tag names in `NameNormalizer.tagDisplay` form (also one leading "@" dropped), counts Unicode scalars, limits notes to 20,000, and keys uniqueness on casefold + NFKC + whitespace (`NameNormalizer.swift`, `Reducer+Validation.swift:1-64`, `Vocabulary.swift:84-91`).

So "Квартира №5" becomes "Квартира No5", "™" becomes "TM", "Home  Repair" becomes "Home Repair", "@home" becomes "home", and "@home" and "home" collide although the old Mac kept both. An import that applied the old values raw would fail verification or validation on ordinary data and strand it.

Before any command is issued, every legacy value therefore passes through `ImportCanonicalizer`. It is a pure, deterministic function from the legacy snapshot to (a) the values the kit will store and (b) a list of adjustments. It is total: for every snapshot the old app could write it yields valid kit values. Its rules:

| field | kit rule | transform (in this order) | where the full original text goes |
|---|---|---|---|
| project name | `NameNormalizer.display`, 1…500 scalars, unique among active projects by `NameNormalizer.project` | 1. `display(legacy)`; 2. empty → "Untitled project"; 3. over 500 scalars → cut at the last grapheme boundary that leaves room for "…" within 500 scalars, then "…"; 4. an **active** project whose key equals an earlier active project's key (legacy order) gets " (2)", " (3)" … (the smallest free number; the base is cut first if the suffix would pass 500). Archived projects get no suffix: they may share a name | import report; backup |
| tag name | `NameNormalizer.tagDisplay`, 1…500 scalars, unique among active tags by `NameNormalizer.tag` | the same four steps with `tagDisplay` and "Untitled tag"; so "@home" and "home" become "home" and "home (2)" | import report; backup |
| task title | `NameNormalizer.stripped`, 1…500 scalars | 1. `stripped(legacy)` (internal spaces are kept, as for every title); 2. empty → "Untitled task"; 3. over 500 scalars → cut as above with "…", and "Full title: <original>" plus a blank line is put before the notes | task notes |
| subtask title | as task title | as task title; the full title goes to the parent task's notes as "Full subtask title: <original>" | task notes |
| waiting-for | stripped, 1…500 scalars, required in Waiting | stripped; over 500 → cut with "…" and "Waiting for: <original>" added to the notes; empty in Waiting → "(not recorded)" | task notes; report |
| notes | ≤ 20,000 scalars, verbatim | after any text added above: over 20,000 scalars → the first part, cut at a grapheme boundary within 20,000 scalars, stays as notes; the rest becomes comments "Notes, continued (k of n):" + the next part, each within 20,000 scalars, created right after the task at its `createdAt`, before its own comments | comments |
| comment body | 1…20,000 scalars, verbatim | over 20,000 → split the same way into consecutive comments, the later ones starting "(continued)" | comments |
| desired outcome | trimmed, blank → nil, ≤ 1,000 scalars | over 1,000 → cut with "…" | import report; backup |
| project colour | ≤ 64 scalars | the old app never sets one (`LocalGTDStore` writes `color: nil`); a value over 64 scalars is dropped | import report |
| due date and other dates | `Date` | an unparseable value is dropped from the task (the task is carried) | import report |
| task state or list | `TaskState`, `OpenList` | an unknown value → the task is carried, open, in Inbox | import report |
| reference to a missing project or tag | — | the task is carried without that reference (deleted tags are dropped, as before) | import report |

**Report and notice**: every adjustment is one entry in the **import report** `local-gtd.import-report-<UTC>.txt` beside the backup (data-model E8), with the kind of record, the original text, the result and the rule. A record the transform still could not carry (none is known; the category exists so nothing can be dropped silently) is listed as "not carried", the backup is then never deleted by the app (data-model E8 condition 3), and X-05 shows "partly carried over" once. With adjustments only, the upgrade stays silent (X-05 default, owner-approved) and X-02 shows "Some details changed during the update" with "Show in Finder". The report never reaches a log; `os.Logger` gets counts only.

**Why rename and not merge on a kit-only collision**: suffixing keeps both records and their memberships apart, is reversible by the person (rename or merge by hand), and loses nothing; merging two of the person's projects or tags would be a silent edit of their organisation. At the first sign-in, merge by name with the account works as usual on the resulting names (kit-commands §3).

## 2. Command plan (canonical records → kit commands)

The import builds the account-less document by applying `GTDCommand`s through `GTDReducer` in **interactive** mode, with `issuedAt` set to the original instants and every value taken from §2a. Because §2a is total over valid kit values, a reducer rejection now means an importer defect: it is reported as `verificationFailed`, never as a corrupt file.

**No compaction** (review c1, F38): the import's outbox is **not** passed through `OutboxCompactor`. Compaction may fold a move into an unsent creation, after which the reducer stamps `waitingSince` with the creation's time (`Compaction.swift:24-28`, `foldMove`), and it changes `orderKey` and a comment's `editedAt`. The importer issues those operations deliberately, and §3 verifies them exactly, so the outbox stays as issued. Edits the person makes later are compacted by the kit as usual.

The order is chosen so that every command is valid when applied and each list keeps the Mac's cross-project order (review c1, F58):

1. **Tags**: `createTag` for each `state == active` tag, issued at the import time, because the legacy tag has no timestamp.
2. **Name-clashing archived projects** (an archived project whose kit key equals an active project's), one at a time, in legacy order, before their active namesake exists:
   1. `createProject(name, color, desiredOutcome)`, issued at the earliest `createdAt` among its tasks, or the import time when it has none;
   2. that project's tasks (step 4), in their legacy order;
   3. `archiveProject`, issued at the import time. It is lossless under §3 of kit-commands, so the tasks keep it.

   Their tasks therefore lead their lists. This is the one accepted reordering, stated in the spec's edge case "Same-named archived projects" (review c2, G08), because two active projects may not share a name; §3 expects exactly this sequence.
3. **Every other project**, active and archived, in legacy order: `createProject(name, color, desiredOutcome)`.
4. **All remaining tasks in one global order**, sorted by `(list, orderKey, createdAt, id)` across projects, so that the reducer's create-time `orderKey` (end of list) and the server's upload order reproduce the Mac's order within each list:
   1. `createTask` into `lastOpenState ?? state` (an open list), with title, details, projectID, tagIDs (active tags only), dueDate, priority and waitingFor (when Waiting), issued at `createdAt`;
   2. "Notes, continued" comments, if §2a produced any;
   3. when the legacy `waitingSince` differs from `createdAt`: `createTask` into Inbox at `createdAt`, then `transitionTask(.move(.waiting, waitingFor))` at `waitingSince`;
   4. `createSubtask` per subtask in `orderKey` order, then `transitionSubtask` for completed and cancelled ones;
   5. `createComment(body)` at `createdAt`, split per §2a when long. The edited text is the stored body; `editedAt` is not reproduced, because the kit has no command that sets it (spec Assumptions);
   6. terminal tasks: `transitionTask(.complete)` at `completedAt`, or `.cancel` at `cancelledAt`.
5. **The other archived projects**: `archiveProject` each, issued at the import time, after all their tasks exist.
6. **Records not imported**:
   - deleted tags;
   - `idempotency` and `idempotencyReceipts`;
   - a comment's `editedAt` marker.

   Each is counted in the import report's counts (not as an adjustment). The review marks go to the sidecar (§4), not to the document.

A legacy id is never sent. Kit records get fresh `EntityID`s from an injectable generator (the tests seed it, so the output is reproducible; §6 golden artifact), and the importer keeps a legacy id → client id map in memory, used for §3 and §4.

**At first sign-in**, an archived Mac project whose name matches an active account project merges into it under kit-commands §3 "Merge by name": its tasks keep the account's project and a sync issue says the archive was not applied. One that matches only an archived account project stays separate (spec edge case "Same-named archived projects").

## 3. Verification (FR-021 "verified")

After writing the staging file, the importer re-reads it, replays its outbox to a `GTDState`, and checks every pair through the id map against the **canonical expectation** that `ImportCanonicalizer` computed from the legacy snapshot, never against the raw legacy value (review c2, G02). Any mismatch fails the import with `verificationFailed`: the staging file is deleted, the legacy file stays untouched, and X-05 "couldn't carry over" runs.

| expectation (from §2a) | kit current state | equality |
|---|---|---|
| carried task count by state | `GTDState.tasks` | exact; carried = legacy − "not carried" |
| title, details (with any added "Full title" / "Waiting for" text), state, `lastOpenState` | `title`, `details`, `state`, `lastOpenList` | exact |
| `projectID`, `tagIDs` (active, existing) | mapped `projectID`, `tagIDs` | exact through the map |
| `dueDate`, `priority`, `waitingFor`, `waitingSince` | same | exact (dates to the second); holds because the outbox is not compacted |
| `completedAt`, `cancelledAt`, `createdAt` | same | to the second |
| order of each open list **across projects** | `GTDQueries` manual sort of the list | identical sequence, with step 2's clashing archived projects' tasks first |
| order within each project | `GTDQueries` manual sort | identical sequence |
| subtasks (canonical title, state, order) | `subtasks` | exact |
| comments ("Notes, continued" first, then the bodies split per §2a, in order) | `comments` | exact; `editedAt` is not compared (not carried) |
| projects (canonical name incl. suffix, colour, state, canonical `desiredOutcome`) | `ProjectRecord` | exact |
| active tags (canonical name incl. suffix) | `TagRecord` | exact |
| the report's adjustment list | — | one entry per adjusted value, none missing |

The log line holds counts only and is written with `os.Logger`: tasks, projects, tags, subtasks, comments, adjusted values, records not carried, skipped deleted tags, skipped comment edit markers, review marks and duration. It never holds a title, a path, a file name or a digest (FR-030, research R21; review c1 F51).

## 4. Review marks → sidecar (FR-023)

| legacy | sidecar (data-model E7.2) |
|---|---|
| `waitingReviews[taskID] = {taskRevision, reviewedAt}` | `waitingReviews["c:<clientID>"] = {reviewedAt, stamp: <HMAC of RecordContentForm(imported task)>}`, only when the legacy receipt was still valid (its `taskRevision` equals the task's revision); an invalid receipt is dropped, which is exactly what the Mac would have shown |
| `somedayReviews[...]` | same rule |
| project `lastReviewedAt`, `lastReviewDecision`, `lastReviewedTaskSignature` | `projectReviews["c:<clientID>"] = {reviewedAt, decision, taskSignature: <HMAC of RecordContentForm(imported tasks)>}`, only when the legacy signature matched the legacy tasks (the project was not "changed since review") |

So a mark that was valid before the upgrade is valid after it, and a mark that was due is still due (US4-1 "review marks are also present").

## 5. Notices (FR-022, FR-033, design X-05)

| cause | `unreadableReason` | X-05 copy |
|---|---|---|
| the JSON does not decode, or a required top-level field is missing (the file itself is damaged); **only** this is `corrupt` (review c2, G02) | `corrupt` | "Brain Buddy couldn't read your earlier tasks" / "The file from the previous version was left exactly as it was. It's here:" / path / "Brain Buddy will start with an empty workspace. Keep the file if you'd like help recovering it." |
| the file was read but §2 or §3 failed: an importer defect, not a bad file (review c1, F38) | `verificationFailed` | "Brain Buddy couldn't carry over your earlier tasks" / "Your file is fine and was left exactly as it was. It's here:" / path / "This is a problem in Brain Buddy. Brain Buddy will start with an empty workspace. Keep the file: it still has all your earlier tasks." (design X-05 "error: couldn't carry over"; no promise that a later version will carry it over, review c2, G05) |
| `version > 1` | `newerVersion` | "They were saved by a newer version of Brain Buddy, so this version left the file exactly as it was." / "Install the newer version to open the file again." |
| the import succeeded but listed records it could not carry (§2a) | — (`completed`, `report.notCarriedCount > 0`) | "Brain Buddy carried over your earlier tasks, except a few it couldn't read" / "They're listed in a report next to the file from the previous version, which stays on this Mac. It's here:" / path of the report (design X-05 "partly carried over") |
| a previous-version file appeared after the workspace existed (FR-033, data-model E7.1) | — (`laterFileKept` / `laterFile`) | "Brain Buddy found tasks from the previous version" / "An older copy of Brain Buddy saved tasks on this Mac after the update. They were not added here, and the file was left exactly as it was. It's here:" / path / "Your current tasks are unchanged." (design X-05 "later file") |

**Recovery**: data-model E7.1 "Recovery, stated honestly". A file that could not be carried over stays untouched; a later build with a higher `importerVersion` retries it only while the workspace is not in use. The plan's guards against reaching that state are §2a's totality, §6's realistic fixture and property test, and the dry run on a copy of the owner's real folder before the owner's own upgrade (quickstart Scenario 6, step 0).

**How the alert behaves**:

- App-modal alert before the workspace opens. The path is selectable.
- "Continue" is the default; "Show in Finder" reveals the file, then behaves like Continue. Esc is not mapped.
- `noticeSeenAt` is recorded on either button.
- A quit while the alert is open records nothing, so it shows again next launch.

**What happens to the file**:

- An unreadable or later file is never renamed, rewritten or deleted.
- The staging file of a failed verification is deleted before the alert; `store.json` was never written.

## 6. Tests (named with requirement ids)

**Canonical transform** (`ImportCanonicalizerTests`, Linux, PR-04; `021-FR-020`), each with its exact expected value and report entry:

- project "Квартира №5" → "Квартира No5"; project "™ Ideas" → "TM Ideas"; project "Home  Repair" → "Home Repair";
- active projects "Home  Repair" and "Home Repair" → "Home Repair" and "Home Repair (2)"; an archived "Home Repair" beside them keeps "Home Repair";
- tags "@home" and "home" → "home" and "home (2)"; tag "Errands " → "Errands";
- a title of 500 emoji graphemes such as "👍🏽" (1,000 scalars) → a title within 500 scalars ending "…", the full title first in the notes, no grapheme split;
- a title "Call  mom" (double space) → unchanged, titles are not collapsed;
- notes of 25,000 characters → notes of at most 20,000 scalars plus one "Notes, continued (1 of 1):" comment, together equal to the original;
- a comment of 30,000 characters → two comments, together equal to the original;
- a desired outcome of 1,200 characters → 1,000 scalars ending "…", the full text in the report;
- a colour of 100 characters → dropped, reported;
- a task whose project id is missing → carried without the project, reported;
- determinism: the same snapshot gives byte-identical output twice.

- **Total over what the old app accepts** (`021-FR-020`; property test): a seeded generator produces snapshots that satisfy the old store's own rules, read from `LocalGTDStore.swift` before PR-08 deletes it (trimmed non-empty names and titles within 500 grapheme clusters, outcomes within 1,000, comments within 20,000, unlimited notes, active names unique under `localizedCaseInsensitiveCompare`), with names drawn from NFKC-sensitive characters (№, ™, ﬁ, full-width letters), "@" prefixes, runs of spaces and multi-scalar emoji. - **Crashes** (`021-FR-021`): injected failures after `inProgress` is recorded, after the staging write, after verification, after `completed` is recorded, and between the two renames each recover on the next run with no duplicate records, the legacy bytes unchanged until the rename, and `store.json` either absent or verified.
- **Import state is explicit** (`021-FR-033`): a first launch with no legacy file records `none` durably before the workspace opens; a completed import records `completed` with the keyed legacy digest, the backup name and `legacyRenamedAt`; `inProgress` is on disk before the staging file exists; the first write of `store.json` records `workspaceFirstWrittenAt`.
- **A previous-version file never overwrites a workspace in use** (`021-FR-033`; each asserts that the bytes of `store.json` (when present), the backup and the found `local-gtd.json` are unchanged, that no import ran, and that the X-05 "later file" notice shows exactly once):

  - **`mac-local.json` removed**: `store.json` exists, the sidecar is deleted, and a `local-gtd.json` is present;
  - **old build writes a new file after the rename**: record `completed`, the backup present, and a new `local-gtd.json` with a different digest;
  - **sign-out, then an older copy writes a new file** (review c2, G06, G10, G33): record `completed`, `store.json` removed by sign-out, no staging file, a new `local-gtd.json` → later file, no import;
  - **signed out without an import, then a file appears**: record `none`, `workspaceFirstWrittenAt` set, `store.json` absent → later file, no import;
  - **backup deleted by retention, then the original restored** (G33): record `completed` with `legacyRenamedAt` and `backupDeletedAt`, a `local-gtd.json` with the imported digest → later file; it is not renamed and not deleted;
  - **`inProgress` record but a `store.json` the attempt did not create** (for example a restored folder): `store.json` untouched, the attempt's staging file deleted;
  - **an older copy keeps writing**: a second, different `local-gtd.json` on the next launch shows no second notice, and X-02's line remains.
- **An unwritten fresh workspace may still import** (`021-FR-033`; G33): record `none`, `store.json` never written, no backup; a `local-gtd.json` copied in → imported normally (row 2).
- **Crash between record and rename** (`021-FR-021`): record `completed`, `legacyRenamedAt` nil, `local-gtd.json` with the imported digest, `store.json` present: only the rename happens.
- **Staging cleanup** (`021-FR-033`; G26): delete the sidecar while an attempt's staging file exists, relaunch: at most one staging file exists during the new attempt and none afterwards; a sign-out deletes any staging file.
- **Backup retention** (`021-FR-021`; rows added in review c2, G24, G63):

  | days since import | sign-out since import | other condition | backup |
  |---|---|---|---|
  | 29 | yes | — | kept |

- **Old copy still running** (`021-FR-020`): a second process holding the legacy `lockf` blocks the import until it releases. After the rename, that process's next write fails with its existing 409 and writes nothing.
- **Review marks** (`021-FR-023`): marks survive import, and a due mark is still due. Their survival across the first sign-in's upload and across sign-out and sign-in to the same account is tested in the kit against the fake server (`RecordContentForm`, kit-commands §8).
- **Time budget** (review c2, G22): `legacy-large.json` (2,000 tasks with subtasks and comments) imports and verifies within 10 s on the hosted macOS runner, a generous bound against regression. The plan's goal of under 2 s on an M-series Mac is a recorded host-check line, not a CI gate.
- **Privacy** (`021-FR-030`; review c1 F51): with a sentinel home folder (for example `/Users/sentinel-home-7f3a`), the populated, awkward, corrupt, newer, verification-failed, partly-carried and later-file paths are driven. The captured `os.Logger` lines hold counts, durations and enum values only: no sentinel title, no `/Users/`, no `local-gtd`, no backup, report or staging file name, and no run of 32 or more hexadecimal characters. `unreadableReason` is logged as its enum name.
