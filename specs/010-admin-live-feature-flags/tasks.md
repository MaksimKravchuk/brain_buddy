## Lane A — the durable runtime store, SQLite-exclusive, migration transactional (010-FR-001, 004, 005; DD-15)

- [ ] **A1** RED `backend/tests/test_feature_flag_repository.py`: after construction on a **fresh** data directory (no legacy JSON, no environment overrides), the repository holds exactly three rows — one per managed flag, each `off` by default — and a migration-ledger marker; a mutation round-trips its mode and cohort. - [ ] **A2** RED same module: **atomicity/idempotence** — a mutation whose transaction fails before commit leaves the previous committed rows unchanged and readable; repeating any mutation leaves the rows unchanged and still reports success; no partial write is ever observable. *(010-FR-005, SC-005)*
- [ ] **A3** RED same module: **concurrency** — N threads each mutating a *different* flag, and N threads adding *different* accounts to one flag, all survive; assert against the rows in the database. *(010-FR-005, SC-005)*
- [ ] **A4** RED same module: **degraded storage, post-migration invariant (DD-2)** — with migration already complete, an unreadable database, a database missing one managed flag's row, and a row whose `mode` is outside the known vocabulary each read as **degraded**; a mutation against any of them writes nothing; the healthy→degraded transition emits exactly one coarse WARNING and a repeated degraded read emits none; an injected `sqlite3.Error`/`OSError` on the read itself reads as the same degraded marker, refuses mutation, and emits the same WARNING shape once per transition. Assert the WARNING carries only a correlation id — no member data, no per-row detail. *(010-FR-004, SC-005, SC-008, DD-2)*
- [ ] **A5** RED same module: **migration preference rule, per flag (DD-15)** — with a legacy JSON overlay entry present and well-formed for `voice_brain_dump`, migration seeds that flag's row from it, ignoring a differing environment state for the same flag; with no legacy entry (or a malformed/absent legacy document), migration seeds from `config.feature_flags.states`, resolving `internal` to `selected_users` by resolving each configured internal-user email through the injected resolver and **skipping** an email that does not resolve; `external_agent_relay` is seeded from the environment even when a legacy JSON document happens to hold a key for it (the pre-correction overlay never wrote that flag, so migration must not read it there). *(010-FR-001, DD-15)*
- [ ] **A5a** RED same module: **migration transactionality and restart-idempotence (DD-15)** — a second construction over an already-migrated data directory is a no-op (no ledger duplicate, rows unchanged) even when the legacy JSON/environment inputs are then edited; a construction whose migration transaction is forced to fail before commit leaves no ledger row and no flag rows, and the legacy JSON file (when present) byte-identical to before the attempt; a subsequent construction without the injected failure then migrates successfully exactly once. *(010-FR-001, 004, DD-15)*
- [ ] **A6** RED same module: **purge scrub across exactly the three managed flags (DD-9)** — `scrub_user(account_id)` removes that ID from each managed flag's `selected_users` set, leaving every other flag's row unchanged; idempotent, including for an ID never present.
