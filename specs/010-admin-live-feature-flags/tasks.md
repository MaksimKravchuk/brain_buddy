# Tasks: Live Feature-Flag Management in the Admin Portal

Grouped into **independently acceptable lanes**, each with its own RED → GREEN ordering and its own evidence checkpoint. See [plan.md](plan.md) for why each exists, [design.md](design.md) for the `F-01`…`F-13` states lanes D and E realize, and [spec.md](spec.md) for the derived decisions DD-1…DD-13.

This list covers **exactly** the ten functional requirements and eight success criteria in [spec.md](spec.md) — see [review-history.md](review-history.md) for the review record and [analysis.md](analysis.md) for the per-requirement trace. There is no lane for a reset command, a cohort sweep beyond the one purge integration DD-9 requires, a privacy-policy rewrite, a new audit schema/store/UI, or a deploy/CI/script change — all are out of scope by spec.md.

Everything here is **runtime-neutral**: no task requires Hermes, a Kanban runtime, or any other control plane (ADR-0010, ADR-0011).

**Nothing is ticked, and that is accurate.** No lane has been started. Tick a box only when the tree actually contains the work and its checkpoint has run green.

**Lane dependencies.** Lane B needs lane A's repository. Lane C needs lane B's service. Lanes D, E and F need C's routes or B's service and are otherwise independent of each other. Lane G is documentation and can run at any point. Lane H is last by construction.

Every test named below must carry the **feature-qualified** requirement id (`010-FR-001`, or `010_FR_001` in a Python name) in its function name, docstring or Allure story, so `python3 scripts/check_requirement_coverage.py specs/010-admin-live-feature-flags` can trace it. A bare `FR-001` is rejected. Every test must also satisfy the Allure taxonomy (`epic`/`feature`/`story`, a human title, at least one named step) per `docs/test-allure-taxonomy.md`.

## Lane A — the durable runtime store (010-FR-001, 004, 005)

- [ ] **A1** RED `backend/tests/test_feature_flag_repository.py`: a document written through the repository round-trips its modes and cohorts; a never-written data directory reports the **healthy** empty overlay (DD-2), not raising or degraded, under `{data_dir}/feature-flags/runtime.json`. Unit-level round-trip only — the process-restart half of SC-001 is proven at the application boundary by **C7**, not here. *(010-FR-001, 005)*
- [ ] **A2** RED same module: **atomicity/idempotence** — a mutation that raises between the temporary write and the rename leaves the previous document byte-identical and readable; repeating any mutation leaves the document byte-identical and still reports success; no partial write is ever observable. *(010-FR-005, SC-005)*
- [ ] **A3** RED same module: **concurrency** — N threads each mutating a *different* flag, and N threads adding *different* accounts to one flag, all survive; assert against the document on disk. *(010-FR-005, SC-005)*
- [ ] **A4** RED same module: **healthy-absence vs. degraded-corruption, and forward compatibility (DD-2, DD-8)** — absence reads healthy and a mutation against it creates the file; a truncated, syntactically invalid, or non-object-top-level document each reads as **degraded**, and a mutation against any of them writes nothing; the healthy→degraded transition emits exactly one coarse WARNING and a repeated degraded read emits none; an undeclared-flag entry, a declared-but-unmanaged-flag entry, and an unrecognized field inside a managed entry are ignored for evaluation/`describe()` but survive a later mutation to a different flag byte-identical; a managed entry's out-of-vocabulary `mode` value reads as **degraded**, not preserved. Separately, an injected `OSError`/`PermissionError` on the read itself reads as the same degraded marker, refuses mutation, and emits the same WARNING shape once per transition. Assert the WARNING carries only correlation id, coarse reason band and affected-override count — no member data. *(010-FR-004, SC-005, SC-008, DD-8)*
- [ ] **A5** RED same module: **clearing an override** — `clear(flag)` removes the entry entirely; evaluation afterward matches the environment-only answer exactly (incl. `internal`); clearing a flag with no entry is a no-op that still reports success; clearing does not touch any other flag's entry or a DD-8-preserved unknown entry. *(010-FR-003, 005, DD-3)*
- [ ] **A6** RED same module: **purge scrub, widened to every parseable cohort (DD-9)** — `scrub_user(account_id)` removes that ID from every managed flag's `selected_users` set **and** from a `selected_users` array inside any other parseable entry, leaving the rest of that entry byte-identical; idempotent, including for an ID never present. Against a **degraded** document, `scrub_user` raises rather than silently completing or skipping, so the caller (Lane C's `AccountService.purge_account`) can enforce DD-13's fail-closed ordering. *(010-FR-001, 007, DD-8, DD-9, DD-13)*
- [ ] **A7** RED same module: **document-shape privacy** — the write path has no field, parameter or code path that can place an email, display name, credential, token or session-hash fragment into the document, asserted at the schema/shape level. The *request-to-document* sentinel proof is **C8**, not here, since it needs the real account-lookup path Lane C introduces. *(010-FR-001, SC-007)*
- [ ] **A8** GREEN `backend/app/repositories/feature_flag.py` — `FeatureFlagOverrideRepository` with `read()`, `mutate(fn)`, `clear(flag)`, `scrub_user(account_id)`. `mutate`/`clear` take an advisory `fcntl.flock` on `runtime.json.lock`, re-read under the lock, apply the pure function to the known portion while carrying the unknown portion through unchanged (DD-8), commit through `atomic_write`. `scrub_user` walks every parseable entry's `selected_users` array (DD-9), raising when `read()` reports degraded (DD-13). Make A1–A7 pass.
