# Feature Specification: Live Feature-Flag Management in the Admin Portal

**Feature Branch**: `feat/010-admin-live-feature-flags` · **Created**: 2026-08-14 · **Founder-corrected**: 2026-08-15
**Status**: Planning, not implemented. Founder-accepted after two review campaigns, both `product-decision-required` — see [review-history.md](review-history.md) for the full record, the original founder-acceptance, and the 2026-08-15 founder correction that supersedes DD-1 through DD-4 and DD-8 through DD-10, DD-12 below. [analysis.md](analysis.md) has per-requirement traceability.
**Input**: see [intake.md](intake.md) for the founder's original ask, verbatim, and [review-history.md](review-history.md)'s Founder correction section for the 2026-08-15 bounded correction to it.

**2026-08-15 founder correction, in one paragraph:** the durable store moves from a JSON document overlaying an environment baseline to **SQLite as the sole source of truth** for three runtime-manageable flags — `voice_brain_dump`, `mobile_task_classification`, and now `external_agent_relay` too. There is no more environment fallback, no more "deploy default" inheritance, and no more clear-override action after a one-time, transactional, restart-idempotent migration runs: every managed flag always has an explicit SQLite row. `admin_portal` is deleted outright as a feature flag everywhere — config, gates, tests, docs, the staged deploy env string — because the Admin Portal is key functionality that must always be reachable by an authenticated, allow-listed operator, never behind a flag that could lock the only operator out. `delivery_canary` is untouched: still a separate, environment/deploy-owned release-smoke input, never runtime-manageable. See [ADR-0019](../../docs/decisions/0019-sqlite-runtime-feature-flag-store.md), which narrows [ADR-0018](../../docs/decisions/0018-runtime-feature-flag-overlay.md) exactly as ADR-0018 itself narrowed ADR-0017, and DD-14/DD-15/DD-16 below.

A second section on the existing `/admin` screen lets an already-authorized operator put each **runtime-manageable** flag into exactly one of three modes — OFF, ON, SELECTED_USERS — and, in SELECTED_USERS mode, add or remove individual accounts found by the exact-match lookup feature 009 already ships. The chosen state is written to one SQLite database on the existing backend data volume — the sole source of truth for these three flags — and is picked up by an already-open browser session within about fifteen seconds without a sign-out.

Nothing about feature 009's authorization or privacy contract changes for account lookup and session revoke: the same session cookie, the same server-owned operator allow-list, the same deny-before-touch precedence. What **does** change, by the 2026-08-15 correction: `/admin` is no longer gated by an `admin_portal` rollout flag at all — it is always available to an authenticated operator on the allow-list (DD-14). This feature adds one narrow audit obligation (DD-10) and one narrow purge obligation (DD-9), unchanged in spirit from the original review findings. Review also found the founder's "already-open session" requirement had been specced web-only when the brief is client-generic; the bounded mobile sublane (FR-009, Lane E) corrects that to match the brief, not new scope, and is untouched by the 2026-08-15 correction.

**Scope is frozen at the founder's slice, as narrowed and corrected by the owner decisions below (including the 2026-08-15 correction).** The requirements after those decisions are the whole feature. A reviewer proposal for adjacent hardening — percentage rollout, new roles, an audit store/UI, a generalized migration framework, websockets/SSE, deployment redesign — is out of scope by construction, not by argument.

SQLite's `feature_flags` table has a fixed, three-row schema this feature alone owns; there is no shared-file forward-compatibility surface left to preserve, and no code path can even construct a row naming a fourth flag (`MANAGED_FLAGS` is a closed three-name tuple enforced by the schema and by `_require_managed`). Documentation edits, all narrowly named: one `docs/data-retention.md` retention-table row plus one export-exclusion line naming the runtime store; the existing Admin access records section amended to also name this feature's own log records under 009's identical disposition (platform log window, excluded from export, not reached by purge); one bullet in `docs/auth.md`'s operator-authority list, pointing at ADR-0019; and one authorized text-only sentence under `frontend/src/pages/PrivacyPolicyPage.tsx`'s "How long we keep it" (it holds only your account id, is scrubbed on account purge, and is excluded from your data export), plus the routine `LAST_UPDATED` bump — no other privacy-policy surface changes (FR-007, SC-007). |
| DD-10 | Are operator mutations and the cohort-resolving read actually logged today? | **Not until this feature adds it, and "exactly one" record means exactly one *new* record, not the whole log-line count for an operation.** Feature 009's `find_account` "Admin lookup" record and its `revoke_sessions` record do not fire for a flag-mode change, a cohort add/remove, or the `GET`'s bulk account-to-email resolution. No email or display name in any of these records, and no new audit store, history API, UI or schema (FR-006, SC-006). |
| DD-11 | Can the 15-second background poll reuse `useAuthStore.hydrate()` unchanged? | **No.** Today's `hydrate()` clears the session to anonymous on *any* thrown failure, including a transient network error, which would turn ordinary poll noise into an unwanted sign-out — the opposite of FR-009. The background poll uses a distinct `refreshSession()` path: a transient (non-401) failure leaves the authenticated session, its user record and its flags untouched and surfaces nothing; a 401 clears the session and stops polling exactly as today. `hydrate()`'s existing behavior for **initial/startup** load — any failure, transient or not, resolves to anonymous — is unchanged, because a cold load against an unreachable backend must not hang on "loading" forever (FR-009, SC-004). Untouched by the 2026-08-15 correction. |
| DD-12 | Which mutations require the lightweight confirmation step, and by what rule? | **An exact operation allowlist, not a computed population-effect rule — superseded 2026-08-15: now two operations, not three.** Confirmation is required for exactly two named operations: **setting a flag OFF, and removing the last remaining SELECTED_USERS member.** ("Clearing a runtime override" is gone with DD-3/DD-15 — there is no more override to clear.) Every other mutation (ON, SELECTED_USERS, adding a user, removing a non-last member) applies immediately. This is deliberately narrower than "every mutation that could reduce exposure" — a computed rule is unenforceable server-side against concurrent edits from two tabs — and a stale-tab race between two operators can still zero a population without either tab's confirm firing, an accepted residual because every mode change is reversible by its own inverse (FR-010). |
| DD-13 | What does account purge do when the runtime store is degraded (unreadable or malformed)? | **Halt and retry — GDPR erasure never completes with a purged ID still readable in the store, and the account is retained, not deleted, until the store is repaired.** `scrub_user` cannot safely mutate a store it could not read, so it raises rather than silently skipping when the store is degraded; `AccountService.purge_account` aborts **before** `user_repo.delete` — the account, its email and its password hash are retained past the documented 14-day promise for as long as the store stays corrupt, and the 60-second maintenance sweep retries the purge on every pass until an operator repairs the store and a subsequent attempt succeeds. `AccountService.purge_due_accounts` MUST isolate this failure per account — a single corrupt runtime store must not also block every other unrelated account's due purge in the same sweep pass (FR-004, FR-007, DD-2, DD-9). |

The Admin Portal is key functionality: an authenticated operator on the server-owned allow-list (feature 009's `require_operator` — valid session AND allow-list membership, deny-before-touch, unchanged) always reaches `/admin`. This closes the original DD-1's self-lockout concern structurally rather than by exclusion — there is no flag left that could lock the only operator out — and changes no navigation: 009 PD-1 still holds, `/admin` is reached only by typing the URL (FR-002, FR-006). |
| DD-15 | *(New 2026-08-15)* What replaces the JSON-overlay-plus-environment-baseline architecture, and how does the one-time migration work? | **SQLite is the sole source of truth for the three managed flags, populated once by a transactional, restart-idempotent migration; there is no runtime fallback afterward.** One `feature_flags` table in the existing repository's SQLite database always holds exactly three rows after migration — one per managed flag — each an explicit `mode` plus its `selected_users` set. The migration runs once, guarded by a ledger row in the same transaction pattern `TaskRepository._migrate_legacy_json_once` already uses in this codebase (`BEGIN IMMEDIATE`, seed rows plus the ledger row committed together, rollback on any failure): per flag, the pre-correction JSON overlay's entry wins when it is present and well-formed **and** the JSON overlay ever covered that flag (`voice_brain_dump`, `mobile_task_classification` only — the pre-correction overlay never wrote `external_agent_relay`); otherwise the environment baseline supplies it, with an `internal` stage resolved to `selected_users` by looking up each configured internal-user email's current immutable account id — an email that does not currently resolve is **skipped, not substituted**, so migration can only narrow a cohort relative to the old INTERNAL-stage behavior, never broaden it. `external_agent_relay` always comes from the environment baseline (never the legacy JSON, which never wrote it). The legacy JSON file and the environment variables are never deleted, renamed or mutated by migration — a failure before the migration transaction commits leaves neither a ledger row nor partial flag rows, and the legacy inputs untouched, so a retried process restart migrates cleanly. After a successful migration, normal reads and writes **never** consult the environment or the JSON file again; a store that cannot be read is degraded (DD-2), never silently reconstructed from either legacy source. `BRAIN_BUDDY_FEATURE_FLAGS`/`BRAIN_BUDDY_FEATURE_FLAG_INTERNAL_USERS` stop being runtime sources for these three flags the moment migration compatibility is complete; any read of them for these three flags is isolated inside migration code, never inside the normal resolver (FR-001, FR-003, FR-004). |
| DD-16 | *(New 2026-08-15)* `external_agent_relay` is now runtime-manageable — how does that interact with `container.py`'s construction-time secret-box decision? | **Rollout state and capability are two separate axes; both must be favorable for the flag to be effective, and the construction-time decision itself is untouched.** SQLite governs *rollout* (is this flag ON/OFF/SELECTED_USERS for this user) exactly like the other two managed flags. `_build_agent_secret_box`'s decision — whether a real secret box or the fail-closed `_UnavailableRelaySecretBox` placeholder is wired at container construction — stays a one-time, construction-only decision; it is not redesigned into a live, re-enterable check. The service combines the two: a user's effective `external_agent_relay` is the SQLite rollout answer **AND** the capability being available, so a runtime ON can never expose the relay when no secret box was actually constructed, and a configured capability with a SQLite OFF/non-matching-cohort answer stays fail-closed exactly as before. `_build_agent_secret_box`'s own decision of whether it is safe to build the placeholder (no `BRAIN_BUDDY_AGENT_RELAY_KEYS`, production, no existing relay data) now reads the flag's *rollout mode* from SQLite instead of the retired environment baseline, treating a degraded read conservatively (as "not confirmed OFF", forcing real keys to be required) rather than granting the placeholder shortcut on an unreadable store (FR-002, FR-008). |

## User Scenarios & Testing

The "user" for stories 1–3 is an authorized operator, authenticated exactly as feature 009 requires. Story 4's user is an ordinary member with a browser tab already open. See [design.md](design.md) for the screen and its states.

### User Story 1 - Operator sets a flag's mode (Priority: P1)

An operator opens `/admin`, sees each of the three managed flags with its current mode — the SQLite row is the sole source of truth, so there is nothing else to show it came from — and switches one flag between OFF, ON and SELECTED_USERS. The change is saved server-side and the operator's view is refreshed from the server's own answer, not from optimistic local state.

**Why this priority**: without it there is no live rollout control at all; every other story builds on the stored mode.

**Independent Test**: on a data volume with no runtime document yet, set a flag to ON, read the flag list back, restart the backend process, read it back again — the document now exists, the mode is still ON, and no other flag moved.

**Acceptance Scenarios**:

1. **Given** the one-time migration has run, **When** the operator sets a flag to ON, **Then** its SQLite row is updated, the response reports mode ON for that flag, every other flag is unchanged, and a later read returns the same state (DD-2, DD-15).
2. **Given** a flag set to ON at runtime, **When** the backend process is restarted, **Then** the flag is still ON.
3. **Given** a flag set to OFF at runtime, **When** any member's effective flags are computed, **Then** the flag is not effective for anyone — there is no environment baseline left to fall back to (DD-3, DD-15).
4. *(Retired 2026-08-15)* There is no more "Use deploy default" action; DD-3/DD-15 remove clearing and inheritance entirely.
5. **Given** a save that fails server-side, **When** the operator retries, **Then** the operator sees an error state carrying the correlation ID and the stored state is unchanged.

### User Story 2 - Operator manages a SELECTED_USERS cohort (Priority: P1)

With a flag in SELECTED_USERS mode, the operator adds an account by typing its exact account ID or canonical email, and removes an account from the list shown on screen. The cohort is retained if the operator later moves the flag to OFF or ON, and reappears exactly as it was if the flag returns to SELECTED_USERS.

**Why this priority**: per-flag cohorts are what the shared global `BRAIN_BUDDY_FEATURE_FLAG_INTERNAL_USERS` list cannot express, and what makes SELECTED_USERS different from ON.

**Independent Test**: add one account to one flag, confirm the count and row appear and a second flag's cohort is unchanged, remove the account, confirm the count returns to zero, then switch the flag to ON and back to SELECTED_USERS and confirm the (still empty) cohort state is unchanged by the round trip.

**Acceptance Scenarios**:

1. **Given** a flag in SELECTED_USERS mode, **When** the operator adds an existing account by exact canonical email, **Then** it appears in the list, the count increments, and adding it again changes nothing and still reports success.
2. **Given** the same flag, **When** the operator submits a prefix, suffix, case variant or whitespace variant of a real account ID or email, **Then** nothing is added and the operator is told no account was found.
3. **Given** an account in a flag's list, **When** the operator removes it, **Then** it disappears from that flag only, and removing it again — or removing an ID never in the cohort, or one that no longer resolves — still reports success (DD-7).
4. **Given** a selected account that has since been deleted, **When** the operator opens the list, **Then** the row still renders with its stored ID and is still removable, until `AccountService.purge_account` removes the ID from the cohort entirely (DD-9).
5. **Given** a flag in SELECTED_USERS mode with a non-empty cohort, **When** the operator switches it to OFF or ON, **Then** the cohort and its count are retained and reappear unchanged if the flag returns to SELECTED_USERS (DD-6).
6. **Given** a flag currently OFF or ON, **When** an add or remove request is made against it, **Then** it is refused (DD-6).

### User Story 3 - The rollout survives restart and redeploy, and migrates safely exactly once (Priority: P1)

The operator's changes persist across a process restart and an image swap. The one-time migration from the pre-correction JSON overlay and the environment baseline into SQLite is transactional and restart-idempotent, and never loses or silently reconstructs state.

**Why this priority**: a rollout control whose state a redeploy silently discards is worse than no control, and a migration that can partially apply or double-apply is worse than the architecture it replaces.

**Independent Test**: seed a legacy JSON overlay and an environment baseline, construct the repository, and confirm the SQLite rows match DD-15's per-flag preference rule and a migration-ledger marker is present. Restart with the legacy inputs changed and confirm SQLite remains authoritative (the legacy inputs are no longer consulted). Inject a failure before the migration transaction commits and confirm no ledger row, no partial flag rows, and the legacy JSON file untouched; retry and confirm it then succeeds. Separately, reopen the same data directory through a fresh application/container instance after a successful migration and confirm the stored state is still in force.

**Acceptance Scenarios**:

1. **Given** a completed migration on the data volume, **When** the backend restarts as a fresh process/application instance over the same data directory, **Then** the stored modes and cohorts are still in force and migration does not run again (the ledger marker short-circuits it).
2. **Given** a legacy JSON overlay entry for `voice_brain_dump` or `mobile_task_classification` and a differing environment baseline for the same flag, **When** migration runs, **Then** the legacy JSON entry wins for that flag; **given** an environment `internal` stage with configured internal-user emails, **When** migration runs, **Then** each email that currently resolves to an account becomes a `selected_users` entry by immutable account id, and an email that does not resolve is skipped, never substituted (DD-15).
3. **Given** the migration transaction fails after seeding some flag rows but before commit, **When** the process is inspected, **Then** no migration-ledger row and no partial flag rows exist, and the legacy JSON file is byte-identical to before the attempt; **When** the repository is constructed again without the injected failure, **Then** migration completes successfully and exactly once.
4. **Given** a SQLite store that cannot be read, or that is missing a managed flag's row, or whose stored `mode` is outside the known vocabulary, **When** flags are evaluated, **Then** every flag resolves to ineffective, degradation is visible to the operator, every mutation is refused, and exactly one coarse WARNING log record marks the transition (DD-2).

### User Story 4 - A signed-in member picks the change up without signing out (Priority: P2)

A member has a session already open — a browser tab, or the mobile app foregrounded or backgrounded. An operator changes a flag that affects them. Within about fifteen seconds — or immediately on returning to the tab or foregrounding the app — the gated capability appears or disappears, without a sign-out, reload or force-quit, and an ordinary network blip during the background refresh never signs them out either. The requirement is client-generic — "an already-open session" is what the founder's brief asks for, not "the web tab" — so it applies to both clients this feature's flags reach (FR-009, Lane E, Mobile E in tasks.md).

**Why this priority**: it is the point of "live", but strictly downstream of stories 1–3.

**Independent Test**: with fake timers, assert the web client refetches `/api/auth/me` on the 15-second interval while authenticated, on window focus and on visibility change, and that the auth store's flags update from the response. Separately, with fake timers and a faked `AppState`, assert the mobile `SessionProvider` issues the equivalent refetch on the same cadence while signed in and active, and immediately on foreground.

**Acceptance Scenarios**:

1. **Given** an authenticated web session, **When** fifteen seconds elapse, **Then** the client refetches `/api/auth/me` and applies the returned flags.
2. **Given** an authenticated web session in a background tab, **When** the tab becomes visible or the window regains focus, **Then** the client refetches immediately.
3. **Given** an unauthenticated visitor, **When** any amount of time elapses, **Then** no polling request is issued at all.
4. **Given** an authenticated session whose background refetch fails transiently, **When** the failure arrives, **Then** the session, user and flags are untouched and nothing is surfaced; a 401 on that same refetch clears the session exactly as today's initial hydration does on any failure, and polling stops (DD-11).
5. **Given** a signed-in mobile session in the foreground, **When** fifteen seconds elapse, **Then** `SessionProvider` refetches `/auth/me` and the resolved `taskClassificationEnabled`/`voiceEnabled` values update; a transient failure leaves the session and flags untouched and polling continues; a 401 signs out exactly as an in-app 401 does today; backgrounding suspends the poll, and returning to foreground triggers an immediate refetch.

### Edge Cases

- Migration has not yet run when the repository is first constructed on a fresh volume: it runs once, transactionally, seeding all three managed flags before any request is served; a second construction (a process restart) is a no-op because the ledger marker is already present (DD-15).
- Migration fails after seeding some rows but before its transaction commits: no ledger row and no partial flag rows exist afterward, and the legacy JSON/environment inputs are untouched; a later retry (the next process start) migrates cleanly (DD-15).
- A previously healthy SQLite store becomes unreadable, loses a managed flag's row, or a row's `mode` value is outside the known vocabulary: every flag resolves to ineffective, every mutation is refused, and exactly one coarse WARNING log record marks the transition (DD-2). There is no environment baseline left to fall back to.
- Two operators (or one in two tabs) mutate different flags at the same moment: both changes survive; neither write is partial (SQLite transaction isolation).
- The backend is killed mid-transaction: the previous committed state is intact and readable; SQLite's own atomic commit means there is no separate temp-file/rename step to reason about.
- An account in a SELECTED_USERS list is deleted: until purge (end of the 14-day grace), its ID stays in the store, the row renders unresolved, and it remains removable — a stale ID grants nothing, since resolution matches the *authenticated* user's ID. Purge removes the ID from every cohort (DD-9).
- A flag is set to SELECTED_USERS with an empty cohort: off for everyone, and the screen says so rather than showing an ambiguous blank.
- A flag leaves SELECTED_USERS mode with a non-empty cohort: retained, count stays visible, reappears unchanged on a return to SELECTED_USERS (DD-6).
- *(Retired 2026-08-15)* There is no more "clear override" action and no retained-cohort-on-clear question — DD-3/DD-15 remove the concept entirely.
- An add or remove request targets a flag currently OFF or ON: refused (DD-6).
- *(Retired 2026-08-15)* There is no more free-form document content to preserve or ignore — SQLite's `feature_flags` table has exactly three rows, one per managed flag, and no code path can construct a fourth (DD-8, DD-15).
- An account selected on a flag is purged while the store is healthy: `scrub_user` removes the ID from every managed flag's cohort before the account record is deleted. If the store is degraded when the purge runs, it halts before deleting the account record and retries on the next 60-second sweep; other accounts' due purges in the same sweep are not blocked (DD-13).
- An operator turns off the flag gating a capability a member is mid-way through: nothing already dispatched is cancelled; existing per-feature rules stand.
- A malformed mode or an unknown/deleted flag name (including `admin_portal`, which is no longer a name at all) in any mutation: refused with an actionable error, no partial write. An unknown account ID: refused when adding; idempotently succeeds when removing (DD-7).
- `external_agent_relay` is set to ON or a matching SELECTED_USERS cohort at runtime, but the construction-time relay capability (secret box) was never configured: the flag stays ineffective for every user — rollout alone never overrides a missing capability (DD-16).
- A signed-in mobile session is backgrounded when a flag affecting it changes: the poll is suspended while inactive, and foregrounding triggers an immediate refetch (User Story 4, Mobile E). Untouched by the 2026-08-15 correction.
- An authenticated, allow-listed operator visits `/admin`: it is always reachable — there is no flag left that could hide it (DD-14).

## Requirements

### Functional Requirements

- **FR-001**: The system MUST hold runtime rollout state in exactly one server-owned SQLite database on the existing backend data volume, in one `feature_flags` table recording for each **runtime-manageable flag** (`voice_brain_dump`, `mobile_task_classification`, `external_agent_relay` — DD-1, DD-15, DD-16) a mode of `off`, `on`, or `selected_users`, and — for `selected_users` — a set of immutable account IDs. The store MUST NOT contain email addresses, display names, credentials, tokens, session hashes, or any member content (DD-5). A **one-time migration** MUST populate the store transactionally and restart-idempotently from the pre-correction JSON overlay and the deploy-staged environment baseline exactly as DD-15 states: the legacy JSON wins per flag where it already covered that flag and holds a well-formed entry; otherwise the environment baseline supplies it, resolving an `internal` stage to `selected_users` by looking up each configured internal-user email's current account id and skipping (never substituting) an email that does not resolve; `external_agent_relay` always comes from the environment baseline, never the legacy JSON. Migration MUST NOT delete, rename or mutate the legacy JSON file or the environment configuration, and MUST fail closed — no ledger marker, no partial rows — if the migration transaction cannot commit, retrying cleanly on the next process start. After migration succeeds, normal reads and writes MUST NOT consult the environment or the legacy JSON again (FR-004).
- **FR-002**: Runtime management MUST be scoped to exactly `voice_brain_dump`, `mobile_task_classification` and `external_agent_relay`. A mutation naming any other name — including `delivery_canary`, or an undeclared name — MUST be refused without writing anything, and the refused flag's effective value MUST remain exactly what the environment configuration produces. `admin_portal` is not merely refused: it MUST NOT exist as a configurable flag name anywhere in the system (config, gates, tests, docs, the deploy-staged env string — DD-14), so a mutation naming it fails the same generic "undeclared name" refusal any other unknown string would (DD-1).
- **FR-003**: Effective-flag evaluation MUST be per flag and MUST resolve **exclusively** from that flag's SQLite row — there is no environment baseline left to blend with or fall back to after migration (DD-15). `on` is effective for every authenticated user, `off` for none, `selected_users` exactly for the users in that flag's set. There is no "clear override"/"use deploy default" operation and no inheritance state (DD-3).
- **FR-004**: After a successful one-time migration (FR-001), the system MUST treat a **readable store holding a well-formed row for each of the three managed flags** as healthy. The system MUST treat anything else — the database unreadable, a managed flag's row missing, or a row's stored `mode` outside its known vocabulary — as **degraded**: every flag resolves to ineffective (never silently reconstructed from any other source), the operator screen MUST surface the degraded state, every mutation MUST be refused rather than overwriting or reconstructing the store, and the transition from a healthy read to a failed one MUST emit exactly one coarse WARNING log record (correlation id only, no member data) rather than one per subsequent read. This applies identically to a process whose very first read after startup is already degraded — the in-process "was the last read healthy" state starts unset, not healthy, so that first degraded read also emits the WARNING exactly once (DD-2). `AccountService.purge_account`'s mutation MUST be refused by this rule exactly like every other mutation while the store is degraded — see DD-13 for the resulting purge disposition, a narrow named exception, not a contradiction. No further recovery, repair or reset machinery is part of this feature.
- **FR-005**: Every mutation MUST be a targeted, idempotent operation: set one flag's mode, add one account to a `selected_users` cohort, or remove one account from a `selected_users` cohort — applied as a read-modify-write inside one SQLite transaction. Add and remove MUST be accepted only while the named flag's current mode is `selected_users`; refused against `off`/`on` (DD-6). A flag's `selected_users` set MUST be retained, not cleared, when its mode changes to `off` or `on`, and MUST still be counted and shown while inactive, so a later switch back to `selected_users` reactivates exactly the retained cohort (DD-6). Concurrent mutations to different flags MUST all survive; a crash at any point MUST leave either the prior committed state or the new one, never a partial one; repeating any mutation MUST be a no-op that still reports success. Runtime state MUST survive a backend process restart, a machine restart, and a deploy that swaps the image. Reads MUST always reflect the database's current committed state, so a mutation is visible to the very next effective-flag evaluation with no separate cache to invalidate.
- **FR-006**: The Admin Portal is key functionality and MUST always be reachable by an authenticated operator on the server-owned allow-list — there is no flag gating it (DD-14). All **four** runtime flag routes — the one `GET` read and the three mutations (set mode, add account, remove account) — MUST sit behind feature 009's operator-authorization gate (a valid session AND operator allow-list membership, in that precedence), with an unauthenticated caller getting 401 and an authenticated non-operator 403, and with no repository read and no write as a side effect of any denial on any of the four, including `GET`. Flags MUST remain exposure control and MUST NOT become authorization: no authorization decision may read a runtime-managed flag, and the operator allow-list stays environment-owned, preserving 009-FR-001, 009-FR-002 and 009-FR-008 exactly (009-FR-013's `admin_portal` gate is retired by DD-14). Every operator mutation MUST emit exactly one new, dedicated, content-free log record — operator id, flag name, action, the target account id when the operation names one, and outcome — **in addition to**, not instead of, feature 009's `find_account` "Admin lookup" record, which still fires unconditionally for a successful add because FR-007 requires add to go through it (DD-10); every `GET` that resolves cohort account IDs to canonical emails MUST emit exactly one aggregate record — operator id, flag count and resolved-account count — with no email or display name in any of these records, and no new audit store, history API, UI or schema (DD-10).
- **FR-007**: Adding a selected user MUST use the exact-match account lookup feature 009 already enforces: exactly one of an immutable account ID or a canonical email per request, matched byte-for-byte, with no partial, prefix, suffix, case-variant, whitespace-variant or fuzzy match, and no listing, enumeration or search endpoint. An add that does not resolve to exactly one existing account MUST be refused and MUST add nobody. Removing a selected user MUST be idempotent by stored account ID: it MUST succeed whether or not that ID currently resolves to an account or is currently present in the cohort, including a second removal of the same ID (DD-7). Only the resolved account ID is stored. A stored ID that no longer resolves MUST still be rendered and removable, until `AccountService.purge_account` removes it from every managed flag's cohort as part of that purge, mirroring `InviteRepository.scrub_user`, invoked before any destructive step of the purge, and failing the whole purge closed (before the account record is deleted) rather than skipping the scrub when the store is degraded (DD-9, DD-13). The documentation this feature edits is exactly what DD-9 names — no broader privacy-policy rewrite or user-facing-summary redesign is in scope.
- **FR-008**: Every existing backend feature-flag check for `voice_brain_dump`, `mobile_task_classification` and `external_agent_relay` MUST resolve through the runtime resolver — named exhaustively: `_me_response` (`auth.py`), `voice_brain_dump_enabled`/`require_voice_brain_dump_enabled` and `external_agent_relay_enabled`/`require_external_agent_relay_enabled` (`dependencies.py`), `_voice_enabled_for_owner` (`container.py`), the direct `voice_brain_dump_enabled(current_user, config)` call inside `command_brain_dump_operation` (`backend/app/api/tasks.py`) that gates the brain-dump command route's forward actions (`commit`, `retry`, `review_provisional`), and every relay route depending on `require_external_agent_relay_enabled` in `backend/app/api/agents.py` — plus the member-facing effective booleans for all three flags in the `/api/auth/me`, `/api/auth/login` and `/api/auth/signup` payloads, so the server stays the sole authority for whether any of the three is effective. `external_agent_relay`'s effective value MUST additionally require the construction-time relay capability (whether a real secret box was wired, never re-evaluated per request) to be available, combined by AND with the SQLite rollout answer, fail-closed on either being unfavorable (DD-16); the secret-box construction/provider infrastructure itself is untouched. `delivery_canary` MUST remain purely environment-derived and untouched. The `feature_flags` key set MUST remain exactly `KNOWN_FEATURE_FLAGS`, and no other member-facing route, response shape, status code, cookie or screen may change — the mobile client requires no change to keep working against the same payload. A runtime override on `voice_brain_dump` MUST NOT move the consent boundary ADR-0002/constitution Principle I already draws: a caller newly admitted by a `selected_users` cohort still MUST fail visibly without explicit per-recording consent, and a caller under a runtime OFF override MUST still reach the owner-authority voice routes (withdraw consent, cancel, delete raw audio) exactly as today.
- **FR-009**: While a session is authenticated, the client MUST refetch its identity-and-flags endpoint every 15 seconds and immediately on returning to the foreground, and MUST apply the returned flags to local state so a gated capability appears or disappears without a logout, login, page reload or app restart. This requirement is client-generic — it applies to the web frontend and the mobile app alike — and each client realizes it through its own idiom: the **web** frontend MUST refetch `GET /api/auth/me` every 15 seconds and immediately on window focus or the document becoming visible, through a session-refresh path distinct from the app's initial/startup hydration (a transient, non-401 failure MUST leave the session, user and flags untouched and surface no error; a 401 MUST clear the session and stop polling; initial/startup hydration behavior is unchanged, DD-11); the **mobile** app's `SessionProvider` MUST refetch `/auth/me` every 15 seconds while signed in and `AppState` is active, and immediately on returning to foreground, with the identical transient-tolerant/401-clearing split. Polling MUST NOT run while unauthenticated, or, on web, while the document is hidden, or, on mobile, while the app is backgrounded, and MUST NOT introduce a WebSocket, an SSE stream, or any other new transport on either client. Untouched by the 2026-08-15 correction.
- **FR-010**: The operator screen MUST display, for each of the three managed flags: its current mode — always present, never null (there is no more inheritance state, DD-3) — as a native `fieldset`/`legend` grouped radio control with exactly one of the three radio inputs checked, matching the stored `mode`; the selected-user count, shown and retained even in OFF/ON mode (DD-6); and a list with enough identity per row — including a "Remove" action whose accessible name includes the row's account identity — with focus moved to a defined target after **any** mutation succeeds: the triggering control (the mode radio or the add-user input) for a mode change or add, and the next remaining row's Remove action — or the add-user input, or the cohort-count region — for a row removal. It MUST express distinct loading, saving, empty-cohort, not-found/unresolvable, degraded-store, list-fetch-failure (distinct from a successful `degraded: true` response) and mutation-error states, each error state carrying the correlation ID when supplied and named fallback copy when not. It MUST require one lightweight confirmation step before exactly two mutations — setting a flag to OFF, and removing the last remaining SELECTED_USERS member — stated as this exact allowlist, not a claim it covers every population-zeroing mutation (DD-12); every other mutation applies immediately. The confirmation step MUST be dismissible by Escape, matching this screen's `RevokeConfirmDialog`/`Overlay` convention, and MUST receive focus on appearance and return focus to the opening control on Cancel or Escape. It MUST remain usable at a 390×851 viewport, with the mode control, cohort rows and confirmation controls stacking with a minimum 44px tappable height. After any mutation it MUST re-render from the server's authoritative response rather than optimistic local state.

### Key Entities

- **Runtime flag store**: one server-owned SQLite database on the data volume, holding one `feature_flags` table. For each of the three runtime-manageable flags: a mode (`off`\|`on`\|`selected_users`) and, for `selected_users`, a set of account IDs — always exactly three rows after the one-time migration (DD-15). Holds no member content, and no unrecognized/opaque content: the schema is fixed and owned solely by this feature (DD-8, retired).
- **Managed flag**: one of the three runtime-manageable flags, `voice_brain_dump`, `mobile_task_classification` and `external_agent_relay` (DD-1, DD-16) — a subset of `KNOWN_FEATURE_FLAGS`. Its effective value comes from its SQLite row exclusively; there is no environment fallback after migration. `delivery_canary` is the one `KNOWN_FEATURE_FLAGS` entry that is **not** a managed flag: always environment-derived. `admin_portal` is not a `KNOWN_FEATURE_FLAGS`/`PRIVATE_FEATURE_FLAGS` entry at all any more (DD-14).
- **Selected user**: an account ID present in one managed flag's set, retained across mode changes away from `selected_users` (DD-6). Rendered with the canonical email resolved live from the account record; never stored alongside the ID. Removed from every managed flag's set when the account is purged (DD-9).

## Success Criteria

### Measurable Outcomes

- **SC-001**: An operator can set each of the three managed flags to OFF, ON and SELECTED_USERS; every state reads back identically through the API and survives a backend process restart; no unmanaged flag and no other managed flag changes as a side effect of any mutation. *(Superseded 2026-08-15: no more "clear override to restore the deploy default" claim — DD-3, DD-15.)*
- **SC-002**: With `voice_brain_dump` in SELECTED_USERS mode and account A selected, `GET /api/auth/me` reports it `true` for A and `false` for B; after A is removed it reports `false` for A next response, with no session invalidated; after A is purged while the store is healthy, its ID is absent from the cohort; a purge attempted while degraded halts before the account record is deleted and succeeds, scrubbing the cohort, on a retried purge once repaired (DD-9, DD-13).
- **SC-003**: *(Superseded 2026-08-15: fallback parity is retired with the environment fallback itself — DD-2, DD-15.)* **Migration parity**: seeding a legacy JSON overlay entry, an environment `off`/`on`/`internal` state, and internal-user emails (some resolvable, some not), then constructing the repository, produces SQLite rows matching DD-15's per-flag preference rule exactly — legacy JSON wins for `voice_brain_dump`/`mobile_task_classification` when present and well-formed, the environment baseline otherwise, `internal` resolved to exactly the resolvable emails' account ids, `external_agent_relay` always from the environment. A second construction over the same data directory (a process restart) leaves the SQLite rows unchanged even when the legacy JSON/environment inputs are then edited — SQLite alone is authoritative from that point on.
- **SC-004**: An authenticated web session issues a `/api/auth/me` refetch once per 15-second interval, once on window focus and once on the document becoming visible, issues none while unauthenticated or hidden, opens no WebSocket or SSE connection, updates the rendered gated capability without a logout/login/reload, survives a transient background-refresh failure without signing the member out or altering stored state, and a 401 on that same path clears the session and stops polling exactly as today's initial hydration does on any failure (DD-11). Untouched by the 2026-08-15 correction.
- **SC-005**: Concurrent targeted mutations against different flags all apply; the store is never observed partially written; a transaction that fails before commit leaves the previous committed state valid and readable; repeating any mutation leaves the store's rows unchanged while still reporting success. *(Superseded 2026-08-15: no more "unrelated entry naming an undeclared flag" claim — DD-8 is retired, there is no such entry to preserve.)*
- **SC-006**: Every mutation naming `delivery_canary` or an undeclared name is refused and writes nothing; naming `admin_portal` is refused as an undeclared name, because it is not a configurable name at all (DD-14); every runtime flag route returns 401/403 correctly (there is no more `admin_portal`-flag 404 state), performing no repository read on a denial (proved by poisoning the target-facing methods) and leaving the store unchanged; every successful mutation and every cohort-resolution `GET` produces exactly one content-free log record (DD-10).
- **SC-007**: Adding a selected user by a prefix, suffix, case variant or whitespace variant of a real account ID/email adds nobody, reports "no account found", leaves the store unchanged; no endpoint can enumerate or list accounts; the store contains no email, display name, credential, token or session hash (proved with distinctive sentinels); a stored ID that resolves to no account still renders and is still removable, and removing any account ID always reports success (DD-7); purging an account removes its ID from every managed flag's cohort (DD-9).
- **SC-008**: The operator section renders its loading, saving, empty-cohort, not-found/unresolvable, degraded, list-fetch-failure and mutation-error states, each error state carrying the correlation ID when available; a lightweight confirmation is required before setting a flag OFF or removing the last selected member and not before any other mutation; the retained selected-user count is visible while a flag is OFF or ON (DD-6); the mode control is a native `fieldset`/`legend` radio group, always exactly one option checked, and each Remove action's accessible name includes the row's identity with focus restored to a defined target after removal; the section reflows usably at 390×851; every mutation result is rendered from the server's returned state; and with an unreadable store every flag resolves to ineffective, the section's controls are disabled, every mutation is refused, and the store's rows are unchanged afterward.

## Manual Acceptance Checks

Use **purpose-seeded, non-real accounts** (`@example.com` addresses created for the check). Any pasted output or screenshot must have account IDs and email addresses redacted before it enters PR or acceptance evidence — constitution Principle I forbids real user data there.

- Sign in as the seeded operator, set `voice_brain_dump` to SELECTED_USERS, add the seeded check account, and confirm in a second browser signed in as that account that the capability appears without signing out.
- Remove the account again and confirm the capability disappears from the already-open second browser within about fifteen seconds.
- Set `voice_brain_dump` back to OFF, confirm the confirmation step appears and is required, and confirm the (now empty) cohort count is still visible on the row.
- Confirm no admin entry appears anywhere in navigation or the account menu (009 PD-1 still holds), and that a non-operator member navigating directly to `/admin` sees only the generic denied state — and that an authorized operator reaches `/admin` regardless of any flag state, since there is no flag left to gate it (DD-14).

- any edit to `.github/workflows/`/`scripts/` beyond retiring the three managed flags' entries from the deploy-staged `BRAIN_BUDDY_FEATURE_FLAGS` string and the `admin_portal` name everywhere it is parsed or validated (DD-14, DD-15; Lane G) — no other deploy mechanism or byte-equivalence assertion changes;
- rollback test machinery beyond SC-003's migration-parity claim.

## Assumptions

- The production backend runs as a single process on a single Fly machine with `min_machines_running = 1` and the `brain_buddy_data` volume mounted at `/app/data`, so SQLite's own single-writer transaction locking is sufficient serialization, matching the pattern `TaskRepository` already uses on the same volume. A move to multiple concurrent backend machines would need this assumption re-examined; not in this feature.
- Operators are the feature 009 allow-list; this feature introduces no new identity, credential, role or login path, and inherits the accepted PD-2/PD-5 risk that the production operator is the seeded smoke identity. The Admin Portal's availability no longer depends on any flag (DD-14).
- Every operator mutation and every cohort-resolving read is now recorded content-free by the existing application logger, in the same shape feature 009 already uses (DD-10); this feature adds no new record type, schema or store.
- No maximum cohort size is enforced. Cohorts are expected to stay small — built one exact-match add at a time, with no listing, search or bulk-import path — so the per-read email-resolution fan-out and the operator screen stay practical without an explicit bound. Bounding them is a follow-up if it ever matters.
- **Primary loop:** this feature does not change the capture → atomic items → clarify/approve → route/CRT → Weekly Review → evidence loop (constitution Principle V). It changes *who* is exposed to already-built capabilities, not what those capabilities do.
- **Viewport:** the `/admin` screen remains usable at a 390×851 viewport; [design.md](design.md) states the reflow treatment explicitly (FR-010, SC-008). It is operator tooling and no mobile-client evidence is required.
- The 15-second interval is a founder-set default, not a derived requirement, stated as a single named constant so changing it is one edit. Untouched by the 2026-08-15 correction.
- Flag changes are **not** retroactive: work already dispatched under a flag keeps its existing per-feature behaviour.
- **One-time migration, not a standing compatibility layer** (DD-15): `BRAIN_BUDDY_FEATURE_FLAGS`/`BRAIN_BUDDY_FEATURE_FLAG_INTERNAL_USERS` are read for the three managed flags exactly once, inside migration code only. The env var itself is not deleted — it keeps staging `delivery_canary`, the one flag still deploy-owned — but the three managed flags' entries are retired from the deploy-staged string (Lane G), since staging them would be inert after migration.
