# Plan: Shared Apple Rust bridge cache

**Spec**: [spec.md](spec.md). **Design**: [design.md](design.md), N/A because there is no user-visible surface.

## Summary and technical context
Add `.github/workflows/warm-rust-bridge.yml`, a trusted push-to-main workflow with read-only contents permission and no environments or secrets. It runs on main pushes (including this workflow's landing), separate from the product CI graph, and serializes producer runs with cancel-in-progress false. A two-entry matrix prepares the existing full Apple and Mac-only bridge variants. Existing CI consumers and keys remain unchanged.
Select Xcode with `ios/scripts/select-xcode.sh`, then compute the identical key from `git rev-parse HEAD:rust HEAD:ios/scripts/build-rust-bridge.sh`, `xcodebuild -version`, `uname -m`, and target selector (`all` or the two darwin targets). Restore/save exactly the same two paths as `.github/workflows/ci.yml`. Install pinned Rust and invoke the unchanged bridge script only on an exact miss. No partial-key fallback. The push workflow checks out its exact triggering SHA. Both matrix entries use the pinned Rust action currently used by CI and Rust 1.99.0. Failed warming is visible but cannot bypass any required check; consumers rebuild cold.

## Ownership, failure and rollback
Writer owns the new workflow, the focused extension in `scripts/test_validate_ci_artifacts.py`, and the necessary invocation in `.github/workflows/ci.yml` only; conductor owns planning/evidence and Git operations. The follow-up documentation owns only ios/README.md and this feature's evidence. On warming failure or cache eviction consumers retain the unchanged cold build. Reverting the new workflow stops warming, with no store/schema rollback. Do not delete caches during normal delivery, change cache permissions or expose landing/production secrets. If an unusable exact-key cache is demonstrated, stop consumers from being counted green, identify only the affected key/ref, and obtain separately recorded owner approval before deleting that entry and rerunning a cold build. Merely reverting the producer does not repair an already bad artifact. No migration.

## Cache lifecycle and log disposition
The existing GitHub Actions cache lifecycle is unchanged: platform-managed inactivity eviction (currently seven days since last access) and repository quota eviction; no new TTL, quota, cleanup automation or personal-data policy. Access refreshes activity. These are source-derived compiler artifacts, not runtime/user data: excluded from account export and untouched by account purge, and they may survive an account purge. No new privacy retention choice is introduced by using the existing cache mechanism. Reference: https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy .
Redact workspace, runner-home and runner-temp roots from the new producer's bridge build stdout/stderr before they enter its log (keep pipefail so build failures remain failures). Evidence contains run URLs, git/cache identifiers and counts/timings only, never credentials or user/device-local paths.
